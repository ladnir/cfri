\section{The Native RAA Relation Compiler}

We now restart Blaze at the model where the Blaze paper first lives: the native
multilinear IOP layer.  This is deliberately before Merkle trees, BaseFold,
systematic encodings, or concrete coordinate-opening implementations.  At this layer the prover
and verifier can name committed Boolean oracle handles \(R_h:\B^d\to\F\),
commit them to MLE oracle handles \(\widehat O_h:\F^d\to\F\), and ask for
field-point MLE evaluations of those hatted handles.

The goal of the native layer is not to prove proximity to a codeword.  Its goal
is to compile one algebraic statement into a small set of MLE evaluation
requests and Boolean-sum claims.  The later authentication layer will then make
those requests cryptographic.

\[
  \begin{aligned}
  \text{RAA relation}
  &\Longrightarrow
  (\EvalReqs,\SumClaims) \\
  &\Longrightarrow
  \text{batched sumcheck}
  \Longrightarrow
  \text{more }\EvalReqs .
  \end{aligned}
\]

\subsection{Native Relation}

Fix a field \(\F\).  Let \(K=2^k\) be the message length and \(N=2^n\) be the
RAA codeword length.  The base native relation is \(\RMLE[\PRAA]\).  The public
evaluation claim is
\[
  z\in\F^k,\qquad v\in\F,
\]
and the implicit input is an alleged codeword
\[
  y\in\F^{\B^n}.
\]
The prover witness is a message tensor
\[
  m\in\F^{\B^k}.
\]
The claim is that
\[
  y=\PRAA(m)
  \qquad\text{and}\qquad
  \MLE(m)(z)=v.
\]

The RAA map is public and has the stage form
\[
  \PRAA(m)
  =
  \Acc\circ M_{\pi_2}\circ\Acc\circ M_{\pi_1}\circ F_{\mathrm{rep}}(m),
\]
where \(F_{\mathrm{rep}}:\F^{\B^k}\to\F^{\B^n}\) repeats message entries,
\(M_{\pi_i}\) is the permutation operator for a public permutation
\(\pi_i:\B^n\to\B^n\), and \(\Acc\) is the prefix-sum map over
\(\B^n\).  We use the push-forward convention
\[
  (M_\pi x)[\pi(b)]=x[b]
  \qquad(b\in\B^n).
\]
Equivalently, \((M_\pi x)[a]=x[\pi^{-1}(a)]\).  This convention is chosen so
that the tagged-product permutation check below compares the pairs
\((x[b],\pi(b))\) with \((y[a],a)\).  The Blaze text states the permutation
test with the same tagged leaves but writes the relation in pullback form
\(y[b]=x[\pi(b)]\)~[Blaze24].  In this explainer we fix the convention that
makes the product argument literal; if one instead uses the pullback
convention, the same checker should be read with \(\pi^{-1}\) in place of
\(\pi\).

Thus an honest prover's stage tensors satisfy
\[
  \begin{aligned}
  u_0&=m,&
  u_1&=F_{\mathrm{rep}}(u_0),&
  u_2&=M_{\pi_1}u_1,&
  u_3&=\Acc(u_2),\\
  u_4&=M_{\pi_2}u_3,&
  u_5&=\Acc(u_4)=y.
  \end{aligned}
\]

The prover provides Boolean oracle handles for
\[
  u_0=m\in\F^{\B^k},
  \qquad
  u_2,u_3,u_4\in\F^{\B^n},
  \qquad
  f_1,g_1,f_2,g_2\in\F^{\B^{n+1}}.
\]
The native MLIOP functionality commits those Boolean handles into hatted MLE
handles before the verifier asks field-point evaluation questions.
The prover does not send \(u_1\) or \(u_5\) as separate native messages.
Queries to \(u_1\) are emulated from \(u_0\) using the repetition layout:
we write
\[
  \widehat O_{u_1}:=\RepView(\widehat O_{u_0}),
  \qquad
  \widehat O_{u_1}(r):=\widehat O_{u_0}(\mathsf{msg}(r)).
\]
This is a derived view, not a fresh call to
\(\mathcal F_{\mathrm{MLIOP}}.\mathsf{Commit}\).  The final stage \(u_5\) is
the input codeword handle supplied to the checker.

\subsection{Request And Claim Sets}

A native evaluation request is a tuple
\[
  (J,r,v)\in\EvalReq,
\]
where \(J\) is a handle that can later authenticate MLE values, \(r\in\F^d\)
has the handle's dimension, and \(v\in\F\).  In the native MLIOP section \(J\)
is a hatted MLE handle \(\widehat O:\F^d\to\F\).  In the compiled Blaze section
the same slot is a coordinate-opening handle \(C\).  The request means that the
later verifier check needs
\[
  J(r)=v.
\]
For example, \((\widehat O_{u_3},r,s)\) means that the value \(s\) must be the
MLE evaluation of the tensor \(u_3\) at \(r\).

A Boolean-sum claim is stored in \(\SumClaims\).  Its logical content is
\[
  (s,G)\in\SumClaims
  \quad\Longleftrightarrow\quad
  \sum_{X\in\B^d}G(X)=s.
\]
In protocol boxes below, the reducers do not return an opaque polynomial name.
They return a small record that says which public residual form is being used,
which MLE handle it touches, which projection point was sampled, and what the
Boolean-sum target is.  The batched sumcheck then expands those records
explicitly.

The native layer uses two kinds of outputs:
\[
  \EvalReqs,\qquad \SumClaims.
\]
\(\EvalReqs\) are MLE claims to authenticate later.  \(\SumClaims\) are
Boolean sums to feed into sumcheck.  Some apparent scalar equalities, such as
the permutation root equality, are encoded by reusing or deriving values inside
\(\EvalReqs\) instead of carrying a separate equality set.

\subsection{How Native Tensor Checks Compose}

The same pattern appears in every RAA stage.  Start with a large relation
between named tensors.  Rewrite that relation as a residual tensor
\[
  R\in\F^{\B^s}
\]
that should be zero at every Boolean coordinate:
\[
  R[a]=0
  \qquad(a\in\B^s).
\]
Each residual value is a public low-degree expression in MLE evaluations of the
named tensors.  Abstractly,
\[
  R[a]
  =
  \Phi_a\Bigl(
    \MLE(t_{j_1})(\psi_1(a)),
    \ldots,
    \MLE(t_{j_q})(\psi_q(a))
  \Bigr),
\]
where \(t_{j_1},\ldots,t_{j_q}\) are the participating tensors, the address
maps \(\psi_t:\B^s\to\F^{d_{j_t}}\) and the expression \(\Phi_a:\F^q\to\F\)
are public.  The subscript \(a\) only means that the coefficients of the
expression may depend on the residual coordinate.
To use sumcheck, the Boolean-coordinate formula must come with a low-degree
field extension: the maps \(\psi_t\) and the expression \(\Phi_a\) are extended
to field points in the way specified by the concrete check.  This is not an
extra commitment.  It is part of the algebraic description of the residual
identity being checked.

The verifier does not read all of \(R\).  It samples a field point
\[
  r\in\F^s
\]
and projects the zero claim to one scalar equation:
\[
  \sum_{a\in\B^s}\chi_a(r)R[a]=0.
\]
If \(R\) is not the zero tensor, this random projection fails with high
probability over \(r\).  When the projected sum is still too large to compute
directly, the prover and verifier run sumcheck on the projected identity.
Sumcheck does not authenticate any tensor value by itself; it only reduces the
identity to endpoint claims of the form
\[
  \MLE(H_j)(r_j)=v_j.
\]
Those endpoint claims become \(\EvalReqs\).  The native layer records them; the
later authentication layer checks them.

A small example is the pointwise product relation
\[
  C[a]=A[a]B[a]\qquad(a\in\B^s).
\]
The residual is
\[
  R[a]=C[a]-A[a]B[a].
\]
The projected zero claim is
\[
  \sum_{a\in\B^s}\chi_a(r)\bigl(C[a]-A[a]B[a]\bigr)=0.
\]
If the prover cheats at one coordinate \(a_0\), the bad contribution is weighted
by \(\chi_{a_0}(r)\).  The point is not that the verifier checks the coordinate
\(a_0\) directly.  The point is that a random linear projection turns a large
coordinate-wise relation into one low-degree scalar identity, and sumcheck then
turns that identity into a few MLE endpoint requests.

\subsection{Accumulator Reducer}

The accumulator relation has the form
\[
  y=\Acc(x),
  \qquad
  x,y\in\F^{\B^n}.
\]
Let
\[
  \widehat A:\F^n\times\F^n\to\F
\]
be the multilinear extension of the accumulator matrix, where the Boolean
matrix has entry \(A[b,a]=1\) exactly when \(\Int(b)\ge \Int(a)\) in the
natural binary order.  In ordinary coordinate language,
\[
  y[b]=\sum_{a\le b}x[a].
\]
This matrix is conceptually \(N\times N\), but the verifier never materializes
it.  For fixed \(r\in\F^n\), the weights
\((\widehat A(r,X))_{X\in\B^n}\) can be generated in one linear pass over the
Boolean domain, and a single field-point value
\(\widehat A(r,s)\) can be computed by the usual recursive comparison formula
for the predicate \(\Int(b)\ge\Int(a)\).  Thus the reducer uses the
accumulator matrix as a compact algebraic kernel, not as a dense table.

The verifier cannot check this equation for every \(b\).  Instead it samples a
field point \(r\in\F^n\) and asks for the same linear relation at that MLE
point.  For an honest accumulator,
\[
  \MLE(y)(r)
  =
  \sum_{X\in\B^n}\widehat A(r,X)\,x[X]
  \qquad
  \text{for every }r\in\F^n.
\]
The value \(\MLE(y)(r)\) is not trusted for free.  The prover sends it as a
scalar \(s\), the reducer records \((\widehat O_y,r,s)\) as an evaluation request,
and the Boolean-sum claim says that the accumulator input \(x\) must sum to the
same scalar \(s\).

\begin{enumerate}[leftmargin=0.24in,label=\textbf{A\arabic*.},itemsep=0.06em,topsep=0.06em,parsep=0pt]

The record \(B_{\mathrm{acc}}=(\mathsf{acc},s_y,\widehat O_x,r)\) means
\[
  \sum_{X\in\B^n}\widehat A(r,X)\MLE(x)(X)=s_y,
\]
where \(\widehat O_x\) is the handle that will later authenticate endpoint
values of \(\MLE(x)\).  The scalar \(s_y\) is local to the reducer.  It is not a
separate output because it is already stored in the evaluation request and in
the Boolean-sum target.
In the RAA relation, this reducer is used twice:
\[
  (u_2,u_3)
  \qquad\text{and}\qquad
  (u_4,y).
\]

\subsection{Permutation Reducer}

The permutation relation has the form
\[
  y=M_\pi x,
  \qquad
  y[\pi(b)]=x[b]\quad\text{for every }b\in\B^n.
\]
The verifier samples \(\alpha,\beta\in\F\).  The prover then constructs two
product-tree tensors \(f,g\in\F^{\B^{n+1}}\).  The leaves are intended to be
\[
  f[\mathsf{leaf}(b)]
  =
  \alpha-\bigl(x[b]+\beta\,\Idx(\pi(b))\bigr),
\]
\[
  g[\mathsf{leaf}(b)]
  =
  \alpha-\bigl(y[b]+\beta\,\Idx(b)\bigr).
\]
If \(y[\pi(b)]=x[b]\) and \(\pi\) is a bijection, these two leaf multisets have
the same product.  The product trees make this global product comparison
locally checkable.

Here is the intuition.  The left product writes each input value together with
the address where it is supposed to land:
\[
  \prod_{b\in\B^n}
    \left(\alpha-\bigl(x[b]+\beta\,\Idx(\pi(b))\bigr)\right).
\]
The right product writes each output value together with its actual address:
\[
  \prod_{a\in\B^n}
    \left(\alpha-\bigl(y[a]+\beta\,\Idx(a)\bigr)\right).
\]
If \(y[\pi(b)]=x[b]\), then renaming the right product by \(a=\pi(b)\) gives
\[
  y[a]=y[\pi(b)]=x[b],
  \qquad
  \Idx(a)=\Idx(\pi(b)),
\]
so the two products are term-by-term equal after reindexing.  If the tagged
multisets differ, the two products agree only with small probability over the
random \(\alpha,\beta\).  The address tag \(\beta\,\Idx(\cdot)\) matters: it
prevents the prover from merely preserving the multiset of values while moving
them to the wrong addresses.

We use the source product-tree coordinate convention
\[
  \mathsf{root}=(1^n,0),\qquad
  \mathsf{leaf}(b)=(0,b),
\]
\[
  \mathsf{parent}(X)=(1,X),\qquad
  \mathsf{left}(X)=(X,0),\qquad
  \mathsf{right}(X)=(X,1).
\]
The same symbols are also the low-degree field maps used in the sumcheck
formulas:
\[
  \mathsf{leaf}(r)=(0,r),\quad
  \mathsf{parent}(r)=(1,r),\quad
  \mathsf{left}(r)=(r,0),\quad
  \mathsf{right}(r)=(r,1)
  \qquad(r\in\F^n).
\]
For \(T\in\F^{\B^{n+1}}\), define
\[
  \mathsf{TreeRes}(T,X)
  =
  \widehat T(\mathsf{parent}(X))
  -
  \widehat T(\mathsf{left}(X))\,\widehat T(\mathsf{right}(X)).
\]
On Boolean \(X\), the equation \(\mathsf{TreeRes}(T,X)=0\) says that the node
named by \(\mathsf{parent}(X)\) is the product of the two children named by
\(\mathsf{left}(X)\) and \(\mathsf{right}(X)\).  Therefore a valid product tree
has a root equal to the product of all its leaves.  The coordinate
\(1^{n+1}\) is the padding point above the root; the honest construction sets
it to \(0\), so the residual at \(X=1^n\) also vanishes.  In protocol boxes,
\(\mathsf{TreeRes}(H_T,X)\) means this same expression with tensor label
\(H_T\); the prover instantiates the polynomial during sumcheck, and the
verifier records the required endpoint evaluations.
For a non-Boolean sumcheck endpoint \(q\in\F^n\), this is a formal-extension
evaluation, not a coordinate opening of \(T\).  Concretely, evaluating
\(\mathsf{TreeRes}(T,q)\) requires the three MLE values
\[
  \widehat T(\mathsf{parent}(q)),\qquad
  \widehat T(\mathsf{left}(q)),\qquad
  \widehat T(\mathsf{right}(q)).
\]
The Blaze prose later says that this contributes two queries per product-tree
tensor.  With the residual written above, the scalar-tensor realization needs
three formal-extension values.  We therefore treat the two-query line as a typo
or as accounting for a virtual/packed object not specified there.  In this
paper all three evaluation claims are made explicit.

The records \(B_f=(\mathsf{tree},0,\widehat O_f,r)\) and
\(B_g=(\mathsf{tree},0,\widehat O_g,r)\) mean
\[
  \sum_{X\in\B^n}\chi_r(X)\mathsf{TreeRes}(f,X)=0,
  \qquad
  \sum_{X\in\B^n}\chi_r(X)\mathsf{TreeRes}(g,X)=0.
\]
The handle stored in each record tells the later endpoint checks which
committed product-tree tensor the values must come from.

The RAA relation uses this reducer twice:
\[
  (u_1,u_2,\pi_1)
  \qquad\text{and}\qquad
  (u_3,u_4,\pi_2).
\]
Therefore it introduces four product-tree tensors
\[
  f_1,g_1,f_2,g_2\in\F^{\B^{n+1}}.
\]
Each tree has \(2^{n+1}=2N\) entries.

For each permutation edge, read the checks as one correlated argument:
the derived leaf values load the claimed products from \(x\) and \(y\), the
parent-child \(\SumClaims\) force \(f\) and \(g\) to be product trees, and the
shared root value compares the two products.  No single one of these checks
proves a permutation by itself.

The top-level Blaze box below performs the native RAA orchestration directly.
It creates the stage handles, calls the two reducers, gathers their returned
requests, and runs one batched sumcheck over the six Boolean-sum claims in a
fixed order.  The \(u_1\) handle is virtual, but not opaque: its evaluation
rule is written where it is created.

\subsection{The Batched Six-Sumcheck}

The two accumulator reducers contribute two Boolean-sum claims \(B_{u2}\) and
\(B_{u4}\).  The two permutation reducers contribute four product-tree
Boolean-sum claims \(B_{f1},B_{g1},B_{f2},B_{g2}\).  Blaze batches these six
named claims into
one sumcheck by sampling one scalar
\[
  \lambda\leftarrow\F
\]
and using the powers \(1,\lambda,\lambda^2,\ldots,\lambda^5\) as batching
weights.
This is only native batching of Boolean-sum claims.  It is not the later
compiler-level batching of arbitrary MLE evaluation requests.  If any one of
the six Boolean-sum identities is false, then the vector of six errors defines
a nonzero polynomial in \(\lambda\) of degree at most \(5\).  The batching step
can hide that error with probability at most \(5/|\F|\).  Conditioned on the
batched claim being false, ordinary sumcheck soundness applies.  This is the
same scalar-power batching pattern used in Blaze's Remark~2.3.

Only the Boolean-sum identities are batched here.  The permutation leaf
equations and root equality have already been encoded as evaluation requests by
deriving leaf values and reusing one root value.  The endpoint values produced
by this sumcheck are still not trusted; they are appended to \(\EvalReqs\) and
authenticated later by \(\MLEAuth\).
This is exactly the endpoint discipline from
Figure~\ref{fig:subroutine-sumcheck-terminal}: \(\SumCheck_n\) produces one
terminal scalar \(T_{\mathrm{sc}}\), and the surrounding RAA flow expands that scalar
into MLE requests against the existing handles \(\widehat O_{u_2}\),
\(\widehat O_{u_4}\), \(\widehat O_{f_1}\), \(\widehat O_{g_1}\),
\(\widehat O_{f_2}\), and \(\widehat O_{g_2}\).

\noindent\(\underline{\RAASixSumcheck(\verifier:(B_{u2},B_{u4},B_{f1},B_{g1},B_{f2},B_{g2}),\ \prover:(u_2,u_4\in\F^{\B^n}, f_1,g_1,f_2,g_2\in\F^{\B^{n+1}}))\to(a_{\mathrm{sc}}\in\{0,1\},\EvalReqs_{\mathrm{sc}})}\)

\begin{enumerate}[leftmargin=0.24in,label=\textbf{S\arabic*.},itemsep=0.06em,topsep=0.06em,parsep=0pt]
  \item \(\verifier\): let
        \(B_{u2}=(\mathsf{acc},s_{u2},\widehat O_{u_2},r_{u2})\) and
        \(B_{u4}=(\mathsf{acc},s_{u4},\widehat O_{u_4},r_{u4})\).
  \item \(\verifier\): let
        \(B_{f1}=(\mathsf{tree},0,\widehat O_{f_1},r_{f1})\),
        \(B_{g1}=(\mathsf{tree},0,\widehat O_{g_1},r_{g1})\),
        \(B_{f2}=(\mathsf{tree},0,\widehat O_{f_2},r_{f2})\), and

        \(\lambda\) to \(\prover\).
  \item \(\verifier\): \(S_\lambda\gets
        s_{u2}+\lambda s_{u4}\).
  \item \(\prover\): \(G_\lambda(X)\gets
        \widehat A(r_{u2},X)\MLE(u_2)(X)
        +\lambda\,\widehat A(r_{u4},X)\MLE(u_4)(X)
        +\lambda^2\chi_{r_{f1}}(X)\mathsf{TreeRes}(f_1,X)
        +\lambda^3\chi_{r_{g1}}(X)\mathsf{TreeRes}(g_1,X)
        +\lambda^4\chi_{r_{f2}}(X)\mathsf{TreeRes}(f_2,X)
        +\lambda^5\chi_{r_{g2}}(X)\mathsf{TreeRes}(g_2,X)\).
  \item \(\prover,\verifier\):
        \((a_{\mathrm{round}},r_{\mathrm{sc}},T_{\mathrm{sc}})

\subsection{Blaze In The \(\mathcal F_{\mathrm{MLIOP}}\)-Hybrid}

We can now state the top-level Blaze flow as a hybrid protocol.  In this

into MLE oracle handles, and the verifier later obtains MLE evaluations at
field points.

Figure~\ref{fig:native-blaze-fmliop-hybrid} is therefore not an incomplete

evaluation requests of the form \(J(r)=v\), and the top-level protocol

\(\mathcal F_{\mathrm{MLIOP}}.\mathsf{Eval}\).  Give this protocol real
implementations of the coordinate-oracle layer and of
\(\mathcal F_{\mathrm{MLIOP}}\), and the composition is a concrete Blaze

batching, BaseFold, Merkle trees, or something else; the Blaze algebra below

\[

\section{Blaze Proof Replay In Handle Form}

\subsection{The Generic Proximity Gap Behind Row Folding}

The extraction argument for the row fold needs one coding-theory input.  This is
the point where it is tempting to reopen the internals of RAA, but we should not
do that here.  For this step, the only RAA-specific fact we need is the setup
event that the packed RAA code
\[
  \PRAA:\F^{\B^k}\to\F^{\B^n}
\]
is linear over \(\F\) and has relative distance \(d\).  Blaze proves this by
its RAA distance analysis~[Blaze24, Section~9].  Once that event holds, the
row-folding proximity argument is generic.

\begin{lemma}[Row-folding proximity gap; cf. Blaze Corollary~2.6]
\label{lem:row-fold-proximity-gap}
Let \(C\subseteq\F^{\B^n}\) be any linear code with relative distance \(d\), and
let \(C^L\subseteq\F^{\B^\ell\times\B^n}\) be its row-wise interleaving, where
\(L=2^\ell\).  Let
\[
  c\in\F^{\B^\ell\times\B^n}
\]
be a committed matrix satisfying
\[
  \Delta(c,C^L)>\delta.
\]
If \(\varepsilon>0\) and \(\delta-\varepsilon<d/3\), then for a uniformly random
\(\rho\in\F^{\B^\ell}\), the folded word
\[
  c_\star[b]
  =
  \sum_{h\in\B^\ell}\rho[h]\,c[h,b]
  \qquad(b\in\B^n)
\]
satisfies
\[
  \Delta(c_\star,C)>\delta-\varepsilon
\]
except with probability at most \(1/(\varepsilon|\F|)\).
\end{lemma}

\begin{proof}[Proof input]
This is the linear proximity-gap theorem used by Blaze as Corollary~2.6,
derived from Ben-Sasson, Kopparty, and Saraf~[BKS18,Blaze24].  We use it as a
black-box coding theorem with the hypotheses and conclusion stated above.  The
surprising part is that the lemma uses only linearity and distance.  It does
not use the fact that RAA was built from repetition, random permutations, and
accumulators.

Here is the proof intuition.  A random row fold samples a random vector from the
row span of \(c\).  The bad event is not merely that a few coordinate errors
cancel.  The bad event is that this random row-span vector lands unusually close
to the code \(C\).  The proximity-gap theorem says that a linear code of
distance \(d\) has no large medium-distance cloud below the \(d/3\) threshold:
if an affine or linear space contains one vector far from the code, then almost
every vector in that space is still far from the code.  Thus, once \(c\) is far
from \(C^L\), a random row combination remains far from \(C\) with high
probability.
\end{proof}

The actual Blaze soundness proof applies this generic lemma after normalizing
the evaluation target.  If the prover sends row-evaluation values \(u\), Blaze
looks at
\[
  c-u\otimes C(1),
\]
where \(C(1)\) is the encoding of the all-ones message.  This shifts the target
evaluation to zero, so the distance question becomes distance from a linear
space rather than an affine space.  After the random row fold, the proof shifts
back and obtains a folded claim of the form
\[
  c_\star \text{ is close to some } C(m_\star)
  \quad\text{with}\quad
  \MLE(m_\star)(z_{\mathrm{in}})=v_\star.
\]
This is the proximity statement that the hybrid extractor will use.

\subsection{The Hybrid Extractor}

We now define the extractor before proving that it works.  The extractor is
allowed to be computationally unbounded.  It runs in the
\(\mathcal F_{\mathrm{MLIOP}}\)-hybrid model and treats
\(\mathcal F_{\mathrm{MLIOP}}\) as a black box.  For an MLE handle
\(\widehat O_h\), write
\[
  \mathsf{Ext}_{\mathrm{MLIOP}}(\widehat O_h)=h^\dagger
\]
for the tensor represented by that MLE handle.  The functionality is
relation-agnostic: it does not know whether \(h^\dagger\) is an RAA stage, a
product tree, or close to any code.  It only guarantees that
\[
  \mathcal F_{\mathrm{MLIOP}}.\mathsf{Eval}(\widehat O_h,r)
  =
  \MLE(h^\dagger)(r).
\]
All proximity claims below are proved outside \(\mathcal F_{\mathrm{MLIOP}}\),
using the row fold and the generic proximity-gap lemma.

For a matrix \(m\in\F^{\B^\ell\times\B^k}\), write \(\PRAA^L(m)\) for the
row-wise interleaved packed RAA encoding:
\[
  \PRAA^L(m)[h,\ast]=\PRAA(m[h,\ast])
  \qquad(h\in\B^\ell).
\]

Line E6 is deliberately unbounded: it is an extractor step, not an honest-prover
algorithm.  The proof obligation is to show that, for accepting transcripts,
the closest codeword chosen in E6 is actually close enough and has the claimed
evaluation.

\paragraph{Folded extraction.}
First look at lines E2--E5.  The terminal evaluation request in
Figure~\ref{fig:native-blaze-fmliop-hybrid} asks the verifier to check
\[
  \mathcal F_{\mathrm{MLIOP}}.\mathsf{Eval}
  (\widehat O_{u_0},z_{\mathrm{in}})
  =
  v_\star.
\]
By the target functionality's contract, this means
\[
  \MLE(u_0^\dagger)(z_{\mathrm{in}})=v_\star.
\]
The accumulator, permutation, and six-sumcheck checks then force the extracted
tensors to satisfy the RAA stage equations, except with the algebraic
soundness error from the random challenges and sumcheck:
\[
  u_1^\dagger=F_{\mathrm{rep}}(u_0^\dagger),\quad
  u_2^\dagger=M_{\pi_1}u_1^\dagger,\quad
  u_3^\dagger=\Acc(u_2^\dagger),\quad
  u_4^\dagger=M_{\pi_2}u_3^\dagger,\quad
  u_5^\dagger=\Acc(u_4^\dagger).
\]
The handle \(\widehat O_{u_5}\) is the MLE handle committed from the virtual
folded coordinate handle \(R_\star\).  Therefore the raw folded word
\(c_\star\) from E2 and the extracted tensor \(u_5^\dagger\) are linked by the
outer row-fold/proximity argument, not by a special RAA-aware MLIOP rule.
Combining that proximity statement with the stage equations gives
\[
  c_\star \text{ is close to } \PRAA(m_\star),
  \qquad
  \MLE(m_\star)(z_{\mathrm{in}})=v_\star.
\]
This is what the local extractor learns from one accepting folded transcript.

\paragraph{Global extraction.}
Line E6 chooses a closest interleaved RAA codeword
\[
  c_{\mathrm{near}}=\PRAA^L(m)
\]
to the committed matrix \(c\).  Suppose, toward soundness, that \(c\) were far
from every interleaved RAA codeword whose message evaluates to \(v\) at
\((z_{\mathrm{slice}},z_{\mathrm{in}})\).  The prover's row-evaluation vector
\(u\) must still pass the explicit interpolation check
\[
  v=
  \sum_{h\in\B^\ell}\chi_h(z_{\mathrm{slice}})\,u[h].
\]
After the verifier samples \(\rho\), the folded value is
\[
  v_\star=\sum_{h\in\B^\ell}\rho[h]\,u[h].
\]
The generic proximity-gap lemma above says that a far committed matrix remains
far after a random row fold, except with probability \(1/(\varepsilon|\F|)\).
Equivalently, after Blaze's normalization by \(u\otimes C(1)\), the folded word
\(c_\star\) is far from every \(\PRAA(m_\star)\) satisfying
\[
  \MLE(m_\star)(z_{\mathrm{in}})=v_\star.
\]
That contradicts the folded extraction conclusion unless one of the named
soundness errors occurs.  Hence an accepting transcript implies that E6's
closest codeword is close and that its decoded message \(m\) satisfies
\[
  \MLE(m)(z_{\mathrm{slice}},z_{\mathrm{in}})=v.
\]

This is the modular picture.  The folded extractor explains what a single
accepting row fold certifies.  The global extractor uses the generic
proximity-gap lemma to turn that folded certificate into a statement about the
whole committed matrix.

The Blaze paper uses a different presentation style.  It first constructs an
MLIOP for \(\RMLE[\PRAA]\), then describes an MLIOP-to-IOPP transformation using

\subsection{Self-Contained Import: Blaze Lemma~6.1 In Handle Form}

This subsection begins the proof import.  It is written as a local proof, not
as a reading guide to the Blaze paper.  The reader should be able to follow the
objects, the reduction, and the soundness argument from the definitions in this
subsection.  Source labels such as ``Blaze Lemma~6.1'' and
``Claim~6.1.x'' are provenance markers: they say which Blaze step we are
mirroring, but the mathematical content is stated here before it is used.
There is no intended divergence from Blaze in this subsection.

\paragraph{Local statement.}
\begin{lemma}[Interleaving RMLE reduction in handle form; cf. Blaze Lemma~6.1]
\label{lem:blaze-interleaving-handle}
Let
\[
  C:\F^{\B^k}\to\F^{\B^n}
\]
be a linear code with relative distance \(\lambda\).  Assume there is a
proximity protocol for \(\RMLE[C]\): on public \((z,v)\in\F^k\times\F\) and
oracle access to a word \(y\in\F^{\B^n}\), the protocol rejects whenever \(y\)
is far from every codeword \(C(m)\) with \(\MLE(m)(z)=v\), except with its
soundness error.  The interleaving reduction below turns this base protocol
into a proximity protocol for \(\RMLE[C^t]\).

Fix a top-level proximity parameter
\[
  \delta<\lambda/3,
  \qquad
  \delta_{\mathrm{base}}=0.99\,\delta,
  \qquad
  \eta=\delta-\delta_{\mathrm{base}}.
\]
Blaze writes \(\delta'\) for \(\delta_{\mathrm{base}}\).  Lemma~6.1 runs the
base protocol at proximity \(\delta_{\mathrm{base}}\).  If the base protocol's
soundness error is \(\varepsilon(\delta_{\mathrm{base}},k)\), the interleaved
protocol's soundness error is
\[
  \varepsilon(\delta_{\mathrm{base}},k)
  +
  \frac{1}{\eta|\F|}.
\]
The second term is the row-fold loss from the linear proximity-gap theorem
stated below.  The other parameters are the base parameters evaluated at
\(\delta_{\mathrm{base}}\), with the same
index and proof alphabet \(\F\), one extra round, input queries lifted from one
base coordinate to one interleaved column read, and the additional
non-oracle communication for the prover's vector \(u\in\F^t\) and the
verifier's fold vector \(\rho\in\F^t\).  This is Blaze's \(2t+\mathsf{cc}(k)\)
term.  The prover time gains the \(O(tn)\) row-combination work, and the
verifier time gains the \(O(t\cdot q_{\mathrm{input}})\) cost of emulating base
input queries by reading columns of \(c\).  We will not need the full parameter
table for the proof; all proof-relevant parameters are named above.
\end{lemma}

\begin{proof}
This proof is our copy of the interleaving argument.  The source tie-back is
Blaze Lemma~6.1; the proof below spells out the relation, the handle
translation, and the three distance claims locally.

\paragraph{The base relation and its proximity protocol.}
For a message tensor \(m\in\F^{\B^k}\), the codeword is
\[
  y=C(m)\in\F^{\B^n}.
\]
For a point \(z\in\F^k\), \(\MLE(m)(z)\) is the multilinear extension of the
message tensor evaluated at \(z\).  The exact \(\RMLE[C]\) relation is
\[
  ((z,v),y;m)\in\RMLE[C]
  \qquad\Longleftrightarrow\qquad
  y=C(m)\ \text{and}\ \MLE(m)(z)=v.
\]
The corresponding proximity protocol for \(\RMLE[C]\) has oracle access to a
literal word \(y\in\F^{\B^n}\) and receives public \((z,v)\).  Its soundness
promise is phrased as distance from the affine target
\[
  \mathcal A^C_{z,v}
  =
  \{C(m):m\in\F^{\B^k},\ \MLE(m)(z)=v\}.
\]
If \(y\) is farther than the chosen proximity parameter from this set, the base
\(\RMLE[C]\)-IOPP rejects except with its soundness error.  The exact relation
names the witness \(m\); the proximity statement is distance from the affine
set \(\mathcal A^C_{z,v}\), not an extra nearest-neighbor decoding step inside
Lemma~6.1.

The construction below gives a proximity protocol for the row-wise interleaved
relation \(\RMLE[C^t]\) for arbitrary \(t\).  Our protocol uses
Boolean tensor notation, so here we specialize to \(t=2^\ell\); a non-power of
two \(t\) would be handled by the usual padding convention before writing the
slice index as \(\B^\ell\).  In this specialization,
\[
  m\in\F^{\B^\ell\times\B^k},
  \qquad
  c\in\F^{\B^\ell\times\B^n},
  \qquad
  C^t(m)[h,\ast]=C(m[h,\ast]).
\]
Blaze sometimes presents the input alphabet as \(F^t\) or as an extension-field
alphabet.  Here we use the expanded column-vector view
\(\F^{\B^\ell}\).  This is a notation translation, not a proof change: the
Lemma~6.1 protocol and proof use the row decomposition of \(m,c\), verifier
queries to columns of \(c\), and \(\F\)-linear row combinations.

\paragraph{Linear-code facts used locally.}
The proof uses only two code facts about \(C\).  First, \(C\) is linear:
\[
  C(a m_0+b m_1)=aC(m_0)+bC(m_1)
  \qquad(a,b\in\F).
\]
Second, \(C\) has relative distance \(\lambda\): any two distinct codewords
differ on at least a \(\lambda\)-fraction of coordinates.  Equivalently, every
nonzero word in the linear code image of \(C\) has relative Hamming weight at
least \(\lambda\).

\paragraph{Our handle version of the input oracle.}
Blaze gives the verifier oracle access to the interleaved input word \(c\).  In
the fixed protocol above, the corresponding object is the handle
\[
  R_c:\B^n\to\F^{\B^\ell},
  \qquad
  R_c(b)=c[\ast,b].
\]
The literal matrix \(c\) is the expanded semantic object behind the handle.  In
the honest commit path \(c=C^t(m)\).  In the proximity setting \(c\) may be a
malicious literal matrix; the proof concerns whether it is close to an
interleaved codeword with the claimed evaluation.

The verifier's public opening claim is
\[
  z=(z_{\mathrm{slice}},z_{\mathrm{in}})
  \in\F^\ell\times\F^k,
  \qquad
  v\in\F.
\]
Blaze writes this as \(z=(z_1,z_2)\).  The relation target is the affine set
\[
  \mathcal A_{z,v}
  =
  \{C^t(m'):\MLE(m')(z_{\mathrm{slice}},z_{\mathrm{in}})=v\}.
\]
For a word or matrix \(w\) and a set \(S\) of same-shaped words or matrices,
write
\[
  \Delta(w,S)=\min_{s\in S}\Delta(w,s)
\]
for relative Hamming distance from \(S\).

\paragraph{The reduction protocol.}
The reduction protocol has five steps.  Each step names both the semantic word
used in the proof and the handle-level object used by the fixed protocol.
Source tie-back: these are the five steps of Blaze Lemma~6.1, written in our
tensor and handle notation.

\emph{Step 1: announce row evaluations.}
The prover sends a full row-evaluation vector
\[
  u\in\F^{\B^\ell}.
\]
For an honest message \(m\),
\[
  u[h]=\MLE(m[h,\ast])(z_{\mathrm{in}})
  \qquad(h\in\B^\ell).
\]
This is exactly Lines O1--O2 of Figure~\ref{fig:native-blaze-fmliop-hybrid}.

\emph{Step 2: check the top-level value through \(u\).}
The verifier views \(u\) as a Boolean tensor on \(\B^\ell\) and checks
\[
  \MLE(u)(z_{\mathrm{slice}})
  =
  v.
\]
This is Line O3.  This line checks consistency of the announced row
evaluations with the public value.  It is not a proximity test for \(c\).

\emph{Step 3: sample the random row fold.}
The verifier samples a random row-combination vector
\[
  \rho\leftarrow\F^{\B^\ell}.
\]
Blaze calls this vector \(r\).  To avoid collision with later MLE evaluation
points, this paper calls it \(\rho\).  Define
\[
  m_\star=\rho^\top m\in\F^{\B^k},
  \qquad
  c_\star=\rho^\top c\in\F^{\B^n},
\]
meaning
\[
  m_\star[a]=\sum_{h\in\B^\ell}\rho[h]m[h,a],
  \qquad
  c_\star[b]=\sum_{h\in\B^\ell}\rho[h]c[h,b].
\]
In our protocol \(c_\star\) is not sent as a fresh literal string.  It is the
expanded semantics of the virtual handle
\[
  R_\star(b)=\sum_{h\in\B^\ell}\rho[h]R_c(b)[h].
\]
This is Lines O4--O7.

\emph{Step 4: call the base \(\RMLE[C]\)-IOPP on the folded input.}
Run the base \(\RMLE[C]\)-IOPP on public point
\[
  z_{\mathrm{in}}\in\F^k
\]
and public value
\[
  v_\star=\ip{\rho}{u}.
\]
The implicit base input oracle is \(c_\star\).  Since the verifier does not
hold \(c_\star\) as a separately committed string, it emulates each query
\(b\in\B^n\) by reading the column \(R_c(b)\) and returning
\[
  c_\star[b]=\sum_{h\in\B^\ell}\rho[h]R_c(b)[h].
\]
This is exactly what the virtual folded handle \(R_\star\) does.  When
\(C=\PRAA\), Lines O8 onward are the inlined base \(\RMLE[\PRAA]\) checker.

\emph{Step 5: accept only if both layers accept.}
Accept if the row-evaluation check and the base \(\RMLE[C]\)-IOPP both accept.
In the fixed protocol, the later native
\(\RMLE[\PRAA]\) work and its MLE-evaluation checks implement this base call.

\paragraph{Completeness.}
Assume the exact interleaved relation holds:
\[
  c=C^t(m),
  \qquad
  \MLE(m)(z_{\mathrm{slice}},z_{\mathrm{in}})=v.
\]
The honest prover sends \(u[h]=\MLE(m[h,\ast])(z_{\mathrm{in}})\).  Recall the
standard tensor expansion of the MLE:
\[
  \MLE(m)(z_{\mathrm{slice}},z_{\mathrm{in}})
  =
  \sum_{h\in\B^\ell}
  \chi_h(z_{\mathrm{slice}})\MLE(m[h,\ast])(z_{\mathrm{in}}),
\]
where \(\chi_h\) is the equality-basis polynomial for the Boolean point
\(h\in\B^\ell\).  Therefore
\[
  \MLE(u)(z_{\mathrm{slice}})
  =
  \sum_{h\in\B^\ell}\chi_h(z_{\mathrm{slice}})u[h]
  =
  \MLE(m)(z_{\mathrm{slice}},z_{\mathrm{in}})
  =
  v,
\]
so the row check passes.

For every verifier challenge \(\rho\), linearity of \(C\) gives
\[
  c_\star
  =
  \rho^\top c
  =
  \rho^\top C^t(m)
  =
  C(\rho^\top m)
  =
  C(m_\star).
\]
The same expansion used above gives
\[
  \MLE(m_\star)(z_{\mathrm{in}})
  =
  \sum_{h\in\B^\ell}\rho[h]\MLE(m[h,\ast])(z_{\mathrm{in}})
  =
  \ip{\rho}{u}
  =
  v_\star.
\]
Thus the base \(\RMLE[C]\) instance is exact and the base protocol accepts by
its completeness.  Source tie-back: this is the completeness proof of
Blaze Lemma~6.1 translated through \(R_c\) and \(R_\star\).

\paragraph{Soundness setup.}
Fix \(z=(z_{\mathrm{slice}},z_{\mathrm{in}})\) and \(v\).  Let the malicious
literal matrix behind \(R_c\) be
\[
  c\in\F^{\B^\ell\times\B^n}.
\]
Assume \(c\) is \(\delta\)-far from the affine target
\[
  \mathcal A_{z,v}
  =
  \{C^t(m'):\MLE(m')(z_{\mathrm{slice}},z_{\mathrm{in}})=v\}.
\]
Fix a deterministic cheating prover strategy.  Let its first message be
\[
  u\in\F^{\B^\ell}.
\]
If \(\MLE(u)(z_{\mathrm{slice}})\ne v\), the verifier rejects immediately, so
the soundness proof conditions on
\[
  \MLE(u)(z_{\mathrm{slice}})=v.
\]
The goal is now to show that, for a random \(\rho\), the folded input
\(\rho^\top c\) is far from the base affine target
\[
  \mathcal A^C_{z_{\mathrm{in}},\ip{\rho}{u}}
  =
  \{C(q):q\in\F^{\B^k},\
  \MLE(q)(z_{\mathrm{in}})=\ip{\rho}{u}\},
\]
except with the row-fold error from Corollary~2.6.  Then the base
\(\RMLE[C]\)-IOPP rejects this folded instance by its own soundness.

We now convert the affine top-level distance statement into a linear
zero-evaluation statement.  Define
\[
  \mathbf 1\in\F^{\B^k},
  \qquad
  \mathbf 1[a]=1,
\]
and let \(C(\mathbf 1)\in\F^{\B^n}\) be its encoding.  Also define
\[
  \mathcal L_{z_{\mathrm{in}}}
  =
  \{C(q):q\in\F^{\B^k},\ \MLE(q)(z_{\mathrm{in}})=0\}.
\]
The row-wise space \((\mathcal L_{z_{\mathrm{in}}})^t\) consists of matrices
whose rows each lie in \(\mathcal L_{z_{\mathrm{in}}}\).
Because \(C\) is linear, \(\mathcal L_{z_{\mathrm{in}}}\) is a linear subcode
of \(C\).  Its distance is at least the distance \(\lambda\) of \(C\), so it
satisfies the distance hypothesis needed for the row-fold theorem.

\begin{claim}[First shift; cf. Blaze Claim~6.1.1]
\label{claim:blaze-interleaving-first-shift}
The shifted matrix is far from the row-wise zero-evaluation code:
\[
  \Delta\!\left(
    c-u\otimes C(\mathbf 1),
    (\mathcal L_{z_{\mathrm{in}}})^t
  \right)>\delta,
\]
where
\[
  (u\otimes C(\mathbf 1))[h,b]=u[h]\,C(\mathbf 1)[b].
\]
\end{claim}

\begin{proof}
Suppose instead, toward a contradiction, that there exists
\[
  c'\in(\mathcal L_{z_{\mathrm{in}}})^t
  \qquad\text{with}\qquad
  \Delta(c-u\otimes C(\mathbf 1),c')\le\delta.
\]
Define
\[
  c''=c'+u\otimes C(\mathbf 1)
\]
so \(\Delta(c,c'')\le\delta\).  For each row \(h\in\B^\ell\), because
\(c'[h,\ast]\in\mathcal L_{z_{\mathrm{in}}}\), choose
\[
  q'_h\in\F^{\B^k}
  \quad\text{such that}\quad
  C(q'_h)=c'[h,\ast],
  \qquad
  \MLE(q'_h)(z_{\mathrm{in}})=0.
\]
Define
\[
  q''_h=q'_h+u[h]\mathbf 1.
\]
By linearity of \(C\),
\[
  C(q''_h)
  =
  c'[h,\ast]+u[h]C(\mathbf 1)
  =
  c''[h,\ast].
\]
Also,
\[
  \MLE(q''_h)(z_{\mathrm{in}})
  =
  \MLE(q'_h)(z_{\mathrm{in}})
  +
  u[h]\MLE(\mathbf 1)(z_{\mathrm{in}})
  =
  u[h].
\]
Let \(q''\in\F^{\B^\ell\times\B^k}\) be the matrix of these row messages.  Then
\[
  c''=C^t(q'')
\]
and
\[
  \MLE(q'')(z_{\mathrm{slice}},z_{\mathrm{in}})
  =
  \sum_{h\in\B^\ell}\chi_h(z_{\mathrm{slice}})
  \MLE(q''_h)(z_{\mathrm{in}})
  =
  \sum_{h\in\B^\ell}\chi_h(z_{\mathrm{slice}})u[h]
  =
  \MLE(u)(z_{\mathrm{slice}})
  =
  v.
\]
Thus \(c''\in\mathcal A_{z,v}\), while \(\Delta(c,c'')\le\delta\).  This
contradicts the soundness assumption \(\Delta(c,\mathcal A_{z,v})>\delta\).
\end{proof}

\begin{claim}[Random fold preserves linear distance; cf. Blaze Claim~6.1.2]
\label{claim:blaze-interleaving-random-fold}
Except with probability at most \(1/(\eta|\F|)\) over
\(\rho\leftarrow\F^{\B^\ell}\),
\[
  \Delta\!\left(
    \rho^\top(c-u\otimes C(\mathbf 1)),
    \mathcal L_{z_{\mathrm{in}}}
  \right)>\delta_{\mathrm{base}}.
\]
\end{claim}

\begin{proof}
By Claim~\ref{claim:blaze-interleaving-first-shift},
\[
  c-u\otimes C(\mathbf 1)
\]
is far from the linear row-wise space \((\mathcal L_{z_{\mathrm{in}}})^t\).
The only external coding-theory fact used in this layer is the following
linear proximity-gap statement: if a matrix is
\(\delta\)-far from the row-wise interleaving of a linear code of distance at
least \(\lambda\), then a random row combination is
\(\delta-\eta\)-far from the base code except with probability at most
\(1/(\eta|\F|)\), provided \(\delta-\eta<\lambda/3\).  Here the base linear code
is \(\mathcal L_{z_{\mathrm{in}}}\), whose distance is at least \(\lambda\).
Since \(\delta-\eta=\delta_{\mathrm{base}}\), applying this theorem to the
matrix \(c-u\otimes C(\mathbf 1)\) gives exactly the claimed bound.
This is the proximity-preservation step.  It is not a coordinate spot check:
the random fold is used together with the proximity-gap theorem behind
Corollary~2.6.
\end{proof}

\begin{claim}[Second shift; cf. Blaze Claim~6.1.3]
\label{claim:blaze-interleaving-second-shift}
Condition on a challenge \(\rho\) for which
Claim~\ref{claim:blaze-interleaving-random-fold} holds.  Define the base affine
target
\[
  \mathcal A'_{z_{\mathrm{in}},v_\star}
  =
  \{C(q):\MLE(q)(z_{\mathrm{in}})=v_\star\},
  \qquad
  v_\star=\ip{\rho}{u}.
\]
Then
\[
  \Delta(\rho^\top c,\mathcal A'_{z_{\mathrm{in}},v_\star})
  >
  \delta_{\mathrm{base}}.
\]
\end{claim}

\begin{proof}
Suppose toward a contradiction that there exists
\[
  c'\in\mathcal A'_{z_{\mathrm{in}},v_\star}
  \qquad\text{with}\qquad
  \Delta(\rho^\top c,c')\le\delta_{\mathrm{base}}.
\]
Because \(c'\in\mathcal A'_{z_{\mathrm{in}},v_\star}\), choose
\[
  q'\in\F^{\B^k}
  \quad\text{such that}\quad
  C(q')=c',
  \qquad
  \MLE(q')(z_{\mathrm{in}})=v_\star.
\]
Define
\[
  q''=q'-v_\star\mathbf 1,
  \qquad
  c''=C(q'')=c'-v_\star C(\mathbf 1).
\]
Then
\[
  \MLE(q'')(z_{\mathrm{in}})
  =
  v_\star-v_\star\MLE(\mathbf 1)(z_{\mathrm{in}})
  =
  0,
\]
so \(c''\in\mathcal L_{z_{\mathrm{in}}}\).  Moreover,
\[
  \rho^\top(u\otimes C(\mathbf 1))
  =
  \left(\sum_{h\in\B^\ell}\rho[h]u[h]\right)C(\mathbf 1)
  =
  v_\star C(\mathbf 1).
\]
Therefore
\[
\begin{aligned}
  \rho^\top(c-u\otimes C(\mathbf 1))-c''
  &=
  \rho^\top c-v_\star C(\mathbf 1)
  -\bigl(c'-v_\star C(\mathbf 1)\bigr) \\
  &=
  \rho^\top c-c'.
\end{aligned}
\]
Thus \(c''\in\mathcal L_{z_{\mathrm{in}}}\) is
\(\delta_{\mathrm{base}}\)-close to
\(\rho^\top(c-u\otimes C(\mathbf 1))\), contradicting the random-fold distance
statement.
\end{proof}

\paragraph{Conclusion of Lemma~6.1.}
For every good \(\rho\), the virtual folded input word
\[
  c_\star=\rho^\top c
\]
is \(\delta_{\mathrm{base}}\)-far from every base codeword \(C(q)\) whose
message satisfies
\[
  \MLE(q)(z_{\mathrm{in}})=v_\star.
\]
Therefore the base \(\RMLE[C]\)-IOPP rejects the folded instance except with
its own soundness error.  Adding the Corollary~2.6 row-fold loss gives the
soundness bound stated at the beginning of this subsection.  Source tie-back:
this completes our proof of Lemma~\ref{lem:blaze-interleaving-handle}, mirroring
Blaze Lemma~6.1.

Instantiating \(C=\PRAA\), the first imported arrow for our fixed protocol is
\[
  \RMLE[\PRAA^t]
  \xrightarrow{\text{Blaze Lemma~6.1}}
  \RMLE[\PRAA].
\]
In our API language, this says: the matrix behind \(R_c\) is reduced to the
virtual folded handle \(R_\star\); if the literal matrix is far from every
valid interleaved packed-RAA codeword with the claimed top-level MLE value,
then, except for the Lemma~6.1 row-fold loss, the folded base instance is far
from \(\RMLE[\PRAA]\) and must be rejected by the base protocol imported next.
\end{proof}

This subsection continues the lemma pass.  The protocol boxes above remain

\paragraph{Native accumulator relation.}
\begin{proposition}[Accumulator reduction; cf. Blaze Propositions~5.2 and~5.3]
\label{prop:native-accumulator-reduction}
Let \(x,y\in\F^{\B^n}\), and let
\[
  A:\B^n\times\B^n\to\F
\]
be the accumulator matrix with \(A[b,a]=1\) exactly when
\(\Int(b)\ge \Int(a)\).  Let
\(\widehat A:\F^n\times\F^n\to\F\) be its multilinear extension.  For
\(r\in\F^n\), define the projected accumulator identity
\[
  \MLE(y)(r)
  =
  \sum_{X\in\B^n}\widehat A(r,X)x[X].
\]
If \(y=\Acc(x)\), this identity holds for every \(r\in\F^n\).  If
\(y\ne\Acc(x)\), then the identity fails for a random \(r\leftarrow\F^n\)
except with probability at most \(n/|\F|\).  Moreover, the vector
\((\widehat A(r,X))_{X\in\B^n}\) can be generated in \(O(N)\) time and
\(\widehat A(r,s)\) can be evaluated at a single field point in \(O(n)\) field
operations, where \(N=2^n\).
\end{proposition}

\begin{proof}
The tensor \(y-\Acc(x)\) is zero exactly when \(y=\Acc(x)\).  Its multilinear
extension at \(r\) is the difference between the two sides of the displayed
identity.  If the tensor is nonzero, this difference is a nonzero multilinear
polynomial in \(n\) variables, so Schwartz--Zippel bounds its zero probability
by \(n/|\F|\).  The efficient computation of \(\widehat A\) is the explicit
accumulator-kernel computation stated in Blaze Proposition~5.3 and used by
Figure~\ref{fig:native-accumulate-reduce}.
\end{proof}

\paragraph{Native permutation relation.}
\begin{proposition}[Permutation product-tree reduction; cf. Blaze Proposition~5.4]
\label{prop:native-permutation-reduction}
Let \(\pi:\B^n\to\B^n\) be a public permutation and let
\[
  x,y\in\F^{\B^n}.
\]
Use the push-forward convention fixed above:
\[
  y[\pi(b)]=x[b]\qquad(b\in\B^n).
\]
For verifier challenges \(\alpha,\beta\in\F\), define the intended tagged
leaf values
\[
  f[\mathsf{leaf}(b)]
  =
  \alpha-\bigl(x[b]+\beta\,\Idx(\pi(b))\bigr),
  \qquad
  g[\mathsf{leaf}(a)]
  =
  \alpha-\bigl(y[a]+\beta\,\Idx(a)\bigr).
\]
If \(y=M_\pi x\), then there exist product-tree tensors
\[
  f,g\in\F^{\B^{n+1}}
\]
whose roots agree, whose leaves are the two displayed tagged lists, and whose
tree residuals vanish on every Boolean internal coordinate.  If
\(y\ne M_\pi x\), then, except with probability at most \((N+1)/|\F|\) over
\((\alpha,\beta)\), every choice of \(f,g\) fails at least one of the root,
leaf, or tree-residual tests for all but a \(10n/|\F|\)-fraction of
\(r\in\F^n\).
\end{proposition}

\begin{proof}
When \(y[\pi(b)]=x[b]\), the two tagged leaf multisets are equal after the
change of variable \(a=\pi(b)\).  The prover can therefore build product trees
over the two equal multisets; the roots match and every parent-child residual
is zero.  When the permutation relation is false, the tagged products agree as
polynomials in \((\alpha,\beta)\) only with the failure probability stated
above, and the product-tree zero tests reduce the remaining global product
claims to the displayed root, leaf, and residual equations.  This is the
push-forward-coordinate copy of Blaze Proposition~5.4; with the pullback
convention one replaces \(\pi\) by \(\pi^{-1}\) in the leaf tag.
\end{proof}

\paragraph{Native \(\RMLE[\PRAA]\) MLIOP.}
\begin{lemma}[Native packed-RAA RMLE MLIOP; cf. Blaze Lemma~5.1 and Proposition~5.5]
\label{lem:native-praa-mliop}
Let
\[
  y\in\F^{\B^n},\qquad z\in\F^k,\qquad v\in\F
\]
be a base folded \(\RMLE[\PRAA]\) claim.  In the
\(\mathcal F_{\mathrm{MLIOP}}\)-hybrid model, the fixed protocol
Figure~\ref{fig:native-blaze-fmliop-hybrid}, restricted to Lines O8 onward
after the folded word \(R_\star\) has been formed, is a native MLIOP for the
exact relation
\[
  y=\PRAA(m)
  \qquad\text{and}\qquad
  \MLE(m)(z)=v.
\]
Completeness is perfect.  Soundness is the native algebraic soundness of Blaze
Proposition~5.5: if the represented MLIOP tensors do not satisfy the displayed
relation, the verifier rejects except with probability at most
\[
  \frac{N+13n+7}{|\F|},
  \qquad N=2^n.
\]
This is an exact native-MLIOP statement about represented tensors and requested
MLE evaluations.  It is not yet a proximity statement about a literal backend
encoded string.
\end{lemma}

\begin{proof}
The prover's represented input tensor is \(u_0\in\F^{\B^k}\).  The verifier
gets \(u_1\) as the derived repetition view \(F_{\mathrm{rep}}u_0\), receives
handles for \(u_2,u_3,u_4\), and treats the input folded word as
\[
  u_5=y.
\]
The direct endpoint request
\[
  (\widehat O_{u_0},z,v)
\]
enforces \(\MLE(u_0)(z)=v\) in the hybrid model.

The remaining checks force the RAA stage equations.  Proposition
\ref{prop:native-accumulator-reduction} is applied to
\[
  u_3=\Acc(u_2)
  \qquad\text{and}\qquad
  u_5=\Acc(u_4),
\]
using the two calls to \(\AccReduce\).  Proposition
\ref{prop:native-permutation-reduction} is applied to
\[
  u_2=M_{\pi_1}u_1
  \qquad\text{and}\qquad
  u_4=M_{\pi_2}u_3,
\]
using the two calls to \(\PermuteCommit\) and \(\PermuteReduce\).  The six
Boolean-sum claims returned by these four reductions are batched by
\(\RAASixSumcheck\).  If any one of those Boolean-sum identities is false, the
scalar-power batch hides it only with the usual low-degree error, and the
sumcheck endpoint values are then checked through \(\mathcal F_{\mathrm{MLIOP}}\).

Therefore, except for the native soundness error bounded in Blaze
Proposition~5.5, acceptance implies
\[
  u_1=F_{\mathrm{rep}}u_0,\quad
  u_2=M_{\pi_1}u_1,\quad
  u_3=\Acc(u_2),\quad
  u_4=M_{\pi_2}u_3,\quad
  u_5=\Acc(u_4).
\]
Since \(u_5=y\), this is exactly \(y=\PRAA(u_0)\), and the direct endpoint
request gives \(\MLE(u_0)(z)=v\).
\end{proof}

\paragraph{Compiler from native MLIOP to backend RMLE.}
\begin{lemma}[MLIOP-to-RMLE IOPP compiler in handle form; cf. Blaze Lemma~4.2 and Proposition~4.4]
\label{lem:mliop-to-rmle-compiler-handle}
Let \(\Pi\) be a native MLIOP whose verifier makes MLE evaluation requests
\[
  \MLE(h)(r)=w
\]
against finitely many native oracle tensors \(h\in\F^{\B^d}\).  Let
\[
  C_{\mathrm{backend}}:\F^{\B^d}\to\F^{D}
\]
be the systematic backend code used to authenticate those native tensors, and
assume we have a backend \(\RMLE[C_{\mathrm{backend}}]\)-IOPP.  Replacing each
native oracle handle by a literal backend string
\[
  y_h\in\F^D
\]
and each native evaluation request by the backend claim
\[
  y_h\approx C_{\mathrm{backend}}(h)
  \qquad\text{and}\qquad
  \MLE(h)(r)=w
\]
gives an IOPP for the same relation as \(\Pi\), with soundness equal to the
native MLIOP soundness plus the backend RMLE and batching errors.
\end{lemma}

\begin{proof}
Completeness follows by encoding every honest native tensor \(h\) as
\(C_{\mathrm{backend}}(h)\) and answering the same MLE values as the native
MLIOP.  For soundness, fix a deterministic compiled prover and expand every
authentication handle into its literal backend string \(y_h\).  There are two
cases.

First, if some \(y_h\) is far from the backend code, the corresponding backend
\(\RMLE[C_{\mathrm{backend}}]\)-IOPP rejects except with its proximity
soundness error.  Second, if every \(y_h\) is close to the backend code, an
unbounded extractor decodes each nearby codeword to an effective tensor
\[
  h^\dagger\in\F^{\B^d}.
\]
The compiled verifier's accepted backend openings then imply that every native
request \(\MLE(h)(r)=w\) is true for the effective tensor
\(h^\dagger\), except with backend and batching error.  The extracted effective
tensors therefore define a native MLIOP transcript for \(\Pi\).  If the
underlying relation is false for those tensors, native MLIOP soundness rejects.
This is the literal/effective split in Blaze Proposition~4.4.
\end{proof}

\begin{proposition}[Batched backend RMLE requests; cf. Blaze Remark~4.3 and Proposition~4.5]
\label{prop:batched-backend-rmle}
The per-oracle backend checks in Lemma~\ref{lem:mliop-to-rmle-compiler-handle}
can be batched: the verifier reduces all native requests
\[
  \MLE(h_j)(r_j)=w_j
\]
to one virtual multilinear evaluation claim, and one query to the virtual
backend word is emulated by the corresponding queries to the literal backend
strings \(y_{h_j}\).  The batching changes the proximity parameter and adds the
batching soundness term stated in Blaze Proposition~4.5, but it does not change
the semantic split: far backend strings are rejected, and close backend strings
decode to effective native tensors.
\end{proposition}

\begin{proof}
The batching protocol is linear in the claimed evaluations and in the virtual
oracle construction.  Thus an honest batch is complete.  If a batch accepts
while some constituent evaluation is false for the effective tensors, the
batching polynomial in the verifier challenge has a nonzero error coefficient
and vanishes only with the standard batching probability.  The resulting single
virtual claim is then checked by the same backend
\(\RMLE[C_{\mathrm{backend}}]\)-IOPP as in
Lemma~\ref{lem:mliop-to-rmle-compiler-handle}.
\end{proof}

\paragraph{Composed theorem.}
\begin{theorem}[Interleaved packed-RAA RMLE IOPP in handle form; cf. Blaze Theorem~7.1]
\label{thm:interleaved-praa-rmle-iopp-handle}
Instantiate Lemma~\ref{lem:blaze-interleaving-handle} with \(C=\PRAA\).  Then
instantiate the base \(\RMLE[\PRAA]\) protocol by
Lemma~\ref{lem:native-praa-mliop} and compile its native evaluation requests by
Lemma~\ref{lem:mliop-to-rmle-compiler-handle}, using the batching of
Proposition~\ref{prop:batched-backend-rmle}.  The result is an
\(\RMLE[\PRAA^t]\)-IOPP for the fixed handle-level protocol above:
the literal matrix behind \(R_c\) is checked for proximity to an interleaved
packed-RAA codeword \(\PRAA^t(m)\), and the effective message satisfies
\[
  \MLE(m)(z_{\mathrm{slice}},z_{\mathrm{in}})=v.
\]
\end{theorem}

\begin{proof}
Lemma~\ref{lem:blaze-interleaving-handle} reduces a bad top-level interleaved
claim to a bad folded base claim, except for the row-fold error from
Lemma~\ref{lem:row-fold-proximity-gap}.  Lemma~\ref{lem:native-praa-mliop}
proves the folded base claim in the native MLIOP model by enforcing the RAA
stage equations and the terminal value \(\MLE(m_\star)(z_{\mathrm{in}})=v_\star\).
Lemma~\ref{lem:mliop-to-rmle-compiler-handle} and
Proposition~\ref{prop:batched-backend-rmle} replace the ideal native MLE
handles by backend encoded strings and backend \(\RMLE[C_{\mathrm{backend}}]\)
checks.  Adding the stated soundness errors gives the theorem.  Appendix~A of
Blaze supplies the round-by-round soundness form needed when this IOPP is later
compiled with Merkle commitments and Fiat--Shamir.
\end{proof}
