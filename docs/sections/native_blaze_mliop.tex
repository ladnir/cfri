\section{The Native RAA Relation Compiler}

We now restart Blaze at the model where the Blaze paper first lives: the native
multilinear IOP layer.  This is deliberately before Merkle trees, BaseFold,
systematic encodings, or concrete coordinate-opening implementations.  At this layer the prover
can commit multilinear-oracle tensors \(h\in\F^{\B^d}\), receive hatted MLE
oracle handles \(\widehat O_h:\F^d\to\F\), and the verifier can ask for
field-point MLE evaluations of those hatted handles.  When a tensor is meant to
stand for a verifier-originated coordinate handle, the compiled/holographic
model uses the separate proximity bridge
\(\mathcal F_{\mathrm{HMLPCS}}^\delta\) from
Figure~\ref{fig:func-hmlpcs-oracle}.

The goal of the native layer is not to prove proximity to a codeword.  Its goal
is to compile one algebraic statement into a small set of MLE evaluation
requests and Boolean-sum claims.  The later authentication layer will then make
those requests cryptographic.

\[
  \begin{aligned}
  \text{RAA relation}
  &\Longrightarrow
  (\EvalReqs,\SumClaims) \\
  &\Longrightarrow
  \text{batched sumcheck}
  \Longrightarrow
  \text{more }\EvalReqs .
  \end{aligned}
\]

\[
  y\in\F^{\B^n}.

The prover witness is a message tensor
\[
  m\in\F^{\B^k}.
\]
The claim is that
\[
  y=\PRAA(m)
  \qquad\text{and}\qquad
  \MLE(m)(z)=v.
\]

The RAA map is public and has the stage form
\[
  \PRAA(m)
  =
  \Acc\circ M_{\pi_2}\circ\Acc\circ M_{\pi_1}\circ F_{\mathrm{rep}}(m),
\]
where \(F_{\mathrm{rep}}:\F^{\B^k}\to\F^{\B^n}\) repeats message entries,
\(M_{\pi_i}\) is the permutation operator for a public permutation
\(\pi_i:\B^n\to\B^n\), and \(\Acc\) is the prefix-sum map over
\(\B^n\).  We use the push-forward convention
\[
  (M_\pi x)[\pi(b)]=x[b]
  \qquad(b\in\B^n).
\]
Equivalently, \((M_\pi x)[a]=x[\pi^{-1}(a)]\).  This convention is chosen so
that the tagged-product permutation check below compares the pairs
\((x[b],\pi(b))\) with \((y[a],a)\).  The Blaze text states the permutation
test with the same tagged leaves but writes the relation in pullback form
\(y[b]=x[\pi(b)]\)~[Blaze24].  In this explainer we fix the convention that
makes the product argument literal; if one instead uses the pullback
convention, the same checker should be read with \(\pi^{-1}\) in place of
\(\pi\).

Thus an honest prover's stage tensors satisfy
\[
  \begin{aligned}
  u_0&=m,&
  u_1&=F_{\mathrm{rep}}(u_0),&
  u_2&=M_{\pi_1}u_1,&
  u_3&=\Acc(u_2),\\
  u_4&=M_{\pi_2}u_3,&
  u_5&=\Acc(u_4)=y.
  \end{aligned}
\]

The prover provides native MLPCS tensors for
\[
  u_0=m\in\F^{\B^k},
  \qquad
  u_2,u_3,u_4\in\F^{\B^n},
  \qquad
  f_1,g_1,f_2,g_2\in\F^{\B^n}.
\]
The native MLPCS functionality turns those prover-committed tensors into
hatted MLE handles before the verifier asks field-point evaluation questions.
The prover does not send \(u_1\) or \(u_5\) as separate native messages.
Queries to \(u_1\) are emulated from \(u_0\) using the repetition layout:
we write
\[
  \widehat O_{u_1}:=\RepView(\widehat O_{u_0}),
  \qquad
  \widehat O_{u_1}(r):=\widehat O_{u_0}(\mathsf{msg}(r)).
\]
This is a derived view, not a fresh call to
\(\mathcal F_{\mathrm{MLPCS}}.\mathsf{Commit}\).  The final stage \(u_5\) is
the input codeword handle supplied to the checker.

\subsection{Request And Claim Sets}

A native evaluation request is a tuple
\[
  (J,r,v)\in\EvalReq,
\]
where \(J\) is a handle that can later authenticate MLE values, \(r\in\F^d\)
has the handle's dimension, and \(v\in\F\).  In the native MLPCS section \(J\)
is a hatted MLE handle \(\widehat O:\F^d\to\F\).  In the compiled Blaze
section the same logical request is realized by a backend encoded oracle string
and an \(\RMLE[C_{\mathrm{backend}}]\) proximity check.  Thus the request slot
remains an MLE-evaluation handle in this API; the expanded semantic view names
the literal backend string that authenticates it.  The request means that the
later verifier check needs
\[
  J(r)=v.
\]
For example, \((\widehat O_{u_3},r,s)\) means that the value \(s\) must be the
MLE evaluation of the tensor \(u_3\) at \(r\).

A Boolean-sum claim is stored in \(\SumClaims\).  Its logical content is
\[
  (s,G)\in\SumClaims
  \quad\Longleftrightarrow\quad
  \sum_{X\in\B^d}G(X)=s.
\]
In protocol boxes below, the reducers do not return an opaque polynomial name.
They return a small record that says which public residual form is being used,
which MLE handle it touches, which projection point was sampled, and what the
Boolean-sum target is.  The batched sumcheck then expands those records
explicitly.

The native layer uses two kinds of outputs:
\[
  \EvalReqs,\qquad \SumClaims.
\]
\(\EvalReqs\) are MLE claims to authenticate later.  \(\SumClaims\) are
Boolean sums to feed into sumcheck.  Some apparent scalar equalities, such as
the permutation root equality, are encoded by reusing or deriving values inside
\(\EvalReqs\) instead of carrying a separate equality set.

\subsection{How Native Tensor Checks Compose}

The same pattern appears in every RAA stage.  Start with a large relation
between named tensors.  Rewrite that relation as a residual tensor
\[
  R\in\F^{\B^s}
\]
that should be zero at every Boolean coordinate:
\[
  R[a]=0
  \qquad(a\in\B^s).
\]
Each residual value is a public low-degree expression in MLE evaluations of the
named tensors.  Abstractly,
\[
  R[a]
  =
  \Phi_a\Bigl(
    \MLE(t_{j_1})(\psi_1(a)),
    \ldots,
    \MLE(t_{j_q})(\psi_q(a))
  \Bigr),
\]
where \(t_{j_1},\ldots,t_{j_q}\) are the participating tensors, the address
maps \(\psi_t:\B^s\to\F^{d_{j_t}}\) and the expression \(\Phi_a:\F^q\to\F\)
are public.  The subscript \(a\) only means that the coefficients of the
expression may depend on the residual coordinate.
To use sumcheck, the Boolean-coordinate formula must come with a low-degree
field extension: the maps \(\psi_t\) and the expression \(\Phi_a\) are extended
to field points in the way specified by the concrete check.  This is not an
extra commitment.  It is part of the algebraic description of the residual
identity being checked.

The verifier does not read all of \(R\).  It samples a field point
\[
  r\in\F^s
\]
and projects the zero claim to one scalar equation:
\[
  \sum_{a\in\B^s}\chi_a(r)R[a]=0.
\]
If \(R\) is not the zero tensor, this random projection fails with high
probability over \(r\).  When the projected sum is still too large to compute
directly, the prover and verifier run sumcheck on the projected identity.
Sumcheck does not authenticate any tensor value by itself; it only reduces the
identity to endpoint claims of the form
\[
  \MLE(H_j)(r_j)=v_j.
\]
Those endpoint claims become \(\EvalReqs\).  The native layer records them; the
later authentication layer checks them.

A small example is the pointwise product relation
\[
  C[a]=A[a]B[a]\qquad(a\in\B^s).
\]
The residual is
\[
  R[a]=C[a]-A[a]B[a].
\]
The projected zero claim is
\[
  \sum_{a\in\B^s}\chi_a(r)\bigl(C[a]-A[a]B[a]\bigr)=0.
\]
If the prover cheats at one coordinate \(a_0\), the bad contribution is weighted
by \(\chi_{a_0}(r)\).  The point is not that the verifier checks the coordinate
\(a_0\) directly.  The point is that a random linear projection turns a large
coordinate-wise relation into one low-degree scalar identity, and sumcheck then
turns that identity into a few MLE endpoint requests.

\subsection{Accumulator Reducer}

The accumulator relation has the form
\[
  y=\Acc(x),
  \qquad
  x,y\in\F^{\B^n}.
\]
Let
\[
  \widehat A:\F^n\times\F^n\to\F
\]
be the multilinear extension of the accumulator matrix, where the Boolean
matrix has entry \(A[b,a]=1\) exactly when \(\Int(b)\ge \Int(a)\) in the
natural binary order.  In ordinary coordinate language,
\[
  y[b]=\sum_{a\le b}x[a].
\]
This matrix is conceptually \(N\times N\), but the verifier never materializes
it.  For fixed \(r\in\F^n\), the weights
\((\widehat A(r,X))_{X\in\B^n}\) can be generated in one linear pass over the
Boolean domain, and a single field-point value
\(\widehat A(r,s)\) can be computed by the usual recursive comparison formula
for the predicate \(\Int(b)\ge\Int(a)\).  Thus the reducer uses the
accumulator matrix as a compact algebraic kernel, not as a dense table.

The verifier cannot check this equation for every \(b\).  Instead it samples a
field point \(r\in\F^n\) and asks for the same linear relation at that MLE
point.  For an honest accumulator,
\[
  \MLE(y)(r)
  =
  \sum_{X\in\B^n}\widehat A(r,X)\,x[X]
  \qquad
  \text{for every }r\in\F^n.
\]
The value \(\MLE(y)(r)\) is not trusted for free.  The prover sends it as a
scalar \(s\), the reducer records \((\widehat O_y,r,s)\) as an evaluation request,
and the Boolean-sum claim says that the accumulator input \(x\) must sum to the
same scalar \(s\).

\noindent Public parameters: \(n\), \(\widehat A:\F^n\times\F^n\to\F\).

\smallskip
\noindent\(\underline{\AccReduce(\verifier:(\widehat O_x:\F^n\to\F,\ \widehat O_y:\F^n\to\F,\ r\in\F^n),\ \prover:(x,y\in\F^{\B^n}))\to(\EvalReqs,B_{\mathrm{acc}})}\)
\begin{enumerate}[leftmargin=0.24in,label=\textbf{A\arabic*.},itemsep=0.06em,topsep=0.06em,parsep=0pt]
  \item \(\prover\): \(s_y\gets \MLE(y)(r)\).
  \item \(\prover\to\verifier\): \(s_y\in\F\).
  \item \(\verifier\): \(\EvalReqs\gets\{(\widehat O_y,r,s_y)\}\).
  \item \(\verifier\): \(B_{\mathrm{acc}}\gets(\mathsf{acc},s_y,\widehat O_x,r)\).
  \item \(\verifier\): return \((\EvalReqs,B_{\mathrm{acc}})\).
\end{enumerate}
\end{protocolbox}

The record \(B_{\mathrm{acc}}=(\mathsf{acc},s_y,\widehat O_x,r)\) means
\[
  \sum_{X\in\B^n}\widehat A(r,X)\MLE(x)(X)=s_y,
\]
where \(\widehat O_x\) is the handle that will later authenticate endpoint
values of \(\MLE(x)\).  The scalar \(s_y\) is local to the reducer.  It is not a
separate output because it is already stored in the evaluation request and in
the Boolean-sum target.
In the RAA relation, this reducer is used twice:
\[
  (u_2,u_3)
  \qquad\text{and}\qquad
  (u_4,y).
\]

\subsection{Permutation Reducer}

The permutation check is the one place where the Blaze paper's most direct
product-tree presentation would introduce one extra Boolean variable.  We use a
split product-tree representation instead.  This is the same grand-product
idea as Blaze Proposition~5.4, but the leaf layer is virtual and the committed
helper tensors are all \(n\)-variate.  This is an intentional
presentation-level divergence from Blaze's literal helper-oracle shape, where
the product-tree tensors are \((n+1)\)-variate.  The equivalence is that the
omitted leaf layer is not free: every leaf value is derived from the existing
source handle and the public tag polynomial, and the split residual below
checks the same parent-equals-product relation on the internal tree.

Fix a permutation map \(\pi:\B^n\to\B^n\), its multilinear tag
\(\widehat\pi:\F^n\to\F\), and the public address tag
\(\Idx:\F^n\to\F\).  For a claimed relation
\[
  y[\pi(b)]=x[b]
  \qquad(b\in\B^n),
\]
the usual tagged products are
\[
  \prod_{b\in\B^n}
    \left(\alpha-\bigl(x[b]+\beta\,\widehat\pi(b)\bigr)\right)
  \quad\text{and}\quad
  \prod_{a\in\B^n}
    \left(\alpha-\bigl(y[a]+\beta\,\Idx(a)\bigr)\right).
\]
If \(y[\pi(b)]=x[b]\), then the two products are term-by-term equal after the
change of variable \(a=\pi(b)\).  If the tagged multisets differ, the two
products agree only with small probability over \(\alpha,\beta\).

For source tensor \(H\in\F^{\B^n}\) and public tag polynomial
\(\tau:\F^n\to\F\), define the virtual leaf tensor
\[
  L_{H,\tau}(b)
  =
  \alpha-\bigl(H(b)+\beta\,\tau(b)\bigr),
  \qquad b\in\B^n.
\]
The prover does not commit \(L_{H,\tau}\).  Its MLE evaluations are derived
from the existing source handle:
\[
  \MLE(L_{H,\tau})(r)
  =
  \alpha-\bigl(\MLE(H)(r)+\beta\,\tau(r)\bigr).
\]
The prover commits only an internal product tensor
\[
  P\in\F^{\B^n}.
\]
Let
\[
  \mathsf{root}_P=(1^{n-1},0)\in\B^n,
  \qquad
  \mathsf{pad}_P=1^n\in\B^n.
\]
The honest internal layer for leaves \(L\) is defined by
\[
  P[0\Vert a]=L[a\Vert0]L[a\Vert1]
  \qquad(a\in\B^{n-1}),
\]
and, for \(t\in\{1,\ldots,n-1\}\) and
\(a\in\B^{n-t-1}\),
\[
  P[1^t\Vert0\Vert a]
  =
  P[1^{t-1}\Vert0\Vert a\Vert0]
  P[1^{t-1}\Vert0\Vert a\Vert1].
\]
The padding coordinate is set to
\[
  P[\mathsf{pad}_P]=0.
\]
The root value is \(P[\mathsf{root}_P]\).

The generic letter \(P\) is useful while defining the split-tree residual.  In
the protocol boxes below we drop the \(P\)-prefix for brevity: the symbols
\(f,g\) and later \(f_1,g_1,f_2,g_2\) denote these committed internal product
tensors, not full product trees with an explicit leaf layer.  The corresponding
leaf tensors remain virtual.

For a field point \(X=(s,a)\in\F\times\F^{n-1}\), define
\[
\begin{aligned}
  \mathsf{SplitTreeRes}(P,H,\tau,\alpha,\beta;X)
  &=
  \MLE(P)(X)\\
  &\quad-
  \Bigl((1-s)\MLE(L_{H,\tau})(a,0)+s\,\MLE(P)(a,0)\Bigr)\\
  &\qquad\cdot
  \Bigl((1-s)\MLE(L_{H,\tau})(a,1)+s\,\MLE(P)(a,1)\Bigr).
\end{aligned}
\]
On Boolean \(X=(s,a)\), this is the parent-minus-children residual for the
virtual full tree whose leaf layer is \(L_{H,\tau}\) and whose internal layer is
\(P\).  The sumcheck domain remains \(\B^n\), and the only committed helper
object is \(P\in\F^{\B^n}\).

The records
\[
  B=(\mathsf{split},\widehat O_P,\widehat O_H,\tau,\alpha,\beta,r)
\]
mean
\[
  \sum_{X\in\B^n}\chi_r(X)
  \mathsf{SplitTreeRes}(P,H,\tau,\alpha,\beta;X)=0.
\]
The committed part of the product tree is \(P\).  The leaf part is the virtual
tensor \(L_{H,\tau}\), whose evaluations are derived from the source handle
\(\widehat O_H\) and public tag polynomial \(\tau\).

The RAA relation uses this reducer twice:
\[
  (u_1,u_2,\pi_1)
  \qquad\text{and}\qquad
  (u_3,u_4,\pi_2).
\]
Therefore it introduces four internal product tensors
\[
  f_1,g_1,f_2,g_2\in\F^{\B^n}.
\]
Each helper has \(N\) entries.  The leaf layers are virtual and are derived
from \(u_1,u_2,u_3,u_4\) when their MLE values are needed.

For each permutation edge, read the checks as one correlated argument: the
virtual leaves load the claimed tagged products from \(x\) and \(y\), the
split residual claims force the internal tensors \(f\) and \(g\) to be
product trees over those virtual leaves, and the shared root value compares the
two products.  No single one of these checks proves a permutation by itself.

The top-level Blaze box below performs the native RAA orchestration directly.
It creates the stage handles, calls the two reducers, gathers their returned
requests, and runs one batched sumcheck over the six Boolean-sum claims in a
fixed order.  The \(u_1\) handle is virtual, but not opaque: its evaluation
rule is written where it is created.

\subsection{The Batched Six-Sumcheck}

The two accumulator reducers contribute two Boolean-sum claims \(B_{u2}\) and
\(B_{u4}\).  The two permutation reducers contribute four product-tree
Boolean-sum claims \(B_{f1},B_{g1},B_{f2},B_{g2}\).  Blaze batches these six
named claims into
one sumcheck by sampling one scalar
\[
  \lambda\leftarrow\F
\]
and using the powers \(1,\lambda,\lambda^2,\ldots,\lambda^5\) as batching
weights.
This is only native batching of Boolean-sum claims.  It is not the later
compiler-level batching of arbitrary MLE evaluation requests.  If any one of
the six Boolean-sum identities is false, then the vector of six errors defines
a nonzero polynomial in \(\lambda\) of degree at most \(5\).  The batching step
can hide that error with probability at most \(5/|\F|\).  Conditioned on the
batched claim being false, ordinary sumcheck soundness applies.  This is the
same scalar-power batching pattern used in Blaze's Remark~2.3.

Only the Boolean-sum identities are batched here.  The permutation root
equalities have already been encoded as evaluation requests.  The split-tree
leaf layers are virtual, so their endpoint values are derived from existing
source handles when the sumcheck terminal point is known.  The endpoint values
produced by this sumcheck are still not trusted; they are appended to
\(\EvalReqs\) and discharged later by the MLPCS-to-IOPP compiler as backend
RMLE evaluation claims.
This is exactly the endpoint discipline from
Figure~\ref{fig:subroutine-sumcheck-terminal}: \(\SumCheck_n\) produces one
terminal scalar \(T_{\mathrm{sc}}\), and the surrounding RAA flow expands that
scalar into MLE requests against the existing stage handles and the internal
product handles \(\widehat O_{f_1}\), \(\widehat O_{g_1}\),
\(\widehat O_{f_2}\), and \(\widehat O_{g_2}\).

For a split-tree record
\[
  B=(\mathsf{split},\widehat O_P,\widehat O_H,\tau,\alpha,\beta,r_B)
\]
and terminal point \(q=(s,a)\in\F\times\F^{n-1}\), let
\(\mathsf{SplitEndpoint}(B,q)\) denote the following local endpoint expansion.  The
prover sends
\[
  w_P=\MLE(P)(q),\quad
  w_{P0}=\MLE(P)(a,0),\quad
  w_{P1}=\MLE(P)(a,1),
\]
and
\[
  w_{H0}=\MLE(H)(a,0),\qquad
  w_{H1}=\MLE(H)(a,1).
\]
The verifier computes
\[
  w_{L0}=\alpha-(w_{H0}+\beta\,\tau(a,0)),
  \qquad
  w_{L1}=\alpha-(w_{H1}+\beta\,\tau(a,1)),
\]
and returns the residual value
\[
  w_P-\bigl((1-s)w_{L0}+s\,w_{P0}\bigr)
      \bigl((1-s)w_{L1}+s\,w_{P1}\bigr)
\]
together with the five evaluation requests for
\(\widehat O_P\) at \(q,(a,0),(a,1)\) and \(\widehat O_H\) at
\((a,0),(a,1)\).

        \(B_{g2}=(\mathsf{split},\widehat O_{g_2},
        \widehat O_{u_4},\Idx,\alpha,\beta,r_{g2})\).
  \item \(\verifier\): sample \(\lambda\leftarrow\F\), then send
        \(\lambda\) to \(\prover\).
  \item \(\verifier\): \(S_\lambda\gets
        s_{u2}+\lambda s_{u4}\).
  \item \(\prover\): \(G_\lambda(X)\gets
        \widehat A(r_{u2},X)\MLE(u_2)(X)
        +\lambda\,\widehat A(r_{u4},X)\MLE(u_4)(X)
        +\lambda^2\chi_{r_{f1}}(X)
        \mathsf{SplitTreeRes}(f_1,u_1,\widehat\pi_1,\alpha,\beta;X)
        +\lambda^3\chi_{r_{g1}}(X)
        \mathsf{SplitTreeRes}(g_1,u_2,\Idx,\alpha,\beta;X)
        +\lambda^4\chi_{r_{f2}}(X)
        \mathsf{SplitTreeRes}(f_2,u_3,\widehat\pi_2,\alpha,\beta;X)
        +\lambda^5\chi_{r_{g2}}(X)
        \mathsf{SplitTreeRes}(g_2,u_4,\Idx,\alpha,\beta;X)\).
  \item \(\prover,\verifier\):
        \((a_{\mathrm{round}},r_{\mathrm{sc}},T_{\mathrm{sc}})
        \gets\SumCheck_n(\verifier:S_\lambda,\prover:G_\lambda)\).
  \item \(\verifier\): if \(a_{\mathrm{round}}=0\), return \((0,\emptyset)\).
  \item \(\prover\): let \(w_{u2}\gets\MLE(u_2)(r_{\mathrm{sc}})\) and
        \(w_{u4}\gets\MLE(u_4)(r_{\mathrm{sc}})\).
  \item \(\prover,\verifier\): run
        \((R_{f1},E_{f1})\gets\mathsf{SplitEndpoint}(B_{f1},r_{\mathrm{sc}})\),
        \((R_{g1},E_{g1})\gets\mathsf{SplitEndpoint}(B_{g1},r_{\mathrm{sc}})\),
        \((R_{f2},E_{f2})\gets\mathsf{SplitEndpoint}(B_{f2},r_{\mathrm{sc}})\), and
        \((R_{g2},E_{g2})\gets\mathsf{SplitEndpoint}(B_{g2},r_{\mathrm{sc}})\).
  \item \(\prover\to\verifier\): send \(w_{u2},w_{u4}\in\F\).  The
        \(\mathsf{SplitEndpoint}\) calls send their own endpoint values.
  \item \(\verifier\): \(T_{\mathrm{endpoint}}\gets
        \widehat A(r_{u2},r_{\mathrm{sc}})
        w_{u2}
        +\lambda\,\widehat A(r_{u4},r_{\mathrm{sc}})
        w_{u4}
        +\lambda^2\chi_{r_{f1}}(r_{\mathrm{sc}})R_{f1}
        +\lambda^3\chi_{r_{g1}}(r_{\mathrm{sc}})R_{g1}
        +\lambda^4\chi_{r_{f2}}(r_{\mathrm{sc}})R_{f2}
        +\lambda^5\chi_{r_{g2}}(r_{\mathrm{sc}})R_{g2}\).
  \item \(\verifier\): if \(T_{\mathrm{sc}}\ne T_{\mathrm{endpoint}}\), return \((0,\emptyset)\).
  \item \(\verifier\): \(\EvalReqs_{\mathrm{sc}}\gets
        \{(\widehat O_{u_2},r_{\mathrm{sc}},w_{u2}),
        (\widehat O_{u_4},r_{\mathrm{sc}},w_{u4})\}
        \cup E_{f1}\cup E_{g1}\cup E_{f2}\cup E_{g2}\).
  \item \(\verifier\): return \((1,\EvalReqs_{\mathrm{sc}})\).
\end{enumerate}
\end{protocolbox}

The terminal request set is explicit in the final steps: those are the values
that the later authentication layer must bind to committed or derived MLE
handles.  The first two requests are ordinary MLE endpoint claims for the
accumulator inputs.  Each split product-tree residual contributes five endpoint
claims: three evaluations of the committed internal product handle
\(\widehat O_P\) and two evaluations of the existing source handle
\(\widehat O_H\) used to derive the virtual leaves.  In the inlined Blaze
protocol below, these handles are objects such as \(\widehat O_{f_1}\),
\(\widehat O_{g_1}\), and \(\widehat O_{u_1}\).
The public factors \(\widehat A(r_{u2},r_{\mathrm{sc}})\),
\(\widehat A(r_{u4},r_{\mathrm{sc}})\), \(\chi_{r_{f1}}(r_{\mathrm{sc}})\),
\(\chi_{r_{g1}}(r_{\mathrm{sc}})\), \(\chi_{r_{f2}}(r_{\mathrm{sc}})\),
\(\chi_{r_{g2}}(r_{\mathrm{sc}})\), and the powers of \(\lambda\) are not oracle
requests.

\subsection{Batching Native Evaluation Requests}

The native RAA checks produce many MLE evaluation requests.  A typical request
is
\[
  (\widehat O_{h_j},r_j,w_j),
  \qquad\text{meaning}\qquad
  \MLE(h_j)(r_j)=w_j .
\]
This subsection explains the ordinary batch for those requests, following
Blaze Theorem~2.4, Remark~4.3, and Proposition~4.5.  In the full Blaze
protocol below, requests to \(\widehat O_{u_5}\) are not part of this ordinary
batch; the main protocol discharges them directly through
\(\mathcal F_{\mathrm{HMLPCS}}^\delta.\mathsf{Eval}\).  This is an intentional
grouping divergence from the most compressed reading of Blaze Remark~4.3, which
batches evaluation requests abstractly across polynomials.  We split the folded
endpoint because its MLE handle must stay proximity-bound to the already-fixed
coordinate handle \(R_\star\); the ordinary prover-originated tensors do not
need that frontend proximity parameter.  Everything in this subsection is only
about merging the ordinary native evaluation requests.

The destination is simple.  Starting from an ordered ordinary list
\[
  E=\bigl((\widehat O_{h_j},r_j,w_j)\bigr)_{j=0}^{q-1},
\]
the batching protocol derives one virtual MLE handle
\[
  \widehat O_{\mathrm{batch}}
  =
  \mathsf{RowFold.Commit}
  \bigl((\widehat O_{h_j},\lambda_j)_{j=0}^{q-1}\bigr)
\]
and one final evaluation claim
\[
  \widehat O_{\mathrm{batch}}(\eta)
  =
  w.
\]
The coefficients \(\lambda_j\), the point \(\eta\), and the value \(w\) are all
determined by the batching transcript.  The prover does not commit a fresh
tensor for \(\widehat O_{\mathrm{batch}}\).

All ordinary requests are first represented as \(n\)-variate requests.  With the
split product-tree representation, the ordinary tensors
\(u_2,u_3,u_4,f_1,g_1,f_2,g_2\) already live in \(\F^{\B^n}\), while
\(u_0\in\F^{\B^k}\).  For a smaller tensor \(h\in\F^{\B^d}\), \(d\le n\), we
use the padded tensor \(\mathsf{pad}(h)\in\F^{\B^n}\) that agrees with \(h\) on
the slice \(0^{n-d}\times\B^d\) and is zero elsewhere.  Then
\(\MLE(h)(r)=w\) is represented as
\(\MLE(\mathsf{pad}(h))(0^{n-d},r)=w\).  From here on, every ordinary request is
assumed to have this uniform form with \(h_j\in\F^{\B^n}\) and
\(r_j\in\F^n\).

Choose \(s\) with \(2^s\ge q\), and write
\(\bits_s(j)\in\B^s\) for the list address of request \(j\).  For
\(r\in\F^n\), define the equality function
\[
  \mathrm{Eq}_r(Y)
  =
  \prod_{i=0}^{n-1}\bigl((1-Y_i)(1-r_i)+Y_i r_i\bigr),
  \qquad Y\in\F^n.
\]
On a Boolean point \(b\in\B^n\), this is exactly the interpolation weight
\(\chi_b(r)\), so
\[
  \sum_{b\in\B^n} h_j(b)\,\mathrm{Eq}_{r_j}(b)
  =
  \MLE(h_j)(r_j).
\]

The CBBZ/Blaze batch begins by sampling one list-address point
\[
  t\leftarrow\F^s.
\]
This point gives the verifier-derived weights \(\chi_{\bits_s(j)}(t)\) for the
claimed values \(w_j\).  Define
\[
  S_t
  =
  \sum_{j=0}^{q-1}\chi_{\bits_s(j)}(t)\,w_j .
\]
Now consider two functions on \(\F^s\times\F^n\):
\[
  G_t(X,Y)
  =
  \sum_{j=0}^{q-1}
    \chi_{\bits_s(j)}(X)\chi_{\bits_s(j)}(t)\MLE(h_j)(Y),
\]
and
\[
  \mathsf{Eq}_E(X,Y)
  =
  \sum_{j=0}^{q-1}
    \chi_{\bits_s(j)}(X)\mathrm{Eq}_{r_j}(Y).
\]
The first function contains the oracle data, so it is not directly computable
by the verifier.  The second is public: it is built only from the request
points \(r_j\) and the list addresses \(\bits_s(j)\).  On the Boolean cube, the
product
\(G_t(X,Y)\mathsf{Eq}_E(X,Y)\) selects one request at a time.  Therefore the
original claims imply the Boolean-sum identity
\[
  \sum_{(X,Y)\in\B^s\times\B^n}
    G_t(X,Y)\,\mathsf{Eq}_E(X,Y)
  =
  S_t .
\]
This is the exact HyperPlonk/CBBZ batching shape imported by Blaze.

Run the reusable sumcheck from Figure~\ref{fig:subroutine-sumcheck-terminal} on
the prover's degree-two product
\[
  P(X,Y)=G_t(X,Y)\mathsf{Eq}_E(X,Y).
\]
The prover supplies the sumcheck messages for this product.  The verifier checks
the sumcheck algebra using the public target \(S_t\) and degree bound \(2\), but
does not evaluate \(G_t\) itself.  The run returns
\[
  (\mathsf{ok},r',T)
  \gets
  \SumCheck_{s+n}(\verifier:S_t,\prover:P),
\]
If
\(\mathsf{ok}=0\), the verifier rejects.  Otherwise write
\[
  r'
  =
  (\xi,\eta)
  \in\F^s\times\F^n.
\]
The remaining terminal condition is
\[
  T
  =
  G_t(\xi,\eta)
  \mathsf{Eq}_E(\xi,\eta).
\]
The verifier computes the public factor
\[
  e
  =
  \mathsf{Eq}_E(\xi,\eta).
\]
If \(e=0\), the verifier aborts this batch.  Otherwise the
needed value of the private factor is forced:
\[
  w
  =
  T/e.
\]

It remains to express this private factor as one evaluation request.  Define
the public RowFold coefficients
\[
  \lambda_j
  =
  \chi_{\bits_s(j)}(\xi)
  \chi_{\bits_s(j)}(t)
  \qquad(0\le j<q),
\]
and derive the virtual handle
\[
  \widehat O_{\mathrm{batch}}
  =
  \mathsf{RowFold.Commit}
  \bigl((\widehat O_{h_j},\lambda_j)_{j=0}^{q-1}\bigr).
\]
By the RowFold definition in the Virtual Handles subsection, this handle
satisfies
\[
  \widehat O_{\mathrm{batch}}(\eta)
  =
  \sum_{j=0}^{q-1}
    \lambda_j\,\widehat O_{h_j}(\eta)
  \qquad(\eta\in\F^n).
\]
Thus the single remaining evaluation claim is
\[
  \widehat O_{\mathrm{batch}}(\eta)
  =
  w.
\]

This last display is a handle-level statement.  In a concrete backend, the
coefficients \(\lambda_j\) scale same-address internal openings of the
component backend oracles; the verifier is not running one MLPCS evaluation
protocol for every \(\widehat O_{h_j}\).  That is the handle/API version of
Blaze Remark~4.3: many different-polynomial, different-point claims become one
virtual RowFold handle opened at one common point.

The row-folded hybrid protocol below still records the unbatched set
\(\EvalReqs_{\RAA}\), because the native RAA checks are easiest to state as
local algebraic constraints.  The main protocol then partitions that set into
\(\EvalReqs_{\mathrm{ord}}\), containing the ordinary requests, and
\(\EvalReqs_{u5}\), containing the requests to \(\widehat O_{u_5}\).  Only
\(\EvalReqs_{\mathrm{ord}}\) is passed to the merged-evaluation subprotocol in
Figure~\ref{fig:protocol-merge-native-evals}.

\subsection{Row-Folded Blaze In The
\(\mathcal F_{\mathrm{MLPCS}}/\mathcal F_{\mathrm{HMLPCS}}^\delta\)-Hybrid}

We can now state the top-level Blaze flow as a hybrid protocol.  In this
subsection, \(\mathcal F_{\mathrm{MLPCS}}\) is the ideal multilinear-oracle
functionality from Figure~\ref{fig:func-mlpcs-oracle}.  It is used for
prover-originated native tensors: the prover commits a tensor, the
functionality returns an MLE oracle handle, and the verifier later obtains MLE
evaluations at field points.  The folded input codeword is different.  It is
already fixed as a coordinate handle \(R_\star\), so the protocol uses
\(\mathcal F_{\mathrm{HMLPCS}}^\delta\) from
Figure~\ref{fig:func-hmlpcs-oracle} to bridge the literal coordinate string
behind \(R_\star\) to the native MLE handle \(\widehat O_{u_5}\).

Figure~\ref{fig:native-blaze-fmlpcs-hybrid} is therefore not an incomplete
protocol and not merely a list of constraints.  It is Blaze in the
\(\mathcal F_{\mathrm{MLPCS}}/\mathcal F_{\mathrm{HMLPCS}}^\delta\)-hybrid
model.  The inlined RAA flow produces
evaluation requests of the form \(J(r)=v\).  The ordinary MLPCS requests are
discharged by the merged-evaluation subprotocol in
Figure~\ref{fig:protocol-merge-native-evals}; requests to
\(\widehat O_{u_5}\) are discharged directly through
\(\mathcal F_{\mathrm{HMLPCS}}^\delta.\mathsf{Eval}\).  Give this protocol real
implementations of the coordinate-oracle layer and of the MLPCS/HMLPCS
interfaces, and the composition is a concrete Blaze implementation.  Ordinary
MLPCS handles are realized by committing an encoded string for each native
tensor and using \(\EncMLE[C]\) to open later evaluation claims.  The
\(u_5/R_\star\) bridge has the stricter requirement captured by
\(\mathcal F_{\mathrm{HMLPCS}}^\delta\): the systematic/message coordinates
must be the already-fixed handle \(R_\star\), or an equivalent binding mechanism
must be proved.

The important topology is the same one frozen in
Figure~\ref{fig:protocol-blaze-pcs}.  The encoded matrix is committed once as a
coordinate oracle; its rows are not separately committed to the MLPCS layer.
Only after the verifier samples \(\rho\) do the parties form the virtual folded
handle
\[
  R_\star(b)
  =
  \sum_{h\in\B^\ell}\rho[h]\,R_c(b)[h],
  \qquad b\in\B^n.
\]
This is the first outer encoded object passed to the inner RAA-opening flow.
The inner flow commits the supplied coordinate handle together with the other
RAA-stage handles before it asks any MLE-evaluation questions.
The folded tensor is
\[
  c_\star[b]=\sum_{h\in\B^\ell}\rho[h]c[h,b],
  \qquad b\in\B^n.
\]
Concretely, the \(\mathcal F_{\mathrm{HMLPCS}}^\delta\) call for this object is
realized by a systematic backend commitment to
\[
  \mathsf{RFC}(u_5)=u_5\Vert p,
\]
where the systematic coordinate handle used by the inner opener is literally
\(O_y=R_\star\), not a fresh commitment to another copy of \(u_5\).  A backend
commitment that re-commits a fresh systematic copy would not realize the handle
relation used by this protocol.  The \(\mathcal F_{\mathrm{HMLPCS}}^\delta\)
threshold is a message-domain threshold for the string behind \(O_y\); the
systematic backend \(\EncMLE[C_{\mathrm{sys}}]\) threshold must therefore be
scaled by the systematic fraction of the backend codeword, as described in
Figure~\ref{fig:func-hmlpcs-oracle}.
The public \(\mathsf{Open}\) entry point below is written first.  It performs
the row-folding adapter and then calls the helper
\(\mathsf{OpenInner}\), defined immediately afterward, on the generic existing
length-\(2^n\) coordinate handle \(O_y=R_\star\).

\section{Blaze Proof Replay In Handle Form}

\subsection{The Generic Proximity Gap Behind Row Folding}

The extraction argument for the row fold needs one coding-theory input.  This is
the point where it is tempting to reopen the internals of RAA, but we should not
do that here.  For this step, the only RAA-specific fact we need is the setup
event that the packed RAA code
\[
  \PRAA:\F^{\B^k}\to\F^{\B^n}
\]
is linear over \(\F\) and has relative distance \(d\).  Blaze proves this by
its RAA distance analysis~[Blaze24, Section~9].  Once that event holds, the
row-folding proximity argument is generic.

\begin{lemma}[Row-folding proximity gap; cf. Blaze Corollary~2.6]
\label{lem:row-fold-proximity-gap}
Let \(C\subseteq\F^{\B^n}\) be any linear code with relative distance \(d\), and
let \(C^L\subseteq\F^{\B^\ell\times\B^n}\) be its row-wise interleaving, where
\(L=2^\ell\).  Let
\[
  c\in\F^{\B^\ell\times\B^n}
\]
be a committed matrix satisfying
\[
  \Delta(c,C^L)>\delta.
\]
If \(\varepsilon>0\) and \(\delta-\varepsilon<d/3\), then for a uniformly random
\(\rho\in\F^{\B^\ell}\), the folded word
\[
  c_\star[b]
  =
  \sum_{h\in\B^\ell}\rho[h]\,c[h,b]
  \qquad(b\in\B^n)
\]
satisfies
\[
  \Delta(c_\star,C)>\delta-\varepsilon
\]
except with probability at most \(1/(\varepsilon|\F|)\).
\end{lemma}

\begin{proof}[Proof input]
This is the linear proximity-gap theorem used by Blaze as Corollary~2.6,
derived from Ben-Sasson, Kopparty, and Saraf~[BKS18,Blaze24].  We use it as a
black-box coding theorem with the hypotheses and conclusion stated above.  The
surprising part is that the lemma uses only linearity and distance.  It does
not use the fact that RAA was built from repetition, random permutations, and
accumulators.

Here is the proof intuition.  A random row fold samples a random vector from the
row span of \(c\).  The bad event is not merely that a few coordinate errors
cancel.  The bad event is that this random row-span vector lands unusually close
to the code \(C\).  The proximity-gap theorem says that a linear code of
distance \(d\) has no large medium-distance cloud below the \(d/3\) threshold:
if an affine or linear space contains one vector far from the code, then almost
every vector in that space is still far from the code.  Thus, once \(c\) is far
from \(C^L\), a random row combination remains far from \(C\) with high
probability.
\end{proof}

The actual Blaze soundness proof applies this generic lemma after normalizing
the evaluation target.  If the prover sends row-evaluation values \(u\), Blaze
looks at
\[
  c-u\otimes C(1),
\]
where \(C(1)\) is the encoding of the all-ones message.  This shifts the target
evaluation to zero, so the distance question becomes distance from a linear
space rather than an affine space.  After the random row fold, the proof shifts
back and obtains a folded claim of the form
\[
  c_\star \text{ is close to some } C(m_\star)
  \quad\text{with}\quad
  \MLE(m_\star)(z_{\mathrm{in}})=v_\star.
\]
This is the proximity statement that the hybrid extractor will use.

\subsection{The Hybrid Extractor}

We now define the extractor before proving that it works.  The extractor is
allowed to be computationally unbounded.  It runs in the hybrid model above and
treats the MLE-handle functionalities as black boxes.  For an MLE handle
\(\widehat O_h\), write
\[
  \mathsf{Ext}_{\mathrm{MLPCS}}(\widehat O_h)=h^\dagger
\]
for the tensor represented by that MLE handle.  The functionality is
relation-agnostic: it does not know whether \(h^\dagger\) is an RAA stage, a
product tree, or close to any code.  It only guarantees that
\[
  \mathcal F_{\mathrm{MLPCS}}.\mathsf{Eval}(\widehat O_h,r)
  =
  \MLE(h^\dagger)(r).
\]
All proximity claims below are proved outside the native MLPCS algebra, using
the row fold, the HMLPCS bridge for the folded input word, and the generic
proximity-gap lemma.

For a matrix \(m\in\F^{\B^\ell\times\B^k}\), write \(\PRAA^L(m)\) for the
row-wise interleaved packed RAA encoding:
\[
  \PRAA^L(m)[h,\ast]=\PRAA(m[h,\ast])
  \qquad(h\in\B^\ell).
\]

\begin{protocolbox}{Extractor: Hybrid Blaze Extractor}{fig:extractor-hybrid-blaze}

Line E6 is deliberately unbounded: it is an extractor step, not an honest-prover
algorithm.  The proof obligation is to show that, for accepting transcripts,
the closest codeword chosen in E6 is actually close enough and has the claimed
evaluation.

\paragraph{Folded extraction.}
First look at lines E2--E5.  The terminal evaluation request in
Figure~\ref{fig:native-blaze-fmlpcs-hybrid} asks the verifier to check
\[
  \mathcal F_{\mathrm{MLPCS}}.\mathsf{Eval}
  (\widehat O_{u_0},z_{\mathrm{in}})
  =
  v_\star.
\]
By the target functionality's contract, this means
\[
  \MLE(u_0^\dagger)(z_{\mathrm{in}})=v_\star.
\]
The accumulator, permutation, and six-sumcheck checks then force the extracted
tensors to satisfy the RAA stage equations, except with the algebraic
soundness error from the random challenges and sumcheck:
\[
  u_1^\dagger=F_{\mathrm{rep}}(u_0^\dagger),\quad
  u_2^\dagger=M_{\pi_1}u_1^\dagger,\quad
  u_3^\dagger=\Acc(u_2^\dagger),\quad
  u_4^\dagger=M_{\pi_2}u_3^\dagger,\quad
  u_5^\dagger=\Acc(u_4^\dagger).
\]
The handle \(\widehat O_{u_5}\) is the MLE handle committed from the virtual
folded coordinate handle \(R_\star\).  Therefore the raw folded word
\(c_\star\) from E2 and the extracted tensor \(u_5^\dagger\) are linked by the
outer row-fold/proximity argument, not by a special RAA-aware MLPCS rule.
Combining that proximity statement with the stage equations gives
\[
  c_\star \text{ is close to } \PRAA(m_\star),
  \qquad
  \MLE(m_\star)(z_{\mathrm{in}})=v_\star.
\]
This is what the local extractor learns from one accepting folded transcript.

\paragraph{Global extraction.}
Line E6 chooses a closest interleaved RAA codeword
\[
  c_{\mathrm{near}}=\PRAA^L(m)
\]
to the committed matrix \(c\).  Suppose, toward soundness, that \(c\) were far
from every interleaved RAA codeword whose message evaluates to \(v\) at
\((z_{\mathrm{slice}},z_{\mathrm{in}})\).  The prover's row-evaluation vector
\(u\) must still pass the explicit interpolation check
\[
  v=
  \sum_{h\in\B^\ell}\chi_h(z_{\mathrm{slice}})\,u[h].
\]
After the verifier samples \(\rho\), the folded value is
\[
  v_\star=\sum_{h\in\B^\ell}\rho[h]\,u[h].
\]
The generic proximity-gap lemma above says that a far committed matrix remains
far after a random row fold, except with probability \(1/(\varepsilon|\F|)\).
Equivalently, after Blaze's normalization by \(u\otimes C(1)\), the folded word
\(c_\star\) is far from every \(\PRAA(m_\star)\) satisfying
\[
  \MLE(m_\star)(z_{\mathrm{in}})=v_\star.
\]
That contradicts the folded extraction conclusion unless one of the named
soundness errors occurs.  Hence an accepting transcript implies that E6's
closest codeword is close and that its decoded message \(m\) satisfies
\[
  \MLE(m)(z_{\mathrm{slice}},z_{\mathrm{in}})=v.
\]

This is the modular picture.  The folded extractor explains what a single
accepting row fold certifies.  The global extractor uses the generic
proximity-gap lemma to turn that folded certificate into a statement about the
whole committed matrix.

\subsection{Self-Contained Import: Blaze Lemma~6.1}

This subsection begins the proof import.  It is written as a local proof, not
as a reading guide to the Blaze paper.  The reader should be able to follow the
objects, the reduction, and the soundness argument from the definitions in this
subsection.  Source labels such as ``Blaze Lemma~6.1'' and
``Claim~6.1.x'' are provenance markers: they say which Blaze step we are
mirroring, but the mathematical content is stated here before it is used.
The first lemma below is the Blaze-side replay.  The second lemma is the
handle/API translation used by the fixed protocol box.  For the present audit,
the Blaze-side replay is the authoritative imported proof; the handle-form
lemma is downstream translation material retained separately.

\paragraph{Blaze-side statement.}
\begin{lemma}[Blaze interleaving RMLE reduction replay; cf. Lemma~6.1]
\label{lem:blaze-interleaving-replay}
Let \(C:\F^k\to\F^n\) be a linear code with relative distance \(\lambda\).
Assume there is an IOPP for \(\RMLE[C]\) which, for proximity parameter
\(\delta'<\lambda/3\), has soundness error
\(\varepsilon(\delta',k)\).  Then, for every interleaving parameter \(t\),
there is an IOPP for \(\RMLE[C^t]\).  For top-level proximity parameter
\(\delta\), Blaze sets
\[
  \delta'=0.99\delta,
\]
and obtains soundness
\[
  \varepsilon(\delta',k)+\frac{1}{(\delta-\delta')|\F|}.
\]
The input alphabet becomes \(\F^t\), the index and proof alphabets remain
\(\F\), the protocol adds one round and \(2t\) field elements of non-oracle
communication, and each base input query is emulated by one column query to
the interleaved input.
\end{lemma}

\begin{proof}
This is Blaze Lemma~6.1 in the paper's notation.  The verifier's explicit
input is \(z=(z_1,z_2)\in\F^{\log t}\times\F^{\log k}\) and \(v\in\F\).  The
implicit input is a word
\[
  c\in(\F^t)^n,
\]
viewed equivalently as a \(t\times n\) matrix over \(\F\).  A witness message is
viewed as a \(t\times k\) matrix \(m\), and \(C^t(m)\) means applying \(C\) to
each row.

The protocol is the five-step reduction in Blaze.  First the prover sends
\[
  u\in\F^t,
  \qquad
  u_i=\widehat m_i(z_2)
\]
in the honest case.  Second, the verifier checks \(\widehat u(z_1)=v\).  Third,
the verifier samples \(r\leftarrow\F^t\) and defines
\[
  m_{\mathrm{combo}}=r^\top m,
  \qquad
  c_{\mathrm{combo}}=r^\top c.
\]
Fourth, the prover and verifier run the assumed IOPP for \(\RMLE[C]\) on point
\(z_2\), value \(v'=\langle u,r\rangle\), and implicit input
\(c_{\mathrm{combo}}\).  The verifier does not receive
\(c_{\mathrm{combo}}\) as a new oracle; a query \(j\in[n]\) is answered by
reading the \(j\)-th column of \(c\) and returning
\(\sum_i r_i c_{i,j}\).  Fifth, the verifier accepts exactly when the row-value
check and the base IOPP accept.

Completeness follows from linearity:
\[
  c_{\mathrm{combo}}
  =
  r^\top C^t(m)
  =
  C(r^\top m)
  =
  C(m_{\mathrm{combo}}),
\]
and
\[
  \widehat m_{\mathrm{combo}}(z_2)
  =
  \sum_i r_i\widehat m_i(z_2)
  =
  \langle u,r\rangle.
\]

For soundness, fix \(c\) that is \(\delta\)-far from
\[
  \mathsf{Aff}_{z,v}
  =
  \{C^t(m):\widehat m(z)=v\},
\]
and fix a deterministic prover message \(u\) with \(\widehat u(z_1)=v\); if
this equality fails, the verifier already rejects.  Let
\[
  \mathsf{Lin}_{z_2}
  =
  \{C(a):\widehat a(z_2)=0\}.
\]
Blaze Claim~6.1.1 states that
\[
  \Delta\bigl(c-u\otimes C(1^k),(\mathsf{Lin}_{z_2})^t\bigr)>\delta.
\]
Otherwise, shifting back by \(u\otimes C(1^k)\) would give a codeword in
\(\mathsf{Aff}_{z,v}\) within distance \(\delta\) of \(c\).

By Corollary~2.6, this row-wise distance survives a random row combination:
with all but probability \(1/((\delta-\delta')|\F|)\) over
\(r\leftarrow\F^t\),
\[
  \Delta\bigl(r^\top(c-u\otimes C(1^k)),\mathsf{Lin}_{z_2}\bigr)>\delta'.
\]
This is Blaze Claim~6.1.2.  Claim~6.1.3 shifts back from the linear target to
the affine target:
\[
  \Delta\bigl(r^\top c,\{C(a):\widehat a(z_2)=\langle u,r\rangle\}\bigr)
  >
  \delta'.
\]
Therefore the folded base instance is \(\delta'\)-far from
\(\RMLE[C]\), and the base IOPP rejects except with error
\(\varepsilon(\delta',k)\).  Adding the Corollary~2.6 bad-fold probability
gives the stated soundness.
\end{proof}

\paragraph{Handle/API translation.}
\begin{lemma}[Interleaving RMLE reduction in handle form; cf. Blaze Lemma~6.1]
\label{lem:blaze-interleaving-handle}
Let
\[
  C:\F^{\B^k}\to\F^{\B^n}
\]
be a linear code with relative distance \(\lambda\).  Assume there is a
proximity protocol for \(\RMLE[C]\): on public \((z,v)\in\F^k\times\F\) and
oracle access to a word \(y\in\F^{\B^n}\), the protocol rejects whenever \(y\)
is far from every codeword \(C(m)\) with \(\MLE(m)(z)=v\), except with its
soundness error.  The interleaving reduction below turns this base protocol
into a proximity protocol for \(\RMLE[C^t]\).

Fix a top-level proximity parameter
\[
  \delta<\lambda/3,
  \qquad
  \delta_{\mathrm{base}}=0.99\,\delta,
  \qquad
  \eta=\delta-\delta_{\mathrm{base}}.
\]
Blaze writes \(\delta'\) for \(\delta_{\mathrm{base}}\).  Lemma~6.1 runs the
base protocol at proximity \(\delta_{\mathrm{base}}\).  If the base protocol's
soundness error is \(\varepsilon(\delta_{\mathrm{base}},k)\), the interleaved
protocol's soundness error is
\[
  \varepsilon(\delta_{\mathrm{base}},k)
  +
  \frac{1}{\eta|\F|}.
\]
The second term is the row-fold loss from the linear proximity-gap theorem
stated below.  The other parameters are the base parameters evaluated at
\(\delta_{\mathrm{base}}\), with the same
index and proof alphabet \(\F\), one extra round, input queries lifted from one
base coordinate to one interleaved column read, and the additional
non-oracle communication for the prover's vector \(u\in\F^t\) and the
verifier's fold vector \(\rho\in\F^t\).  This is Blaze's \(2t+\mathsf{cc}(k)\)
term.  The prover time gains the \(O(tn)\) row-combination work, and the
verifier time gains the \(O(t\cdot q_{\mathrm{input}})\) cost of emulating base
input queries by reading columns of \(c\).  We will not need the full parameter
table for the proof; all proof-relevant parameters are named above.
\end{lemma}

\begin{proof}
This proof is our copy of the interleaving argument.  The source tie-back is
Blaze Lemma~6.1; the proof below spells out the relation, the handle
translation, and the three distance claims locally.

\paragraph{The base relation and its proximity protocol.}
For a message tensor \(m\in\F^{\B^k}\), the codeword is
\[
  y=C(m)\in\F^{\B^n}.
\]
For a point \(z\in\F^k\), \(\MLE(m)(z)\) is the multilinear extension of the
message tensor evaluated at \(z\).  The exact \(\RMLE[C]\) relation is
\[
  ((z,v),y;m)\in\RMLE[C]
  \qquad\Longleftrightarrow\qquad
  y=C(m)\ \text{and}\ \MLE(m)(z)=v.
\]
The corresponding proximity protocol for \(\RMLE[C]\) has oracle access to a
literal word \(y\in\F^{\B^n}\) and receives public \((z,v)\).  Its soundness
promise is phrased as distance from the affine target
\[
  \mathcal A^C_{z,v}
  =
  \{C(m):m\in\F^{\B^k},\ \MLE(m)(z)=v\}.
\]
If \(y\) is farther than the chosen proximity parameter from this set, the base
\(\RMLE[C]\)-IOPP rejects except with its soundness error.  The exact relation
names the witness \(m\); the proximity statement is distance from the affine
set \(\mathcal A^C_{z,v}\), not an extra nearest-neighbor decoding step inside
Lemma~6.1.

The construction below gives a proximity protocol for the row-wise interleaved
relation \(\RMLE[C^t]\) for arbitrary \(t\).  Our protocol uses
Boolean tensor notation, so here we specialize to \(t=2^\ell\); a non-power of
two \(t\) would be handled by the usual padding convention before writing the
slice index as \(\B^\ell\).  In this specialization,
\[
  m\in\F^{\B^\ell\times\B^k},
  \qquad
  c\in\F^{\B^\ell\times\B^n},
  \qquad
  C^t(m)[h,\ast]=C(m[h,\ast]).
\]
Blaze sometimes presents the input alphabet as \(F^t\) or as an extension-field
alphabet.  Here we use the expanded column-vector view
\(\F^{\B^\ell}\).  This is a notation translation, not a proof change: the
Lemma~6.1 protocol and proof use the row decomposition of \(m,c\), verifier
queries to columns of \(c\), and \(\F\)-linear row combinations.

\paragraph{Linear-code facts used locally.}
The proof uses only two code facts about \(C\).  First, \(C\) is linear:
\[
  C(a m_0+b m_1)=aC(m_0)+bC(m_1)
  \qquad(a,b\in\F).
\]
Second, \(C\) has relative distance \(\lambda\): any two distinct codewords
differ on at least a \(\lambda\)-fraction of coordinates.  Equivalently, every
nonzero word in the linear code image of \(C\) has relative Hamming weight at
least \(\lambda\).

\paragraph{Our handle version of the input oracle.}
Blaze gives the verifier oracle access to the interleaved input word \(c\).  In
the fixed protocol above, the corresponding object is the handle
\[
  R_c:\B^n\to\F^{\B^\ell},
  \qquad
  R_c(b)=c[\ast,b].
\]
The literal matrix \(c\) is the expanded semantic object behind the handle.  In
the honest commit path \(c=C^t(m)\).  In the proximity setting \(c\) may be a
malicious literal matrix; the proof concerns whether it is close to an
interleaved codeword with the claimed evaluation.

The verifier's public opening claim is
\[
  z=(z_{\mathrm{slice}},z_{\mathrm{in}})
  \in\F^\ell\times\F^k,
  \qquad
  v\in\F.
\]
Blaze writes this as \(z=(z_1,z_2)\).  The relation target is the affine set
\[
  \mathcal A_{z,v}
  =
  \{C^t(m'):\MLE(m')(z_{\mathrm{slice}},z_{\mathrm{in}})=v\}.
\]
For a word or matrix \(w\) and a set \(S\) of same-shaped words or matrices,
write
\[
  \Delta(w,S)=\min_{s\in S}\Delta(w,s)
\]
for relative Hamming distance from \(S\).

\paragraph{The reduction protocol.}
The reduction protocol has five steps.  Each step names both the semantic word
used in the proof and the handle-level object used by the fixed protocol.
Source tie-back: these are the five steps of Blaze Lemma~6.1, written in our
tensor and handle notation.

\emph{Step 1: announce row evaluations.}
The prover sends a full row-evaluation vector
\[
  u\in\F^{\B^\ell}.
\]
For an honest message \(m\),
\[
  u[h]=\MLE(m[h,\ast])(z_{\mathrm{in}})
  \qquad(h\in\B^\ell).
\]
This is exactly Lines O1--O2 of Figure~\ref{fig:native-blaze-fmlpcs-hybrid}.

\emph{Step 2: check the top-level value through \(u\).}
The verifier views \(u\) as a Boolean tensor on \(\B^\ell\) and checks
\[
  \MLE(u)(z_{\mathrm{slice}})
  =
  v.
\]
This is Line O3.  This line checks consistency of the announced row
evaluations with the public value.  It is not a proximity test for \(c\).

\emph{Step 3: sample the random row fold.}
The verifier samples a random row-combination vector
\[
  \rho\leftarrow\F^{\B^\ell}.
\]
Blaze calls this vector \(r\).  To avoid collision with later MLE evaluation
points, this paper calls it \(\rho\).  Define
\[
  m_\star=\rho^\top m\in\F^{\B^k},
  \qquad
  c_\star=\rho^\top c\in\F^{\B^n},
\]
meaning
\[
  m_\star[a]=\sum_{h\in\B^\ell}\rho[h]m[h,a],
  \qquad
  c_\star[b]=\sum_{h\in\B^\ell}\rho[h]c[h,b].
\]
In our protocol \(c_\star\) is not sent as a fresh literal string.  It is the
expanded semantics of the virtual handle
\[
  R_\star(b)=\sum_{h\in\B^\ell}\rho[h]R_c(b)[h].
\]
This is Lines O4--O7.

\emph{Step 4: call the base \(\RMLE[C]\)-IOPP on the folded input.}
Run the base \(\RMLE[C]\)-IOPP on public point
\[
  z_{\mathrm{in}}\in\F^k
\]
and public value
\[
  v_\star=\ip{\rho}{u}.
\]
The implicit base input oracle is \(c_\star\).  Since the verifier does not
hold \(c_\star\) as a separately committed string, it emulates each query
\(b\in\B^n\) by reading the column \(R_c(b)\) and returning
\[
  c_\star[b]=\sum_{h\in\B^\ell}\rho[h]R_c(b)[h].
\]
This is exactly what the virtual folded handle \(R_\star\) does.  When
\(C=\PRAA\), Lines O8 onward are the inlined base \(\RMLE[\PRAA]\) checker.

\emph{Step 5: accept only if both layers accept.}
Accept if the row-evaluation check and the base \(\RMLE[C]\)-IOPP both accept.
In the fixed protocol, the later native
\(\RMLE[\PRAA]\) work and its MLE-evaluation checks implement this base call.

\paragraph{Completeness.}
Assume the exact interleaved relation holds:
\[
  c=C^t(m),
  \qquad
  \MLE(m)(z_{\mathrm{slice}},z_{\mathrm{in}})=v.
\]
The honest prover sends \(u[h]=\MLE(m[h,\ast])(z_{\mathrm{in}})\).  Recall the
standard tensor expansion of the MLE:
\[
  \MLE(m)(z_{\mathrm{slice}},z_{\mathrm{in}})
  =
  \sum_{h\in\B^\ell}
  \chi_h(z_{\mathrm{slice}})\MLE(m[h,\ast])(z_{\mathrm{in}}),
\]
where \(\chi_h\) is the equality-basis polynomial for the Boolean point
\(h\in\B^\ell\).  Therefore
\[
  \MLE(u)(z_{\mathrm{slice}})
  =
  \sum_{h\in\B^\ell}\chi_h(z_{\mathrm{slice}})u[h]
  =
  \MLE(m)(z_{\mathrm{slice}},z_{\mathrm{in}})
  =
  v,
\]
so the row check passes.

For every verifier challenge \(\rho\), linearity of \(C\) gives
\[
  c_\star
  =
  \rho^\top c
  =
  \rho^\top C^t(m)
  =
  C(\rho^\top m)
  =
  C(m_\star).
\]
The same expansion used above gives
\[
  \MLE(m_\star)(z_{\mathrm{in}})
  =
  \sum_{h\in\B^\ell}\rho[h]\MLE(m[h,\ast])(z_{\mathrm{in}})
  =
  \ip{\rho}{u}
  =
  v_\star.
\]
Thus the base \(\RMLE[C]\) instance is exact and the base protocol accepts by
its completeness.  Source tie-back: this is the completeness proof of
Blaze Lemma~6.1 translated through \(R_c\) and \(R_\star\).

\paragraph{Soundness setup.}
Fix \(z=(z_{\mathrm{slice}},z_{\mathrm{in}})\) and \(v\).  Let the malicious
literal matrix behind \(R_c\) be
\[
  c\in\F^{\B^\ell\times\B^n}.
\]
Assume \(c\) is \(\delta\)-far from the affine target
\[
  \mathcal A_{z,v}
  =
  \{C^t(m'):\MLE(m')(z_{\mathrm{slice}},z_{\mathrm{in}})=v\}.
\]
Fix a deterministic cheating prover strategy.  Let its first message be
\[
  u\in\F^{\B^\ell}.
\]
If \(\MLE(u)(z_{\mathrm{slice}})\ne v\), the verifier rejects immediately, so
the soundness proof conditions on
\[
  \MLE(u)(z_{\mathrm{slice}})=v.
\]
The goal is now to show that, for a random \(\rho\), the folded input
\(\rho^\top c\) is far from the base affine target
\[
  \mathcal A^C_{z_{\mathrm{in}},\ip{\rho}{u}}
  =
  \{C(q):q\in\F^{\B^k},\
  \MLE(q)(z_{\mathrm{in}})=\ip{\rho}{u}\},
\]
except with the row-fold error from Corollary~2.6.  Then the base
\(\RMLE[C]\)-IOPP rejects this folded instance by its own soundness.

We now convert the affine top-level distance statement into a linear
zero-evaluation statement.  Define
\[
  \mathbf 1\in\F^{\B^k},
  \qquad
  \mathbf 1[a]=1,
\]
and let \(C(\mathbf 1)\in\F^{\B^n}\) be its encoding.  Also define
\[
  \mathcal L_{z_{\mathrm{in}}}
  =
  \{C(q):q\in\F^{\B^k},\ \MLE(q)(z_{\mathrm{in}})=0\}.
\]
The row-wise space \((\mathcal L_{z_{\mathrm{in}}})^t\) consists of matrices
whose rows each lie in \(\mathcal L_{z_{\mathrm{in}}}\).
Because \(C\) is linear, \(\mathcal L_{z_{\mathrm{in}}}\) is a linear subcode
of \(C\).  Its distance is at least the distance \(\lambda\) of \(C\), so it
satisfies the distance hypothesis needed for the row-fold theorem.

\begin{claim}[First shift; cf. Blaze Claim~6.1.1]
\label{claim:blaze-interleaving-first-shift}
The shifted matrix is far from the row-wise zero-evaluation code:
\[
  \Delta\!\left(
    c-u\otimes C(\mathbf 1),
    (\mathcal L_{z_{\mathrm{in}}})^t
  \right)>\delta,
\]
where
\[
  (u\otimes C(\mathbf 1))[h,b]=u[h]\,C(\mathbf 1)[b].
\]
\end{claim}

\begin{proof}
Suppose instead, toward a contradiction, that there exists
\[
  c'\in(\mathcal L_{z_{\mathrm{in}}})^t
  \qquad\text{with}\qquad
  \Delta(c-u\otimes C(\mathbf 1),c')\le\delta.
\]
Define
\[
  c''=c'+u\otimes C(\mathbf 1)
\]
so \(\Delta(c,c'')\le\delta\).  For each row \(h\in\B^\ell\), because
\(c'[h,\ast]\in\mathcal L_{z_{\mathrm{in}}}\), choose
\[
  q'_h\in\F^{\B^k}
  \quad\text{such that}\quad
  C(q'_h)=c'[h,\ast],
  \qquad
  \MLE(q'_h)(z_{\mathrm{in}})=0.
\]
Define
\[
  q''_h=q'_h+u[h]\mathbf 1.
\]
By linearity of \(C\),
\[
  C(q''_h)
  =
  c'[h,\ast]+u[h]C(\mathbf 1)
  =
  c''[h,\ast].
\]
Also,
\[
  \MLE(q''_h)(z_{\mathrm{in}})
  =
  \MLE(q'_h)(z_{\mathrm{in}})
  +
  u[h]\MLE(\mathbf 1)(z_{\mathrm{in}})
  =
  u[h].
\]
Let \(q''\in\F^{\B^\ell\times\B^k}\) be the matrix of these row messages.  Then
\[
  c''=C^t(q'')
\]
and
\[
  \MLE(q'')(z_{\mathrm{slice}},z_{\mathrm{in}})
  =
  \sum_{h\in\B^\ell}\chi_h(z_{\mathrm{slice}})
  \MLE(q''_h)(z_{\mathrm{in}})
  =
  \sum_{h\in\B^\ell}\chi_h(z_{\mathrm{slice}})u[h]
  =
  \MLE(u)(z_{\mathrm{slice}})
  =
  v.
\]
Thus \(c''\in\mathcal A_{z,v}\), while \(\Delta(c,c'')\le\delta\).  This
contradicts the soundness assumption \(\Delta(c,\mathcal A_{z,v})>\delta\).
\end{proof}

\begin{claim}[Random fold preserves linear distance; cf. Blaze Claim~6.1.2]
\label{claim:blaze-interleaving-random-fold}
Except with probability at most \(1/(\eta|\F|)\) over
\(\rho\leftarrow\F^{\B^\ell}\),
\[
  \Delta\!\left(
    \rho^\top(c-u\otimes C(\mathbf 1)),
    \mathcal L_{z_{\mathrm{in}}}
  \right)>\delta_{\mathrm{base}}.
\]
\end{claim}

\begin{proof}
By Claim~\ref{claim:blaze-interleaving-first-shift},
\[
  c-u\otimes C(\mathbf 1)
\]
is far from the linear row-wise space \((\mathcal L_{z_{\mathrm{in}}})^t\).
The only external coding-theory fact used in this layer is the following
linear proximity-gap statement: if a matrix is
\(\delta\)-far from the row-wise interleaving of a linear code of distance at
least \(\lambda\), then a random row combination is
\(\delta-\eta\)-far from the base code except with probability at most
\(1/(\eta|\F|)\), provided \(\delta-\eta<\lambda/3\).  Here the base linear code
is \(\mathcal L_{z_{\mathrm{in}}}\), whose distance is at least \(\lambda\).
Since \(\delta-\eta=\delta_{\mathrm{base}}\), applying this theorem to the
matrix \(c-u\otimes C(\mathbf 1)\) gives exactly the claimed bound.
This is the proximity-preservation step.  It is not a coordinate spot check:
the random fold is used together with the proximity-gap theorem behind
Corollary~2.6.
\end{proof}

\begin{claim}[Second shift; cf. Blaze Claim~6.1.3]
\label{claim:blaze-interleaving-second-shift}
Condition on a challenge \(\rho\) for which
Claim~\ref{claim:blaze-interleaving-random-fold} holds.  Define the base affine
target
\[
  \mathcal A'_{z_{\mathrm{in}},v_\star}
  =
  \{C(q):\MLE(q)(z_{\mathrm{in}})=v_\star\},
  \qquad
  v_\star=\ip{\rho}{u}.
\]
Then
\[
  \Delta(\rho^\top c,\mathcal A'_{z_{\mathrm{in}},v_\star})
  >
  \delta_{\mathrm{base}}.
\]
\end{claim}

\begin{proof}
Suppose toward a contradiction that there exists
\[
  c'\in\mathcal A'_{z_{\mathrm{in}},v_\star}
  \qquad\text{with}\qquad
  \Delta(\rho^\top c,c')\le\delta_{\mathrm{base}}.
\]
Because \(c'\in\mathcal A'_{z_{\mathrm{in}},v_\star}\), choose
\[
  q'\in\F^{\B^k}
  \quad\text{such that}\quad
  C(q')=c',
  \qquad
  \MLE(q')(z_{\mathrm{in}})=v_\star.
\]
Define
\[
  q''=q'-v_\star\mathbf 1,
  \qquad
  c''=C(q'')=c'-v_\star C(\mathbf 1).
\]
Then
\[
  \MLE(q'')(z_{\mathrm{in}})
  =
  v_\star-v_\star\MLE(\mathbf 1)(z_{\mathrm{in}})
  =
  0,
\]
so \(c''\in\mathcal L_{z_{\mathrm{in}}}\).  Moreover,
\[
  \rho^\top(u\otimes C(\mathbf 1))
  =
  \left(\sum_{h\in\B^\ell}\rho[h]u[h]\right)C(\mathbf 1)
  =
  v_\star C(\mathbf 1).
\]
Therefore
\[
\begin{aligned}
  \rho^\top(c-u\otimes C(\mathbf 1))-c''
  &=
  \rho^\top c-v_\star C(\mathbf 1)
  -\bigl(c'-v_\star C(\mathbf 1)\bigr) \\
  &=
  \rho^\top c-c'.
\end{aligned}
\]
Thus \(c''\in\mathcal L_{z_{\mathrm{in}}}\) is
\(\delta_{\mathrm{base}}\)-close to
\(\rho^\top(c-u\otimes C(\mathbf 1))\), contradicting the random-fold distance
statement.
\end{proof}

\paragraph{Conclusion of Lemma~6.1.}
For every good \(\rho\), the virtual folded input word
\[
  c_\star=\rho^\top c
\]
is \(\delta_{\mathrm{base}}\)-far from every base codeword \(C(q)\) whose
message satisfies
\[
  \MLE(q)(z_{\mathrm{in}})=v_\star.
\]
Therefore the base \(\RMLE[C]\)-IOPP rejects the folded instance except with
its own soundness error.  Adding the Corollary~2.6 row-fold loss gives the
soundness bound stated at the beginning of this subsection.  Source tie-back:
this completes our proof of Lemma~\ref{lem:blaze-interleaving-handle}, mirroring
Blaze Lemma~6.1.

Instantiating \(C=\PRAA\), the first imported arrow for our fixed protocol is
\[
  \RMLE[\PRAA^t]
  \xrightarrow{\text{Blaze Lemma~6.1}}
  \RMLE[\PRAA].
\]
In our API language, this says: the matrix behind \(R_c\) is reduced to the
virtual folded handle \(R_\star\); if the literal matrix is far from every
valid interleaved packed-RAA codeword with the claimed top-level MLE value,
then, except for the Lemma~6.1 row-fold loss, the folded base instance is far
from \(\RMLE[\PRAA]\) and must be rejected by the base protocol imported next.
\end{proof}

\paragraph{Native accumulator relation.}

\begin{proposition}[Blaze matrix-vector test replay; cf. Proposition~5.2]
\label{prop:blaze-matrix-vector-replay}
Let
\[
  M:\B^m\times\B^m\to\F,
  \qquad
  x,y:\B^m\to\F,
\]
and let \(\widehat M:\F^m\times\F^m\to\F\),
\(\widehat x:\F^m\to\F\), and \(\widehat y:\F^m\to\F\) be their multilinear
extensions.  If \(y=Mx\), meaning
\[
  y(i)=\sum_{j\in\B^m}M(i,j)x(j)
  \qquad(i\in\B^m),
\]
then for every \(r\in\F^m\),
\[
  \widehat y(r)=
  \sum_{j\in\B^m}x(j)\widehat M(r,j).
\]
If \(y\ne Mx\), then for a uniformly random \(r\leftarrow\F^m\), the displayed
identity fails except with probability at most \(m/|\F|\).
\end{proposition}

\begin{proof}
This is Blaze Proposition~5.2.  In the honest case, the displayed identity
holds at every Boolean point \(r\in\B^m\) by the definition of matrix-vector
multiplication.  Both sides are multilinear polynomials in \(r\), so equality
on the Boolean cube implies equality over all \(r\in\F^m\).  In the false case,
the two sides are distinct multilinear polynomials in \(r\); Schwartz--Zippel
bounds their agreement probability by \(m/|\F|\).
\end{proof}

\begin{proposition}[Blaze accumulation-kernel replay; cf. Proposition~5.3]
\label{prop:blaze-accumulation-kernel-replay}
Let
\[
  A:\B^m\times\B^m\to\{0,1\}
\]
be the accumulation matrix, where \(A(i,j)=1\) exactly when the integer encoded
by \(i\) is at least the integer encoded by \(j\).  Then:
\[
  \bigl(\widehat A(r,b)\bigr)_{b\in\B^m}
\]
can be generated in \(O(2^m)\) field operations for any \(r\in\F^m\), and
\(\widehat A(i,j)\) can be evaluated at one field point
\((i,j)\in\F^m\times\F^m\) using \(O(m)\) field operations.
\end{proposition}

\begin{proof}
This is Blaze Proposition~5.3.  For the vector-generation claim, multilinear
extension gives
\[
  \widehat A(r,b)=
  \sum_{x\in\B^m}\mathrm{eq}(x,r)A(x,b)
  =
  \sum_{x\ge b}\mathrm{eq}(x,r).
\]
After generating all equality-basis values \(\mathrm{eq}(x,r)\), one obtains
the displayed suffix sums over the integer order in linear time in the table
size.  For the point-evaluation claim, Blaze observes that the comparison
predicate \(i\ge j\) has a width-three read-once branching program, and also
gives an explicit recursion.  Writing \(i=(i_1,i_2)\) and \(j=(j_1,j_2)\) with
the first bits most significant,
\[
  A_m(i,j)=
  (i_1=1\wedge j_1=0)
  \vee
  (i_1=j_1\wedge A_{m-1}(i_2,j_2)).
\]
Its multilinear extension is computed recursively in \(O(m)\) arithmetic
operations, with \(A_0\equiv 1\).
\end{proof}

\begin{proposition}[Accumulator reduction; cf. Blaze Propositions~5.2 and~5.3]
\label{prop:native-accumulator-reduction}
Let \(x,y\in\F^{\B^n}\), and let
\[
  A:\B^n\times\B^n\to\F
\]
be the accumulator matrix with \(A[b,a]=1\) exactly when
\(\Int(b)\ge \Int(a)\).  Let
\(\widehat A:\F^n\times\F^n\to\F\) be its multilinear extension.  For
\(r\in\F^n\), define the projected accumulator identity
\[
  \MLE(y)(r)
  =
  \sum_{X\in\B^n}\widehat A(r,X)x[X].
\]
If \(y=\Acc(x)\), this identity holds for every \(r\in\F^n\).  If
\(y\ne\Acc(x)\), then the identity fails for a random \(r\leftarrow\F^n\)
except with probability at most \(n/|\F|\).  Moreover, the vector
\((\widehat A(r,X))_{X\in\B^n}\) can be generated in \(O(N)\) time and
\(\widehat A(r,s)\) can be evaluated at a single field point in \(O(n)\) field
operations, where \(N=2^n\).
\end{proposition}

\begin{proof}
The tensor \(y-\Acc(x)\) is zero exactly when \(y=\Acc(x)\).  Its multilinear
extension at \(r\) is the difference between the two sides of the displayed
identity.  If the tensor is nonzero, this difference is a nonzero multilinear
polynomial in \(n\) variables, so Schwartz--Zippel bounds its zero probability
by \(n/|\F|\).  The efficient computation of \(\widehat A\) is the explicit
accumulator-kernel computation stated in Blaze Proposition~5.3 and used by
Figure~\ref{fig:native-accumulate-reduce}.
\end{proof}

\paragraph{Native permutation relation.}

\begin{proposition}[Blaze permutation product-tree reduction; replay of Proposition~5.4]
\label{prop:blaze-permutation-replay}
Let \(m\ge 1\), let \(|\F|\ge 2^m\), and let
\[
  \pi:\B^m\to\B^m
\]
be a public permutation.  As in Blaze, also view \(\pi\) as a tag map
\(\B^m\to\F\) by assigning distinct field elements to the \(2^m\) Boolean
addresses, and write
\[
  \widehat\pi:\F^m\to\F
\]
for its multilinear extension in that tag view.  Let
\[
  x,y\in\F^{\B^m}
\]
with multilinear extensions \(\MLE(x),\MLE(y):\F^m\to\F\).

First suppose that
\[
  y(b)=x(\pi(b))\qquad(b\in\B^m).
\]
Then for every \(\alpha,\beta\in\F\) there exist multilinear polynomials
\[
  f,g:\F^{m+1}\to\F
\]
such that, for every \(r\in\F^m\),
\[
  f(1^m,0)=g(1^m,0),
\]
\[
  f(0,r)=\alpha-\bigl(\MLE(x)(r)+\beta\,\widehat\pi(r)\bigr),
  \qquad
  g(0,r)=\alpha-\bigl(\MLE(y)(r)+\beta\,\Idx(r)\bigr),
\]
and
\[
  \sum_{a\in\B^m}\chi_a(r)
  \bigl(f(1,a)-f(a,0)f(a,1)\bigr)=0,
\]
\[
  \sum_{a\in\B^m}\chi_a(r)
  \bigl(g(1,a)-g(a,0)g(a,1)\bigr)=0.
\]
Moreover, for honest \(x,y,\alpha,\beta\), the prover can construct such
\(f,g\) in \(O(2^m)\) field operations.

Conversely, if there exists \(b\in\B^m\) with \(y(b)\ne x(\pi(b))\), then
except with probability at most \((2^m+1)/|\F|\) over
\(\alpha,\beta\leftarrow\F\), every multilinear pair
\[
  f,g:\F^{m+1}\to\F
\]
fails at least one of the five displayed tests for all but a
\(10m/|\F|\)-fraction of \(r\in\F^m\).
\end{proposition}

\begin{proof}
This is Blaze Proposition~5.4, restated with this paper's tensor convention
\(\MLE(\cdot)\) and equality polynomial \(\chi_a(r)\).  The proof is the
standard grand-product-to-sumcheck reduction used by CBBZ and imported by
Blaze.  The tagged leaf lists
\[
  \alpha-(x[b]+\beta\,\widehat\pi(b))
  \qquad\text{and}\qquad
  \alpha-(y[a]+\beta\,\Idx(a))
\]
have the same product when the permutation relation holds.  The tensors
\(f\) and \(g\) are product trees over those leaves: the two leaf equations bind
the bottom layer, the two Boolean-sum identities enforce the parent-product
recursion, and the root equality compares the two products.  If the
permutation relation is false, the two tagged products agree only for the
exceptional choices of \((\alpha,\beta)\) bounded above; conditioned on a
non-exceptional choice, the product-tree tests fail on all but the stated
fraction of projection points \(r\).  This is exactly the permutation input
used by Blaze Section~5.3.
\end{proof}

\begin{proposition}[Split-tree translation of Blaze Proposition~5.4]
\label{prop:native-permutation-reduction}
Let \(\pi:\B^n\to\B^n\) be a public permutation and let
\[
  x,y\in\F^{\B^n}.
\]
Use the push-forward convention fixed above:
\[
  y[\pi(b)]=x[b]\qquad(b\in\B^n).
\]
For verifier challenges \(\alpha,\beta\in\F\), define the intended tagged
leaf values
\[
  f[\mathsf{leaf}(b)]
  =
  \alpha-\bigl(x[b]+\beta\,\widehat\pi(b)\bigr),
  \qquad
  g[\mathsf{leaf}(a)]
  =
  \alpha-\bigl(y[a]+\beta\,\Idx(a)\bigr).
\]
In the split representation, these leaf lists are virtual.  If \(y=M_\pi x\),
then there exist internal product tensors
\[
  f,g\in\F^{\B^n}
\]
whose roots agree and whose split residuals vanish on every Boolean internal
coordinate with respect to the two displayed virtual leaf tensors.  If
\(y\ne M_\pi x\), then, except with probability at most \((N+1)/|\F|\) over
\((\alpha,\beta)\), every choice of \(f,g\) fails at least one of the root
or split-residual tests for all but a \(10n/|\F|\)-fraction of
\(r\in\F^n\).
\end{proposition}

\begin{proof}
This proof is the translation step, not a new permutation argument.  Blaze
Proposition~5.4 uses two \((n+1)\)-variate product-tree oracles.  Our protocol
stores only the internal product layers and derives the leaf layer from the
existing source handle.

Start with the honest case.  Under the push-forward convention
\(y[\pi(b)]=x[b]\), the two tagged leaf multisets are equal after the change of
variable \(a=\pi(b)\).  Therefore Blaze's full product-tree witnesses exist by
Proposition~\ref{prop:blaze-permutation-replay}.  Delete their leaf layer and
keep exactly the internal nodes; these internal nodes are the tensors
\(f,g\in\F^{\B^n}\) used by this paper.  Whenever the split residual needs a
leaf value, it recomputes the deleted leaf from the source tensor and public
tag:
\[
  L_{x,\widehat\pi}(b)
  =
  \alpha-\bigl(x[b]+\beta\,\widehat\pi(b)\bigr),
  \qquad
  L_{y,\Idx}(a)
  =
  \alpha-\bigl(y[a]+\beta\,\Idx(a)\bigr).
\]
Thus every parent-product equation in the full Blaze tree is represented by
one split residual equation in our internal tree, and the root equality is the
same scalar equality.

For soundness, suppose our split-tree checks pass for some internal tensors
\(f,g\).  Reattach the virtual leaf layers \(L_{x,\widehat\pi}\) and
\(L_{y,\Idx}\) to obtain full \((n+1)\)-variate product-tree oracles in the
sense of Proposition~\ref{prop:blaze-permutation-replay}.  The split residuals
are exactly the full-tree parent-product identities for those reattached
oracles, and the root equality is unchanged.  Therefore any adversary that
passes the split-tree tests with false permutation data gives an adversary
against Blaze Proposition~5.4 with the same \((\alpha,\beta,r)\), up to the
push-forward convention.  Since \(N=2^n\), the exceptional probability
\((N+1)/|\F|\) and the bad-projection fraction \(10n/|\F|\) are exactly Blaze's
\((2^m+1)/|\F|\) and \(10m/|\F|\) with \(m=n\).
\end{proof}

\paragraph{Native \(\RMLE[\PRAA]\) MLPCS.}

\begin{lemma}[Blaze native PRAA RMLE MLIOP replay in MLPCS notation; cf. Lemma~5.1 and Proposition~5.5]
\label{lem:blaze-native-praa-replay}
Fix permutations \(\pi_1,\pi_2:\B^n\to\B^n\), the repetition map
\(F_{\mathrm{rep}}\), the accumulation operator \(\Acc\), and the packed RAA
map
\[
  \PRAA=\Acc\circ M_{\pi_2}\circ\Acc\circ M_{\pi_1}\circ F_{\mathrm{rep}}.
\]
Let the public \(\RMLE[\PRAA]\) claim be
\[
  z\in\F^k,\qquad v\in\F,
\]
and let the implicit input oracle be an alleged codeword
\[
  y\in\F^{\B^n}.
\]
Blaze's native MLIOP, written here in our MLPCS notation, proves the exact
relation
\[
  \exists m\in\F^{\B^k}:
  \qquad
  y=\PRAA(m)
  \quad\text{and}\quad
  \MLE(m)(z)=v.
\]
It has perfect completeness.  If a deterministic cheating prover makes the
verifier accept while the displayed relation is false, then the verifier's
acceptance probability is at most
\[
  \frac{N+13n+7}{|\F|},
  \qquad N=2^n.
\]
This is Blaze Proposition~5.5 with Blaze's codeword length \(n_{\mathrm{Blaze}}\)
written here as \(N=2^n\).
\end{lemma}

\begin{proof}
This is the proof spine of Blaze Section~5.3, replayed before translating to
our handle presentation.

The prover's intended intermediate tensors are
\[
  u_1=F_{\mathrm{rep}}m,\qquad
  u_2=M_{\pi_1}u_1,\qquad
  u_3=\Acc(u_2),\qquad
  u_4=M_{\pi_2}u_3,\qquad
  u_5=\Acc(u_4).
\]
The verifier has MLE access to the implicit input \(y\), so Blaze writes
\(u_5\equiv y\).  The prover sends oracle access to
\[
  m,\quad u_2,\quad u_3,\quad u_4,
\]
and the verifier emulates access to \(u_1\) from \(m\) by the repetition view.
The verifier first checks the direct evaluation claim
\[
  \MLE(m)(z)=v.
\]

Next the verifier samples \(\alpha,\beta\leftarrow\F\).  For the two
permutation claims
\[
  u_2=M_{\pi_1}u_1,
  \qquad
  u_4=M_{\pi_2}u_3,
\]
the prover supplies product-tree witnesses
\[
  (f_1,g_1)
  \qquad\text{and}\qquad
  (f_2,g_2)
\]
as in Proposition~\ref{prop:blaze-permutation-replay}.  The verifier checks the
two root equalities.  It then samples \(r\leftarrow\F^n\) and checks the four
leaf equations for the two permutation products at \(r\).  Finally, the
verifier runs one scalar-batched sumcheck for six Boolean-sum claims:
\[
  u_3=\Acc(u_2),\qquad
  u_5=\Acc(u_4),
\]
and the four product-tree recurrence sums for
\[
  f_1,\quad g_1,\quad f_2,\quad g_2.
\]
This is exactly Blaze's Step~7: the two accumulator sums come from
Propositions~5.2 and~5.3, and the four product-tree sums come from
Proposition~5.4.  The scalar batching is the standard Remark~2.3 batch.

Completeness is direct.  If the witness \(m\) is honest and \(y=\PRAA(m)\),
then all five stage equations above hold.  Proposition~\ref{prop:blaze-permutation-replay}
provides product-tree witnesses for the two permutation stages, the two
accumulator identities hold for every \(r\), and the six sumcheck targets are
true.  Therefore every verifier check accepts.

For soundness, fix a deterministic cheating prover and name the oracles it
sends
\[
  m,\quad u_2,\quad u_3,\quad u_4,
\]
with \(u_1=F_{\mathrm{rep}}m\) and \(u_5=y\).  If \(\MLE(m)(z)\ne v\), the
verifier rejects immediately in the direct evaluation check.  Otherwise assume
\(\MLE(m)(z)=v\) and suppose \(u_5\ne\PRAA(m)\).  Then at least one of the four
stage equations is false:
\[
  u_2\ne M_{\pi_1}u_1,\qquad
  u_3\ne\Acc(u_2),\qquad
  u_4\ne M_{\pi_2}u_3,\qquad
  u_5\ne\Acc(u_4).
\]

If \(u_2\ne M_{\pi_1}u_1\), Proposition~\ref{prop:blaze-permutation-replay}
says that, except with probability \((N+1)/|\F|\) over
\((\alpha,\beta)\), the prover's chosen \(f_1,g_1\) fail at least one of the
root, leaf, or product-tree-sum tests for all but a \(10n/|\F|\)-fraction of
projection points \(r\).  A root or leaf failure is caught directly.  If the
failure is one of the two product-tree sums, the batched sumcheck rejects
except for the scalar-batching and sumcheck error bounded in Blaze by
\((3n+6)/|\F|\).  This gives the Case~1 rejection bound in Blaze
Proposition~5.5.

If \(u_3\ne\Acc(u_2)\), Proposition~\ref{prop:native-accumulator-reduction}
says that, except with probability \(n/|\F|\) over \(r\), the corresponding
accumulator Boolean-sum claim is false.  The batched sumcheck then rejects
except with the same \((3n+6)/|\F|\) batching/sumcheck error.  This is Blaze's
Case~2.

The cases \(u_4\ne M_{\pi_2}u_3\) and \(u_5\ne\Acc(u_4)\) are identical to the
first two cases, using the second permutation pair \((f_2,g_2)\) and the
second accumulator claim.  The soundness error is the maximum of these case
bounds, not their sum, because at least one fixed case applies to any fixed bad
transcript.  In the notation of this paper, this is bounded by
\((N+13n+7)/|\F|\).  Therefore, except with that probability, acceptance
implies all four stage equations and \(\MLE(m)(z)=v\), hence
\[
  y=u_5=\PRAA(m)
  \qquad\text{and}\qquad
  \MLE(m)(z)=v,
\]
contradicting falsity of the \(\RMLE[\PRAA]\) relation.
\end{proof}

\begin{lemma}[Native packed-RAA RMLE MLPCS; cf. Blaze Lemma~5.1 and Proposition~5.5]
\label{lem:native-praa-mlpcs}
Let
\[
  y\in\F^{\B^n},\qquad z\in\F^k,\qquad v\in\F
\]
be a base folded \(\RMLE[\PRAA]\) claim.  In the native
\(\mathcal F_{\mathrm{MLPCS}}\)-hybrid model, the verifier is given the input

\(\mathcal F_{\mathrm{HMLPCS}}^\delta\); after that bridge, the RAA checks are

  y=\PRAA(m)
  \qquad\text{and}\qquad

Completeness is perfect.  Soundness is the native algebraic soundness of Blaze

relation, the verifier rejects except with probability at most
\[
  \frac{N+13n+7}{|\F|},
  \qquad N=2^n.
\]
This is an exact native-MLPCS statement about represented tensors and requested
MLE evaluations.  It is not yet a proximity statement about a literal backend
encoded string.
\end{lemma}

\begin{proof}
The previous lemma is the Blaze proof in Blaze's native MLIOP language, already
renamed into our MLPCS interface.  This paragraph translates that proof to the
fixed protocol box
Figure~\ref{fig:native-blaze-fmlpcs-hybrid}.

The prover's represented input tensor is \(u_0\in\F^{\B^k}\).  The verifier
gets \(u_1\) as the derived repetition view \(F_{\mathrm{rep}}u_0\), receives
handles for \(u_2,u_3,u_4\), and treats the input folded word as
\[
  u_5=y.
\]
The direct endpoint request
\[
  (\widehat O_{u_0},z,v)
\]
enforces \(\MLE(u_0)(z)=v\) in the hybrid model.

The remaining checks force the RAA stage equations.  Proposition
\ref{prop:native-accumulator-reduction} is applied to
\[
  u_3=\Acc(u_2)
  \qquad\text{and}\qquad
  u_5=\Acc(u_4),
\]
using the two calls to \(\AccReduce\).  Proposition
\ref{prop:native-permutation-reduction} is applied to
\[
  u_2=M_{\pi_1}u_1
  \qquad\text{and}\qquad
  u_4=M_{\pi_2}u_3,
\]
using the two calls to \(\PermuteCommit\) and \(\PermuteReduce\).  The six

  u_2=M_{\pi_1}u_1,\quad
  u_3=\Acc(u_2),\quad
  u_4=M_{\pi_2}u_3,\quad
  u_5=\Acc(u_4).
\]
Since \(u_5=y\), this is exactly \(y=\PRAA(u_0)\), and the direct endpoint
request gives \(\MLE(u_0)(z)=v\).
\end{proof}

\begin{theorem}[Blaze backend RMLE proof input; cf. Theorem~4.1]
\label{thm:blaze-backend-rmle-input}
Let \(\lambda_{\mathrm{sec}}\) be the security parameter.  Let \(k\) be a power
of two, and let
\[
  \mathrm{RS}=\mathrm{RS}[\F,k,n]
\]
be a Reed--Solomon code with message length \(k\), blocklength \(n=O(k)\), and
relative distance \(d\in(0,1)\), over a binary extension field or smooth field
\(\F\) with \(|\F|>2^{\lambda_{\mathrm{sec}}}\).  For proximity parameter
\(\delta<d/3\), Blaze uses a backend IOPP for \(\RMLE[\mathrm{RS}]\) with
\[
  q_{\mathrm{inp}}=O(\lambda_{\mathrm{sec}}/\delta),
  \qquad
  q_{\mathrm{pf}}=O(\lambda_{\mathrm{sec}}\log k/\delta),
  \qquad
  \mathrm{rounds}=O(\log k),
\]
oracle proof communication \(O(n)\), non-oracle proof communication
\(O(\log k)\), soundness
\[
  2^{-\lambda_{\mathrm{sec}}}+O(\log n/|\F|),
\]
prover time \(O(n)\) given the encoded implicit input, and verifier time
\[
  O(\lambda_{\mathrm{sec}}\log k/\delta).
\]
\end{theorem}

\begin{proof}[Proof input]
This is Blaze Theorem~4.1, quoted from BaseFold and FRI-Binius.  Blaze uses it
as the backend \(\RMLE[C]\)-IOPP inside its MLIOP-to-IOPP compiler, which is
our MLPCS compiler after the terminology rename.  The theorem
does not prove anything about RAA by itself; it supplies the backend proximity
and evaluation check for a systematic encoded multilinear oracle.
\end{proof}

\begin{lemma}[Blaze MLIOP-to-IOPP compiler replay in MLPCS notation; cf. Lemma~4.2 and Proposition~4.4]
\label{lem:blaze-mlpcs-compiler-replay}
Let \(\Pi=(I,P,V)\) be an MLPCS for a relation \(R\).  Assume that each
multilinear oracle used by \(\Pi\) has at most \(\ell\) variables, and let
\[
  C:\F^{\B^\ell}\to\F^D
\]
be a systematic linear code of relative distance \(d\).  Suppose there is a
backend IOPP for the relation
\[
  \RMLE[C]:
  \qquad
  y\approx C(m)
  \quad\text{and}\quad
  \MLE(m)(z)=v.
\]
Then Blaze's compiler replaces the native MLPCS oracles by encoded oracle
strings and obtains an IOPP for \(R\).  Its soundness is the native MLPCS
soundness plus the backend \(\RMLE[C]\) soundness and the evaluation-batching
soundness error.
\end{lemma}

\begin{proof}
This is the proof spine of Blaze Proposition~4.4, which proves the compiler
used in Lemma~4.2.  We restate it before translating to our handle API.

First describe the compiled protocol.  The compiled prover and verifier
simulate the MLPCS transcript.  Whenever the MLPCS prover would send a
multilinear oracle \(m\in\F^{\B^\ell}\), the compiled prover instead sends the
encoded string
\[
  C(m)\in\F^D.
\]
If the relation has a long implicit input \(y\in\F^{\B^\ell}\), Blaze uses
that input as the systematic part of \(C(y)\): the prover sends only the
non-systematic part \(\widetilde y\), and together the two strings give oracle
access to
\[
  C(y)=y\Vert\widetilde y.
\]
For every MLPCS evaluation query
\[
  \MLE(m)(z)=v,
\]
the compiled protocol runs a backend \(\RMLE[C]\)-IOPP on the encoded oracle
for \(m\).  Before the backend calls, Blaze may batch all evaluation claims for
one oracle, and Remark~4.3 explains how to batch across oracles by using a
virtual multilinear polynomial.  The compiled verifier accepts only if the
simulated MLPCS verifier accepts and all backend \(\RMLE[C]\) checks accept.

Completeness is immediate: an honest prover sends honest encodings, the batched
evaluation claims are true, and the backend \(\RMLE[C]\)-IOPP accepts.

For soundness, fix a deterministic compiled prover.  Fix the public coins of
the simulated MLPCS transcript.  This fixes the literal encoded strings sent by
the compiled prover and the list of evaluation claims
\[
  (j,z,v),
\]
where \(j\) names the encoded string being queried.

Construct an unbounded native MLPCS prover \(\widetilde P\) from this compiled
prover as follows.  For each literal encoded string \(\pi_j\), check whether
\(\pi_j\) is within the chosen proximity parameter \(\delta<d/3\) of the code
\(C\).  If \(\pi_j\) is \(\delta\)-far from every codeword, \(\widetilde P\)
aborts.  Otherwise, since \(\delta<d/3\), the nearby codeword is unique; decode
it to a message tensor
\[
  m_j^\dagger\in\F^{\B^\ell}
\]
and give \(m_j^\dagger\) as the corresponding native MLPCS oracle.  For the
implicit input, Blaze applies the same step to
\[
  \pi_y=(y\Vert\widetilde y).
\]
If \(\pi_y\) decodes to \(y^\dagger\), then because \(C\) is systematic of rate
\(c\), distance \(\Delta(\pi_y,C(y^\dagger))\le\delta\) implies that the
literal input part \(y\) is at distance at most
\[
  \delta'=\delta/c
\]
from \(y^\dagger\).  Thus if the original input \(y\) is \(\delta'\)-far from
every valid implicit input for \(R\), then \((i,x,y^\dagger)\notin R\).

Now split into the two Blaze cases.  If some literal encoded string \(\pi_j\)
is \(\delta\)-far from the code, then the backend \(\RMLE[C]\)-IOPP rejects
except with its proximity soundness error.  If all strings are \(\delta\)-close
to the code, but some accepted evaluation claim
\[
  (j,z,v)
\]
is false for the decoded message \(m_j^\dagger\), meaning
\[
  \MLE(m_j^\dagger)(z)\ne v,
\]
then the batching protocol plus the backend \(\RMLE[C]\)-IOPP rejects except
with the batching error and backend soundness error.  If neither bad case
occurs, then every compiled evaluation response is consistent with the decoded
native tensors, so the compiled prover induces a genuine native MLPCS prover
\(\widetilde P\) for the decoded transcript.  Since the decoded implicit input
is not in the relation, native MLPCS soundness bounds \(\widetilde P\)'s
success.  Adding the backend and batching errors gives Blaze Proposition~4.4,
and the stated complexity parameters with the Reed--Solomon backend give
Blaze Lemma~4.2.
\end{proof}

\begin{lemma}[MLPCS-to-RMLE IOPP compiler in handle form; cf. Blaze Lemma~4.2 and Proposition~4.4]
\label{lem:mlpcs-to-rmle-compiler-handle}
Let \(\Pi\) be a native MLPCS whose verifier makes MLE evaluation requests
\[
  \MLE(h)(r)=w
\]
against finitely many native oracle tensors \(h\in\F^{\B^d}\).  Let
\[
  C_{\mathrm{backend}}:\F^{\B^d}\to\F^{D}
\]
be the systematic backend code used to authenticate those native tensors, and
assume we have a backend \(\RMLE[C_{\mathrm{backend}}]\)-IOPP.  Replacing each
native oracle handle by a literal backend string
\[
  y_h\in\F^D
\]
and each native evaluation request by the backend claim
\[
  y_h\approx C_{\mathrm{backend}}(h)
  \qquad\text{and}\qquad
  \MLE(h)(r)=w
\]
gives an IOPP for the same relation as \(\Pi\), with soundness equal to the
native MLPCS soundness plus the backend RMLE and batching errors.
\end{lemma}

\begin{proof}
Lemma~\ref{lem:blaze-mlpcs-compiler-replay} is the Blaze compiler proof in
Blaze's notation.  This paragraph is the handle-level dictionary used by our
protocol boxes.

A native handle
\[
  \widehat O_h:\F^d\to\F
\]
means exact MLE access to a native tensor \(h\in\F^{\B^d}\).  In the compiled
semantic view, that hatted handle is authenticated by a literal backend string
\[
  y_h\in\F^D.
\]
The backend check for a request \((\widehat O_h,r,w)\) is the expanded
\(\RMLE[C_{\mathrm{backend}}]\) statement
\[
  y_h\approx C_{\mathrm{backend}}(h)
  \qquad\text{and}\qquad
  \MLE(h)(r)=w.
\]
Thus the hatted handle remains the API-level object, while \(y_h\) is the
literal oracle string that the compiler/extractor reasons about.

Completeness follows by encoding every honest native tensor \(h\) as
\(C_{\mathrm{backend}}(h)\) and answering the same MLE values as the native
MLPCS.  For soundness, fix a deterministic compiled prover and expand every
authentication handle into its literal backend string \(y_h\).  The two cases
are exactly the two Blaze cases.

First, if some \(y_h\) is far from the backend code, the corresponding backend
\(\RMLE[C_{\mathrm{backend}}]\)-IOPP rejects except with its proximity
soundness error.  Second, if every \(y_h\) is close to the backend code, an
unbounded extractor decodes each nearby codeword to an effective tensor
\[
  h^\dagger\in\F^{\B^d}.
\]
The compiled verifier's accepted backend openings then imply that every native
request \(\MLE(h)(r)=w\) is true for the effective tensor
\(h^\dagger\), except with backend and batching error.  The extracted effective
tensors therefore define a native MLPCS transcript for \(\Pi\).  If the
underlying relation is false for those tensors, native MLPCS soundness rejects.

For the folded endpoint \(u_5\), our protocol uses
\(\mathcal F_{\mathrm{HMLPCS}}^\delta\) to name explicitly what Blaze obtains
from a systematic codeword \(C(y)=y\Vert\widetilde y\): the literal coordinate
string behind \(R_\star\) is the systematic/message part, and the effective
tensor used by the native MLPCS is the decoded nearby message.  This is a
presentation/API divergence from Blaze, but it is the same literal/effective
split from Proposition~4.4.
\end{proof}

\begin{theorem}[Blaze evaluation-batching proof input; cf. Theorem~2.4]
\label{thm:blaze-evaluation-batching-input}
Let \(f:\B^\ell\to\F\), and let \(\widehat f:\F^\ell\to\F\) be its
multilinear extension.  For any \(Q>1\), there is an interactive protocol that
reduces \(Q\) claimed evaluations of \(\widehat f\) to one claimed evaluation
of \(\widehat f\).  Its soundness error is
\[
  \frac{2^{\ell+3}\log_2(Q)}{|\F|},
\]
its prover time is \(O(Q2^\ell)\), its verifier time is \(O(Q\ell)\), its
communication is \(O(\ell+\log Q)\), and it uses
\(\ell+\log_2(Q)+O(1)\) rounds.
\end{theorem}

\begin{proof}[Proof input]
This is Blaze Theorem~2.4, quoted from CBBZ.  Blaze uses it first to batch
multiple evaluations of one multilinear oracle, and then invokes
Remark~4.3 to batch across different multilinear oracles by forming a virtual
multilinear polynomial.  The theorem is the source of the
\(2^{\ell+3}\log_2(Q)/|\F|\) term in Proposition~4.5.
\end{proof}

\begin{proposition}[Blaze batched compiler parameters replay; cf. Remark~4.3 and Proposition~4.5]
\label{prop:blaze-batched-compiler-replay}
Let \(\Pi=(I,P,V)\) be an MLPCS for a relation \(R\).  Suppose the largest
multilinear oracle used by \(\Pi\) has \(\ell\) variables, and let
\[
  Q=q_{\mathrm{inp}}+q_{\mathrm{idx}}+q_{\mathrm{pf}}
\]
be the total number of MLE evaluation requests made to input, index, and prover
oracles in the native MLPCS.  Let \(n_{\mathrm{oracle}}\) be the number of
prover oracles sent by the MLPCS prover, and assume, as in Blaze
Proposition~4.5, that there is one index oracle.  Let
\[
  C:\F^{\B^\ell}\to\F^{N_C}
\]
be a systematic code, and let \(\Sigma_C=(P_{\mathrm{mle}},V_{\mathrm{mle}})\)
be a backend IOPP for \(\RMLE[C]\).

Then the Blaze compiler from Lemma~\ref{lem:blaze-mlpcs-compiler-replay},
combined with the cross-oracle batching optimization from Remark~4.3, produces
an IOPP for \(R\).  In Blaze's parameter accounting, this compiled protocol has
soundness
\[
  \epsilon+\epsilon'
  +
  \frac{2^{\ell+3}\log_2(Q)}{|\F|},
\]
where \(\epsilon\) is the native MLPCS soundness and \(\epsilon'\) is the
backend \(\RMLE[C]\)-IOPP soundness.  Its round count is
\[
  \mathrm{rnd}+\mathrm{rnd}'+\ell+\log_2(Q)+O(1),
\]
its oracle proof communication is \(n_{\mathrm{oracle}}N_C+
cc'_{\mathrm{oracle}}\), and its non-oracle proof communication is
\[
  cc+cc'+O(\ell+\log Q).
\]
The backend proof-query complexity is
\[
  n_{\mathrm{oracle}}\cdot q'_{\mathrm{inp}}+q'_{\mathrm{pf}}.
\]
\end{proposition}

\begin{proof}
This is the content of Blaze Proposition~4.5, with the backend blocklength
renamed from \(n\) to \(N_C\) to avoid colliding with our tensor dimension.
The proof is the promised combination of Proposition~4.4 and Remark~4.3.

Proposition~4.4 already gives the soundness reduction: a cheating compiled
prover either sends a backend string far from \(C\), answers some MLE request
incorrectly for the unique decoded nearby tensor, or induces a cheating native
MLPCS prover.  The far-string and decoded-native cases are charged to
\(\epsilon'\) and \(\epsilon\).  The only new term in Proposition~4.5 is the
probability that the batching protocol hides at least one false evaluation
claim when the verifier compresses \(Q\) claims to one claim.  Blaze imports
the CBBZ/HyperPlonk multilinear-evaluation batching theorem for that step,
which contributes
\[
  \frac{2^{\ell+3}\log_2(Q)}{|\F|}.
\]

Remark~4.3 is the cross-oracle part.  Instead of running one backend
\(\RMLE[C]\)-IOPP for each multilinear oracle, the verifier forms one virtual
multilinear polynomial from all requested polynomials.  A query to the encoding
of that virtual polynomial is answered by querying the corresponding locations
of the original encoded oracle strings, one per original polynomial.  This is
why the backend proof-query count has the form
\[
  n_{\mathrm{oracle}}\cdot q'_{\mathrm{inp}}+q'_{\mathrm{pf}}:
\]
input queries of the backend virtual word fan out across original encoded
oracles, while proof-oracle queries of the backend IOPP are shared by the one
batched backend execution.  The additional \(\ell+\log_2(Q)+O(1)\) rounds and
\(O(\ell+\log Q)\) field elements are exactly the evaluation-batching
sumcheck and its terminal reduction to one MLE claim.
\end{proof}

\begin{proposition}[Batched backend RMLE requests in handle form; cf. Blaze Remark~4.3 and Proposition~4.5]
\label{prop:batched-backend-rmle}
The per-oracle backend checks in Lemma~\ref{lem:mlpcs-to-rmle-compiler-handle}
can be batched within a chosen group: the verifier reduces the requests in that
group
\[
  \MLE(h_j)(r_j)=w_j
\]
to one virtual multilinear evaluation claim, and one query to the virtual
backend word is emulated by the corresponding queries to the literal backend
strings \(y_{h_j}\).  The batching changes the proximity parameter and adds the
batching soundness term stated in Blaze Proposition~4.5, but it does not change
the semantic split: far backend strings are rejected, and close backend strings
decode to effective native tensors.

In the row-folded RAA instantiation we use two groups.  This is an intentional
divergence from a single all-oracles batch: the ordinary prover-originated
MLPCS tensors are batched together, while the folded endpoint tensor \(u_5\),
whose systematic coordinates are tied to the row-fold handle \(R_\star\), is
checked through a separate holographic backend claim.  This separation keeps
the ordinary batch at its ordinary backend proximity parameter instead of
forcing it to use the smaller parameter needed to bind \(u_5\) to the literal
string behind \(R_\star\).
\end{proposition}

\begin{proof}
Proposition~\ref{prop:blaze-batched-compiler-replay} is the literal Blaze
parameter statement.  The only dictionary needed for our protocol box is the
meaning of the virtual polynomial from Remark~4.3.

For a chosen group of handle-level requests
\[
  E=\bigl((\widehat O_{h_j},r_j,w_j)\bigr)_{j=0}^{q-1},
\]
Figure~\ref{fig:protocol-merge-native-evals} runs exactly the
CBBZ/HyperPlonk batching step used by Blaze.  It samples the list-address
challenge \(t\), defines the public selector \(\mathsf{Eq}_E\), runs one
sumcheck on \(G_t\mathsf{Eq}_E\), and obtains a single terminal claim
\[
  \widehat O_{\mathrm{batch}}(\eta)=w.
\]
The handle
\[
  \widehat O_{\mathrm{batch}}
  =
  \mathsf{RowFold.Commit}
  \bigl((\widehat O_{h_j},\lambda_j)_{j=0}^{q-1}\bigr)
\]
is our explicit API name for Blaze's ``virtual multilinear polynomial.''  A
backend query to this virtual object is implemented by same-address backend
queries to the original authenticated strings \(y_{h_j}\), combined with the
public coefficients \(\lambda_j\).  Thus the proof is still the Blaze
Proposition~4.5 proof: completeness follows from linearity, and soundness
fails only if the batching reduction hides a false constituent evaluation or
the backend \(\RMLE[C_{\mathrm{backend}}]\)-IOPP accepts a false/far encoded
claim.

In the row-folded RAA protocol we instantiate this proposition twice in spirit
but not symmetrically.  The ordinary requests are merged by
\(\mathsf{MergeNativeEvals}\).  The \(\widehat O_{u_5}\) requests are left out
of that group and are checked directly through
\(\mathcal F_{\mathrm{HMLPCS}}^\delta.\mathsf{Eval}\), because those requests
must bind the decoded effective tensor to the literal coordinate handle
\(R_\star\).  This is the intentional grouping divergence stated before
Figure~\ref{fig:protocol-merge-native-evals}; it weakens no Blaze proof step,
because running fewer requests inside a batch only removes batching
opportunities and leaves the same far/close backend cases.
\end{proof}

\paragraph{Composed theorem.}

\begin{theorem}[Blaze final composition replay; cf. Theorem~7.1]
\label{thm:blaze-final-composition-replay}
Let \(\lambda_{\mathrm{sec}}\) be the security parameter, and let \(\PRAA\) be
a packed RAA code over \(\F\) with message length \(K\) and block length \(N\),
where \(|\F|>2^{\lambda_{\mathrm{sec}}}\).  For every interleaving parameter
\(t=t(K)\), Blaze obtains an IOPP for
\[
  \RMLE[\PRAA^t],
\]
where the interleaved alphabet is \(\F^t\).  For proximity parameter \(\delta\),
the parameter table in Blaze Theorem~7.1 gives, in particular,
\[
  q_{\mathrm{inp}}=O(\lambda_{\mathrm{sec}}/\delta),
  \qquad
  q_{\mathrm{pf}}=O(\lambda_{\mathrm{sec}}\log N/\delta),
  \qquad
  \mathrm{rounds}=O(\log N),
\]
oracle proof communication \(O(N)\), non-oracle proof communication
\(2t+O(\log N)\), prover time \(O(tN+N\log N)\), and verifier time
\[
  O((t+\log N)\lambda_{\mathrm{sec}}/\delta).
\]
With \(t=\Theta(\log N)\), the stated prover time becomes \(O(tN)\) after the
linear-time interleaved RAA encoding optimization used by Blaze.
\end{theorem}

\begin{proof}
This is the three-line composition proof at the end of Blaze Section~7, with
the block length renamed from \(n\) to \(N\).

First, Blaze Lemma~5.1 gives what Blaze calls a native MLIOP for
\(\RMLE[\PRAA]\).  In our terminology this is the native MLPCS layer.  This
native protocol has a constant number of prover oracles and evaluation queries,
prover time \(O(N)\), and verifier time \(O(\log N)\).  Its content is the RAA
stage chain
\[
  u_1=F_{\mathrm{rep}}m,\quad
  u_2=M_{\pi_1}u_1,\quad
  u_3=\Acc(u_2),\quad
  u_4=M_{\pi_2}u_3,\quad
  u_5=\Acc(u_4)=y,
\]
together with the evaluation claim \(\MLE(m)(z)=v\).

Second, Blaze Lemma~4.2 compiles that native MLIOP, equivalently our native
MLPCS layer, into an IOPP for \(\RMLE[\PRAA]\) by authenticating each native
multilinear oracle with a
systematic backend code and replacing every native evaluation request by a
backend \(\RMLE[C]\) check.  This gives the base IOPP parameters quoted by
Blaze: \(O(\lambda_{\mathrm{sec}}/\delta)\) input queries,
\(O(\lambda_{\mathrm{sec}}\log N/\delta)\) proof queries, prover time
\(O(N\log N)\), and verifier time
\(O(\lambda_{\mathrm{sec}}\log N/\delta)\).  Blaze pads the smaller
message-size oracles to length \(N\) for ease of encoding, while noting that an
implementation can use different backend encodings for different oracle sizes.

Third, Blaze Lemma~6.1 bootstraps the base IOPP for \(\RMLE[\PRAA]\) to the
interleaved relation \(\RMLE[\PRAA^t]\).  The top-level prover sends the row
evaluation vector \(u\), the verifier checks \(\MLE(u)(z_{\mathrm{slice}})=v\),
samples \(\rho\), defines the folded word \(c_\star=\rho^\top c\) and folded
value \(v_\star=\langle\rho,u\rangle\), and invokes the base
\(\RMLE[\PRAA]\)-IOPP on \((c_\star,z_{\mathrm{in}},v_\star)\).  Each input
query made by the base IOPP becomes the corresponding query to the interleaved
input oracle.  Combining these three ingredients gives Blaze Theorem~7.1.
\end{proof}

\begin{theorem}[Interleaved packed-RAA RMLE IOPP in handle form; cf. Blaze Theorem~7.1]
\label{thm:interleaved-praa-rmle-iopp-handle}
Instantiate Lemma~\ref{lem:blaze-interleaving-handle} with \(C=\PRAA\).  Then
instantiate the base \(\RMLE[\PRAA]\) protocol by
Lemma~\ref{lem:native-praa-mlpcs} and compile its native evaluation requests by
Lemma~\ref{lem:mlpcs-to-rmle-compiler-handle}, using the grouped batching of
Proposition~\ref{prop:batched-backend-rmle}: one batch for the ordinary MLPCS
requests and one separate holographic backend check for \(u_5\).  The result is an
\(\RMLE[\PRAA^t]\)-IOPP for the fixed handle-level protocol above:
the literal matrix behind \(R_c\) is checked for proximity to an interleaved
packed-RAA codeword \(\PRAA^t(m)\), and the effective message satisfies
\[
  \MLE(m)(z_{\mathrm{slice}},z_{\mathrm{in}})=v.
\]
\end{theorem}

\begin{proof}
Theorem~\ref{thm:blaze-final-composition-replay} is the Blaze theorem in the
paper's own proof order.  We now translate the three layers to the fixed
handle-level protocol boxes above.

Lemma~\ref{lem:blaze-interleaving-handle} reduces a bad top-level interleaved
claim to a bad folded base claim, except for the row-fold error from
Lemma~\ref{lem:row-fold-proximity-gap}.  Lemma~\ref{lem:native-praa-mlpcs}
proves the folded base claim in the native MLPCS model by enforcing the RAA
stage equations and the terminal value \(\MLE(m_\star)(z_{\mathrm{in}})=v_\star\).
Lemma~\ref{lem:mlpcs-to-rmle-compiler-handle} and
Proposition~\ref{prop:batched-backend-rmle} replace the ideal native MLE
handles by backend encoded strings and grouped backend
\(\RMLE[C_{\mathrm{backend}}]\) checks.  Adding the stated soundness errors gives
the theorem.  Appendix~A of
Blaze supplies the round-by-round soundness form needed when this IOPP is later

\end{proof}

\paragraph{Round-by-round soundness import.}

\begin{proposition}[Blaze round-by-round soundness replay; cf. Appendix~A]
\label{prop:blaze-rbr-replay}
The IOPP for \(\RMLE[\PRAA^t]\) obtained in
Theorem~\ref{thm:blaze-final-composition-replay} is round-by-round sound in
the sense used by Blaze Appendix~A, assuming the underlying evaluation-batching
protocol, the backend \(\RMLE[C]\)-IOPP, and the native MLPCS building blocks
have the corresponding round-by-round soundness guarantees.
\end{proposition}

\begin{proof}
This is a replay of the proof skeleton in Blaze Appendix~A.  Round-by-round
soundness is phrased through a state function on partial public-coin
transcripts.  For a false instance, the empty transcript is in a doomed state;
after each prover message and verifier challenge, a doomed transcript remains
doomed except with the stated round error; and a verifier rejects every doomed
final transcript.

Blaze proves the claim in three layers.  First, Appendix~A.1 records
round-by-round soundness for the building blocks.  Evaluation batching starts
from a list of multilinear evaluation claims; the initial state is doomed when
at least one claim is false.  After the first batching challenge, the state is
doomed exactly when the induced sumcheck claim is false, and then ordinary
sumcheck round-by-round soundness applies.  The native MLPCS for
\(\RMLE[\PRAA]\) uses the same staged equations as Lemma~5.1:
\[
  u_2=M_{\pi_1}u_1,\qquad
  u_3=A u_2,\qquad
  u_4=M_{\pi_2}u_3,\qquad
  y=A u_4,
\]
together with \(\widehat m(z)=v\).  The doomed state is updated after the
\(\alpha,\beta\) permutation challenges, after the random point \(r\), and
after the terminal sumcheck transcript.  The CBBZ permutation reduction,
Schwartz--Zippel, and sumcheck RBR soundness ensure that doomed states remain
doomed except with the same algebraic errors used in Section~5.  Appendix~A.1
also recalls that the BaseFold backend \(\RMLE[\mathrm{RS}]\)-IOPP is RBR
sound by combining the standard sumcheck and FRI-style RBR arguments.

Second, Appendix~A.2 shows that the MLPCS-to-IOPP transformation preserves
round-by-round soundness.  The state first decodes the systematic implicit
input encoding \(\pi_y=(y\Vert\widetilde y)\) if it is \(\delta\)-close to the
backend code, and otherwise marks the transcript doomed.  Subsequent prover
oracles are treated the same way: a close encoded string contributes its
decoded native multilinear oracle to the simulated MLPCS transcript, and a far
string contributes \(\bot\).  The batching transcript is then governed by the
batching state function, and the final backend \(\RMLE[C]\)-IOPP transcript is
governed by the backend state function.  Thus an escape from a doomed compiled
state would imply an escape in the native MLPCS, the batching protocol, or the
backend \(\RMLE[C]\)-IOPP.

Third, Appendix~A.3 shows that the interleaving transformation preserves
round-by-round soundness.  For a false \(\RMLE[C^t]\) instance, the first state
after the prover's vector \(u\in\F^t\) is doomed if the input is far from
\(C^t\), or if the decoded message does not have row evaluations \(u_i\), or if
\(\widehat u(z_1)\ne v\).  After the verifier samples \(r\in\F^t\), the state
is doomed exactly when the folded instance
\[
  (z_2,\langle u,r\rangle,r^\top c)
\]
is not a valid \(\RMLE[C]\) instance at the reduced proximity parameter.  Blaze
uses Claim~6.1.1 and Corollary~2.6 to show that this doomed condition persists
with high probability.  The remaining interaction is the base
\(\RMLE[C]\)-IOPP, so its RBR soundness completes the argument for
\(\RMLE[\PRAA^t]\).
\end{proof}

\section{Native Hybrid Proof Rewrite}

\subsection{Inventory And \(\mathsf{OpenInner}\) Proof Target}

This subsection is the proof rewrite inventory.  It supersedes the
wrapper-style translation plan above: the finished proof should be a native
hybrid proof for the protocol of
Figure~\ref{fig:native-blaze-fmlpcs-hybrid}.  Blaze remains the mathematical
source for each transition, but the proof statements should be about our
handles, transcripts, virtual handles, backend openings, effective tensors,
rewinding, and extraction.

The proof now proceeds from the inside out.  The public entry point
\(\mathsf{Open}\) is only the row-folding adapter.  Its helper
\(\mathsf{OpenInner}(O_y,z,v)\) is the collapsed packed-RAA opener: it receives
an existing coordinate handle \(O_y:\B^n\to\F\cup\{\bot\}\), a point
\(z\in\F^k\), and a claimed value \(v\in\F\).  The API does not pass a string
\(y\).  In the proof, after a transcript prefix fixes \(O_y\), we write
\[
  y\in\F^{\B^n}
\]
for the concrete string behind that handle.  This is proof notation only.

The central functionality stack is:
\[
\begin{array}{rcl}
\EncMLE[C] &:&
  \text{encoded opening primitive for an already-fixed encoded oracle},\\
\mathrm{MLPCS} &:&
  \text{commit } O_{C(h)} \text{ first, then answer evals using }\EncMLE[C],\\
\mathrm{HMLPCS} &:&
  \text{message-domain proximity for an already-fixed message handle }O_y.
\end{array}
\]
The last line is the important one for \(\mathsf{OpenInner}\).  HMLPCS is not
itself \(\EncMLE[C]\): its input handle opens the message-domain string.  It can
be realized by a systematic backend
\[
  C_{\mathrm{sys}}(h)=h\Vert\mathrm{parity}(h),
\]
where the verifier's existing \(O_y\) supplies the systematic/message
coordinates and the prover supplies the parity coordinates.  If the systematic
fraction of the encoded word is \(\alpha\), then the backend encoded proximity
threshold must satisfy
\[
  \delta_{\mathrm{enc}}\le \alpha\delta
\]
to realize an HMLPCS message-domain threshold \(\delta\).

The extractor is MPC-style.  Fix an adversarial prover \(\prover^\ast\), a
transcript prefix before each verifier challenge, and the handles fixed at that
prefix.  The extractor may rewind to such a prefix, resample the next
challenge, and compare accepting continuations.  Accepted continuations expose:
\begin{itemize}[leftmargin=*]
  \item coordinate handles and the concrete strings behind them;
  \item ordinary MLPCS handles and their effective tensors;
  \item HMLPCS handles, whose effective tensors are close to an already-fixed
        message-domain handle;
  \item virtual handles such as \(R_\star\), determined by prior handles and
        verifier challenges;
  \item opened values and MLE-evaluated values returned by the ideal calls in
        the protocol.
\end{itemize}

\paragraph{High-level \(\mathsf{OpenInner}\) extraction sketch.}
The proof must keep the endpoint objects separate.  The input handle
\(O_y\) opens a concrete message-domain string
\[
  y\in\F^{\B^n}.
\]
Inside \(\mathsf{OpenInner}\), the protocol creates an HMLPCS evaluation handle
\(\widehat O_{u_5}\).  This name is protocol notation; it does not mean that
the string behind \(O_y\) literally equals the tensor evaluated by the handle.
If
\[
  \mathcal F_{\mathrm{HMLPCS}}^\delta.\mathsf{Eval}
    (\widehat O_{u_5},r)
\]
returns a field element, the ideal functionality returns
\[
  \MLE(u_5^\dagger)(r)
\]
for an effective tensor \(u_5^\dagger\in\F^{\B^n}\) stored behind
\(\widehat O_{u_5}\), and its contract gives only
\[
  \Delta(y,u_5^\dagger)\le\delta.
\]
In general \(y\) and \(u_5^\dagger\) are not equal.

The native RAA checks have a different job: they show that this effective
endpoint tensor is actually the output of the packed RAA pipeline.  From the
ordinary MLPCS handles the extractor obtains effective tensors
\[
  m^\dagger,u_2^\dagger,u_3^\dagger,u_4^\dagger
\]
and the helper tensors.  The accepted accumulator, permutation, repetition, and
sumcheck checks are then used to force
\[
  u_5^\dagger
  =
  \Acc(u_4^\dagger)
  =
  \PRAA(m^\dagger),
  \qquad
  \MLE(m^\dagger)(z)=v.
\]
Combining the HMLPCS proximity with the native RAA conclusion gives the
encoded-MLE statement for the packed RAA code:
\[
  \Delta\bigl(y,\PRAA(m^\dagger)\bigr)\le\delta,
  \qquad
  \MLE(m^\dagger)(z)=v.
\]
Equivalently, \(\mathsf{OpenInner}\) is the protocol-side realization of the
ideal opening
\[
  \mathcal F_{\EncMLE[\PRAA]}^\delta.\mathsf{Open}(O_y,z,v).
\]
This is the native form of the base \(\RMLE[\PRAA]\) claim used by the outer
row-fold argument.

\paragraph{Native proof target.}
The statement below is proved in this paper's handle/functionality model.  The
imported replay above remains available for source auditing, but the proof here
states the needed algebraic checks directly.

\begin{lemma}[Split-tree permutation soundness used by \(\mathsf{OpenInner}\)]
\label{lem:split-tree-openinner-soundness}
Fix \(x,y\in\F^{\B^n}\), a public permutation \(\pi:\B^n\to\B^n\), and
\(N=2^n\).  Assume the public address map \(\Idx:\B^n\to\F\) is injective and
that \(\widehat\pi(b)=\Idx(\pi(b))\) for every \(b\in\B^n\).  Let
\[
  L_x(b)=\alpha-\bigl(x[b]+\beta\,\widehat\pi(b)\bigr),
  \qquad
  L_y(a)=\alpha-\bigl(y[a]+\beta\,\Idx(a)\bigr)
\]
be the two virtual leaf tensors used by \(\PermuteCommit\).  If
\[
  y\ne M_\pi x,
\]
then, except with probability at most \((N+1)/|\F|\) over
\((\alpha,\beta)\leftarrow\F^2\), the following holds for every pair of
internal product tensors \(f,g\in\F^{\B^n}\): if
\[
  f[\mathsf{root}_P]=g[\mathsf{root}_P],
\]
then at least one of
\[
  \mathsf{SplitTreeRes}(f,x,\widehat\pi,\alpha,\beta;\cdot),
  \qquad
  \mathsf{SplitTreeRes}(g,y,\Idx,\alpha,\beta;\cdot)
\]
is a nonzero tensor in \(\F^{\B^n}\).  Consequently, for a fresh
\(r\leftarrow\F^n\), the probability that both projected split sums vanish is
at most \(n/|\F|\).
\end{lemma}

\begin{proof}
The false permutation relation means that the pair multisets
\[
  \{(x[b],\widehat\pi(b)):b\in\B^n\}
  \quad\text{and}\quad
  \{(y[a],\Idx(a)):a\in\B^n\}
\]
are not equal.  Indeed, since \(\Idx\) is injective and
\(\widehat\pi(b)=\Idx(\pi(b))\), equality of the pair multisets would force,
for every \(b\in\B^n\), the pair
\((x[b],\Idx(\pi(b)))\) to match the unique pair in the second multiset whose
second coordinate is \(\Idx(\pi(b))\).  That unique pair is
\((y[\pi(b)],\Idx(\pi(b)))\), so equality of multisets would imply
\(y[\pi(b)]=x[b]\) for all \(b\), namely \(y=M_\pi x\).

If \(\beta=0\), the address tags are erased; this exceptional
event has probability \(1/|\F|\).  For the remaining bad event, compare the
degree-\(N\) products
\[
  \prod_{b\in\B^n}\bigl(\alpha-(x[b]+\beta\,\widehat\pi(b))\bigr)
  \quad\text{and}\quad
  \prod_{a\in\B^n}\bigl(\alpha-(y[a]+\beta\,\Idx(a))\bigr)
\]
at the sampled \((\alpha,\beta)\).  Their difference is a nonzero polynomial in
\((\alpha,\beta)\) of total degree at most \(N\).  To see nonzeroness, view the
two products as factorizations over \(\F[\alpha,\beta]\).  Equality as formal
polynomials would make the multisets of linear factors
\(\alpha-(x[b]+\beta\widehat\pi(b))\) and
\(\alpha-(y[a]+\beta\Idx(a))\) equal, and hence would imply equality of the
pair multisets displayed above.  By
Schwartz--Zippel, this product-difference polynomial vanishes on a uniform
\((\alpha,\beta)\) with probability at most \(N/|\F|\).  Combining this with
the \(\beta=0\) event, except with probability \((N+1)/|\F|\), the two virtual
leaf products are different.

Now fix such a non-exceptional \((\alpha,\beta)\).  If a split residual tensor
is zero on all Boolean points, the internal tensor is a valid product tree over
its virtual leaves: at the bottom layer the residual equations give
\[
  P[0\Vert a]=L[a\Vert0]L[a\Vert1],
\]
and each higher layer equation gives parent equals product of its two children.
Induction over the tree layers therefore gives
\[
  P[\mathsf{root}_P]=\prod_{b\in\B^n}L[b].
\]
Apply this to \(f\) and \(g\).  If both split residual tensors were zero and
the roots were equal, then the two virtual leaf products would be equal,
contradicting the non-exceptional choice of \((\alpha,\beta)\).  Hence at
least one split residual tensor is nonzero.

For a nonzero residual tensor \(R\in\F^{\B^n}\), its multilinear extension is a
nonzero polynomial of total degree at most \(n\).  The projected split sum at
\(r\) is exactly \(\MLE(R)(r)\), so
\[
  \Pr_{r\leftarrow\F^n}[\MLE(R)(r)=0]\le\frac{n}{|\F|}.
\]
This proves the stated projection bound.
\end{proof}

\paragraph{Divergence from Blaze.}
The lemma above is the native proof for our split-tree presentation.  Blaze's
literal product-tree statement keeps a separate leaf layer and uses a
conservative \(10n/|\F|\) projection envelope.  Our protocol derives the leaf
values virtually from already-fixed handles and checks one split residual whose
Boolean vanishing directly implies the product-tree root value.  This changes
only the proof accounting for the helper representation; it does not change the
protocol box.

\begin{lemma}[\(\mathsf{OpenInner}\) realizes encoded MLE for \(\PRAA\)]
\label{lem:native-openinner-target}
In the
\(\mathcal F_{\mathrm{MLPCS}}/\mathcal F_{\mathrm{HMLPCS}}^\delta\)-hybrid,
\(\mathsf{OpenInner}\) realizes the encoded-MLE opening functionality
\[
  \mathcal F_{\EncMLE[\PRAA]}^\delta.\mathsf{Open}.
\]
More explicitly, for every PPT prover \(\prover^\ast\) attacking
\(\mathsf{OpenInner}\), there is a PPT extractor/simulator
\(\mathcal S_{\mathrm{inner}}^{\prover^\ast}\) that controls the verifier
challenges, extracts an effective \(m^\dagger\), sends \(m^\dagger\) to
\[
  \mathcal F_{\EncMLE[\PRAA]}^\delta.\mathsf{Open}(O_y,z,v),
\]
receives the ideal output bit, and samples a transcript consistent with that
bit.  The
statistical distance between the real uniform-challenge execution and this
programmed-challenge simulation is at most
\(\varepsilon_{\mathrm{inner}}\).
\end{lemma}

\begin{proof}
Write
\[
  N=2^n.
\]
\smallskip\noindent\textbf{Hybrid 0: accounting and naming only.}
The first hybrid is pure accounting.  It runs the real
\(\mathsf{OpenInner}(O_y,z,v)\) verifier in the
\(\mathcal F_{\mathrm{MLPCS}}/\mathcal F_{\mathrm{HMLPCS}}^\delta\)-hybrid and
then names the concrete or effective objects determined by the transcript.
The input coordinate handle \(O_y:\B^n\to\F\cup\{\bot\}\) determines a concrete
string
\[
  y\in\F^{\B^n}.
\]
The ordinary MLPCS handle \(\widehat O_{u_0}\) created in the protocol stores
an effective message tensor
\[
  m^\dagger\in\F^{\B^k}.
\]
For \(i\in\{2,3,4\}\), the ordinary MLPCS handle \(\widehat O_{u_i}\) stores an
effective tensor
\[
  u_i^\dagger\in\F^{\B^n}.
\]
The repetition view is virtual, so Hybrid~0 defines
\[
  u_1^\dagger:=F_{\mathrm{rep}}m^\dagger.
\]
The HMLPCS handle \(\widehat O_{u_5}\) created from verifier input \(O_y\)
stores an effective endpoint tensor
\[
  u_5^\dagger\in\F^{\B^n}.
\]
For \(j\in\{1,2\}\), the permutation helper handles
\(\widehat O_{f_j}\) and \(\widehat O_{g_j}\) store effective helper tensors
\[
  f_j^\dagger,g_j^\dagger\in\F^{\B^n}.
\]
Hybrid~0 also records the verifier challenges \(\alpha,\beta,r_{\mathrm{chk}}\),
the sumcheck transcript, the ordinary evaluation request set, the
\(\mathsf{MergeNativeEvals}\) transcript, and the HMLPCS endpoint evaluation
results.  This hybrid changes no verifier messages, challenges, oracle calls,
or accept/reject rule; it only names the objects fixed by those calls.
The named objects need not be mutually consistent.  In particular, Hybrid~0
does not yet produce the adversary's effective input for
\(\mathcal F_{\EncMLE[\PRAA]}^\delta\).

After Hybrid~0, the proof evaluates, as mathematical predicates on the named
objects, whether the transcript represents a valid encoded MLE opening.  The
remaining hybrids force those predicates one at a time by programming
challenges.  The common transition is as follows.

Fix a transcript prefix before the verifier challenge used by the target check,
and let \(\Omega\) be that challenge's sampling domain.  If the target relation
is false, define
\[
  A_{\mathrm{bad}}(\mathsf{prefix})
  \subseteq \Omega
\]
to be the challenge values for which the false relation is not exposed by this
check, and define the good set
\[
  G(\mathsf{prefix})
  :=
  \Omega\setminus A_{\mathrm{bad}}(\mathsf{prefix}).
\]
The real verifier samples uniformly from \(\Omega\).  The programmed hybrid
samples uniformly from \(G(\mathsf{prefix})\); equivalently, it samples a
challenge that forces this false predicate to be rejected.  If
\[
  p(\mathsf{prefix})
  =
  \Pr_{\omega\leftarrow\Omega}
    [\omega\in A_{\mathrm{bad}}(\mathsf{prefix})],
\]
then the statistical distance between uniform sampling from \(\Omega\) and
uniform sampling from \(G(\mathsf{prefix})\) is exactly
\(p(\mathsf{prefix})\).  Indeed, conditioning a uniform distribution on an
event of probability \(1-p\) changes it by total variation distance \(p\).

The rest of the proof bounds \(p(\mathsf{prefix})\) for each object.  A nonzero
degree-\(D\) polynomial over a uniformly sampled field point vanishes with
probability at most \(D/|\F|\) by Schwartz--Zippel.  A
\(\SumCheck_d\) with individual degree bound \(\Delta\) accepts a false sum
with probability at most \(d\Delta/|\F|\) once its terminal value is checked
against the relevant ideal MLE handles.  The factor \(d\Delta\) is the union
bound over the \(d\) sumcheck rounds: in each round, a false univariate
identity of degree at most \(\Delta\) can survive the verifier's random
challenge with probability at most \(\Delta/|\F|\).

\smallskip\noindent\textbf{Hybrid 1: endpoint proximity.}
This hybrid is identical to Hybrid~0 except that it explicitly rejects if
\[
  \Delta(y,u_5^\dagger)>\delta.
\]
The change has distance \(0\).  Indeed,
\(\widehat O_{u_5}\) was created by
\(\mathcal F_{\mathrm{HMLPCS}}^\delta.\mathsf{Commit}
(\prover:u_5,\verifier:O_y)\).  The second accumulator reduction always places
at least one request
\[
  (\widehat O_{u_5},r,w)\in\EvalReqs_{u5}
\]
into the endpoint request set, and step~I20 evaluates every such request through
\(\mathcal F_{\mathrm{HMLPCS}}^\delta.\mathsf{Eval}\).  If
\(\Delta(y,u_5^\dagger)>\delta\), that ideal evaluation returns \(\bot\), so
the comparison with the field value \(w\) rejects.  Hence every accepting
transcript in Hybrid~1 satisfies
\[
  \Delta(y,u_5^\dagger)\le\delta.
\]
This is the handle-level literal/effective split: \(y\) is the string opened by
the input handle, while \(u_5^\dagger\) is the effective tensor evaluated by
the HMLPCS handle.  In the present
\(\mathcal F_{\mathrm{HMLPCS}}^\delta\)-hybrid, proximity between them is an
ideal-functionality fact rather than a probabilistic backend claim.

\smallskip\noindent\textbf{Hybrid 2: ordinary evaluation requests are true.}
Let
\[
  \EvalReqs_{\mathrm{ord}}
  =
  ((\widehat O_{h_j},r_j,w_j))_{j=0}^{q-1}
\]
be the ordinary request list passed to \(\mathsf{MergeNativeEvals}\) in
step~I18.  Each \(\widehat O_{h_j}\) is either an ordinary MLPCS handle for one
of
\[
  m^\dagger,u_2^\dagger,u_3^\dagger,u_4^\dagger,
  f_1^\dagger,g_1^\dagger,f_2^\dagger,g_2^\dagger,
\]
or the virtual repetition handle whose represented tensor is
\[
  u_1^\dagger:=F_{\mathrm{rep}}m^\dagger.
\]
Hybrid~2 rejects whenever some ordinary request is false, namely whenever
\[
  \MLE(h_j^\dagger)(r_j)\ne w_j
  \quad\text{for some }j\in\{0,\ldots,q-1\}.
\]
The transition from Hybrid~1 to Hybrid~2 is justified by the algebra of the
batched-evaluation check.  After the transcript prefix fixes the handles,
points, and claimed values, \(\mathsf{MergeNativeEvals}\) uses verifier
randomness to form one linear combination of the individual identities
\[
  \MLE(h_j^\dagger)(r_j)=w_j.
\]
Let
\[
  \delta_j=\MLE(h_j^\dagger)(r_j)-w_j
  \qquad(0\le j<q),
\]
and let \(s=\lceil\log_2 q\rceil\), as in
\(\mathsf{MergeNativeEvals}\).  If some ordinary request is false, then the
polynomial
\[
  D(t)=\sum_{j=0}^{q-1}\chi_{\bits_s(j)}(t)\delta_j
\]
is not the zero polynomial on \(\F^s\), because its Boolean value at
\(\bits_s(j)\) is \(\delta_j\).  It is multilinear, so
\[
  \Pr_{t\leftarrow\F^s}[D(t)=0]\le \frac{s}{|\F|}.
\]
For this first batching challenge, the accepting-bad set is
\[
  A_{\mathrm{merge},t}
  =
  \{t\in\F^s:D(t)=0\},
  \qquad
  G_{\mathrm{merge},t}
  =
  \F^s\setminus A_{\mathrm{merge},t}.
\]
Thus replacing uniform \(t\leftarrow\F^s\) by uniform
\(t\leftarrow G_{\mathrm{merge},t}\) has distance at most \(s/|\F|\).

Conditioned on \(t\in G_{\mathrm{merge},t}\), the Boolean-sum claim in
\(\mathsf{MergeNativeEvals}\) is false.  The sumcheck has dimension \(s+n\)
and individual degree bound \(2\): the checked polynomial is
\[
  G_t(X,Y)\mathsf{Eq}_E(X,Y),
\]
where each factor is multilinear in \((X,Y)\).  Hence the sumcheck contribution
is
\[
  \frac{2(s+n)}{|\F|}.
\]
Equivalently, after \(t\in G_{\mathrm{merge},t}\) is fixed, let
\(A_{\mathrm{merge},\mathrm{sc}}(t)\) be the set of sumcheck challenge tapes
for which this false sumcheck still accepts, and let
\[
  G_{\mathrm{merge},\mathrm{sc}}(t)
  =
  \Omega_{\mathrm{sc}}^{s+n}\setminus
  A_{\mathrm{merge},\mathrm{sc}}(t).
\]
The sumcheck bound gives
\[
  \Pr[A_{\mathrm{merge},\mathrm{sc}}(t)]\le \frac{2(s+n)}{|\F|},
\]
so programming the sumcheck tape from
\(G_{\mathrm{merge},\mathrm{sc}}(t)\) changes the distribution by at most this
amount.  The notation \(\Omega_{\mathrm{sc}}^{s+n}\) denotes the verifier's
full random tape for the \((s+n)\)-round sumcheck.
There is one more explicit bad challenge for this presentation.  The verifier
divides by
\[
  e=\mathsf{Eq}_E(\xi,\eta).
\]
If \(e=0\), the protocol rejects.  This cannot help a cheating prover, but it
does affect the transcript distribution and honest completeness.  Define
\[
  A_{\mathrm{merge},e}
  =
  \{(\xi,\eta)\in\F^s\times\F^n:
    \mathsf{Eq}_E(\xi,\eta)=0\},
  \qquad
  G_{\mathrm{merge},e}
  =
  (\F^s\times\F^n)\setminus A_{\mathrm{merge},e}.
\]
The polynomial \(\mathsf{Eq}_E\) is nonzero when \(q>0\) and has total degree
at most \(s+n\), so
\[
  \Pr[(\xi,\eta)\in A_{\mathrm{merge},e}]
  \le \frac{s+n}{|\F|}.
\]
In the programmed hybrid, the simulator samples the merge sumcheck tape
conditioned on producing a terminal point \((\xi,\eta)\in G_{\mathrm{merge},e}\).
This is the same division-by-zero bad challenge that is implicit in Blaze's
batched evaluation step; we name it because the protocol box makes the division
explicit.

Thus the probability that a false ordinary request list passes is at most
\[
  \varepsilon_{\mathrm{merge}}
  :=
  \frac{s+2(s+n)+(s+n)}{|\F|}
  =
  \frac{4s+3n}{|\F|}.
\]
Therefore the output distributions of Hybrids~1 and~2 differ by at most
\(\varepsilon_{\mathrm{merge}}\).  In Hybrid~2 every accepting transcript has
all ordinary native terminal evaluations correct, including the public message
claim
\[
  \MLE(m^\dagger)(z)=v.
\]

\smallskip\noindent\textbf{Hybrid 3: accumulator identities.}
Hybrid~3 rejects unless the two accumulator relations on the extracted tensors
hold:
\[
  u_3^\dagger=\Acc(u_2^\dagger),
  \qquad
  u_5^\dagger=\Acc(u_4^\dagger).
\]
The first relation is checked by the first call to \(\AccReduce\), whose
terminal requests are ordinary requests and are already true in Hybrid~2.  The
second relation is checked by the second call to \(\AccReduce\), whose
ordinary-side terminal requests are true by Hybrid~2 and whose endpoint-side
terminal requests are exact HMLPCS evaluations of \(u_5^\dagger\).  If either
accumulator identity is false, choose the first false accumulator in protocol
order.  Let \((x_{\mathrm{acc}},y_{\mathrm{acc}})\) be the input and output
tensors of that chosen accumulator: either
\[
  (x_{\mathrm{acc}},y_{\mathrm{acc}})
  =
  (u_2^\dagger,u_3^\dagger)
\]
or
\[
  (x_{\mathrm{acc}},y_{\mathrm{acc}})
  =
  (u_4^\dagger,u_5^\dagger).
\]
For that accumulator, the tensor
\[
  R_{\mathrm{acc}}=y_{\mathrm{acc}}-\Acc(x_{\mathrm{acc}})
\]
is nonzero.  Its multilinear extension is a nonzero polynomial of total degree
at most \(n\), so the projection sampled in step~I9 satisfies
\[
  \Pr_{r_{\mathrm{chk}}\leftarrow\F^n}
  [\MLE(R_{\mathrm{acc}})(r_{\mathrm{chk}})=0]
  \le \frac{n}{|\F|}.
\]
For this projection challenge, define
\[
  A_{\mathrm{acc},r}
  =
  \{r\in\F^n:\MLE(R_{\mathrm{acc}})(r)=0\},
  \qquad
  G_{\mathrm{acc},r}
  =
  \F^n\setminus A_{\mathrm{acc},r}.
\]
Replacing uniform \(r_{\mathrm{chk}}\leftarrow\F^n\) by uniform sampling from
\(G_{\mathrm{acc},r}\) has distance at most \(n/|\F|\).  On this good set, the
corresponding Boolean-sum claim has nonzero error \(E_i\).  In
\(\RAASixSumcheck\), the verifier batches the six Boolean-sum errors as
\[
  E_0+\lambda E_1+\lambda^2E_2+\cdots+\lambda^5E_5.
\]
This is a nonzero polynomial in \(\lambda\) of degree at most \(5\), hence it
vanishes for a random \(\lambda\leftarrow\F\) with probability at most
\[
  \frac{5}{|\F|}.
\]
The number \(5\) is not a security parameter; it is one less than the number of
batched Boolean-sum claims.
Let
\[
  A_{\mathrm{acc},\lambda}
  =
  \{\lambda\in\F:
    E_0+\lambda E_1+\cdots+\lambda^5E_5=0\},
  \qquad
  G_{\mathrm{acc},\lambda}
  =
  \F\setminus A_{\mathrm{acc},\lambda}.
\]
Programming \(\lambda\) from \(G_{\mathrm{acc},\lambda}\) changes the
distribution by at most \(5/|\F|\).  Conditioned on these two good events, the
batched sumcheck claim is false.  The
sumcheck has dimension \(n\) and individual degree bound \(3\).  This degree
bound is the public parameter of \(\RAASixSumcheck\): each accumulator summand
is multilinear in the sumcheck variable, and each split-tree summand is bounded
by the declared degree-three expression used by
\(\mathsf{SplitEndpoint}\).  All terminal values are exact by Hybrid~2 and by
the HMLPCS endpoint evaluations.  If
\(A_{\mathrm{acc},\mathrm{sc}}(r,\lambda)\) is the set of \(n\)-round sumcheck
tapes that accept this false batched claim, and
\[
  G_{\mathrm{acc},\mathrm{sc}}(r,\lambda)
  =
  \Omega_{\mathrm{sc}}^n\setminus
  A_{\mathrm{acc},\mathrm{sc}}(r,\lambda),
\]
then
\[
  \Pr[A_{\mathrm{acc},\mathrm{sc}}(r,\lambda)]
  \le \frac{3n}{|\F|}.
\]
Sampling the sumcheck tape from
\(G_{\mathrm{acc},\mathrm{sc}}(r,\lambda)\) is the final programmed step for
this hybrid.  Therefore
\[
  \varepsilon_{\mathrm{acc}}
  :=
  \frac{n+5+3n}{|\F|}
  =
  \frac{4n+5}{|\F|}.
\]
Hybrid~3 is within
\(\varepsilon_{\mathrm{acc}}\) of Hybrid~2, and every accepting transcript in
Hybrid~3 satisfies the two displayed accumulator identities.  This also fixes
the priority rule for the shared challenge \(r_{\mathrm{chk}}\): when the
simulator reaches the \(r_{\mathrm{chk}}\) sample, it first checks the two
accumulator predicates.  If either accumulator predicate is false, it programs
\(r_{\mathrm{chk}}\) using \(G_{\mathrm{acc},r}\) for the first false
accumulator in protocol order.  Only when both accumulator predicates are true
does the simulator allow Hybrid~4 to use the same \(r_{\mathrm{chk}}\) sample
for a false permutation predicate.

\smallskip\noindent\textbf{Hybrid 4: permutation identities.}
Hybrid~4 rejects unless
\[
  u_2^\dagger=M_{\pi_1}u_1^\dagger,
  \qquad
  u_4^\dagger=M_{\pi_2}u_3^\dagger.
\]
For each \(j\in\{1,2\}\), the prover has already fixed helper tensors
\[
  f_j^\dagger,g_j^\dagger\in\F^{\B^n}
\]
after seeing \((\alpha,\beta)\).  For fixed tensors \(x,y\), the randomized
leaf tags
\[
  \alpha-\bigl(x[b]+\beta\,\widehat\pi(b)\bigr)
  \qquad\text{and}\qquad
  \alpha-\bigl(y[a]+\beta\,\Idx(a)\bigr)
\]
turn equality of the two tagged multisets into a single product identity.  If
\(y\ne M_\pi x\), choose the first false permutation in protocol order.  For
that pair, Lemma~\ref{lem:split-tree-openinner-soundness} gives two bad-event
terms.  First define the exceptional tag set
\[
  A_{\mathrm{perm},\alpha\beta}
  =
  \{(\alpha,\beta)\in\F^2:
      \text{the two virtual leaf products are equal}\},
\]
where this set also includes the tag-erasing event \(\beta=0\).  Let
\[
  G_{\mathrm{perm},\alpha\beta}
  =
  \F^2\setminus A_{\mathrm{perm},\alpha\beta}.
\]
The split-tree lemma gives
\[
  \Pr_{(\alpha,\beta)\leftarrow\F^2}
    [(\alpha,\beta)\in A_{\mathrm{perm},\alpha\beta}]
  \le
  \frac{N+1}{|\F|}.
\]
Thus programming \((\alpha,\beta)\) from
\(G_{\mathrm{perm},\alpha\beta}\) changes the distribution by at most
\((N+1)/|\F|\).

Condition on \((\alpha,\beta)\in G_{\mathrm{perm},\alpha\beta}\).  After the
prover sends the helper tensors, their effective root values are fixed.  If the
two root values are unequal, then the ordinary root-equality evaluation request
is false and Hybrid~2 rejects.  If the two root values are equal, the
split-tree lemma says that at least one split residual tensor is nonzero.  In
Hybrid~4 we are already in the branch where ordinary evaluation requests have
been forced true, so this second case is the only one that can still reach the
permutation residual projection.  For the chosen nonzero split residual
\(R_{\mathrm{perm}}\), define
\[
  A_{\mathrm{perm},r}
  =
  \{r\in\F^n:\MLE(R_{\mathrm{perm}})(r)=0\},
  \qquad
  G_{\mathrm{perm},r}
  =
  \F^n\setminus A_{\mathrm{perm},r}.
\]
The projection bound gives
\[
  \Pr_{r_{\mathrm{chk}}\leftarrow\F^n}
    [r_{\mathrm{chk}}\in A_{\mathrm{perm},r}]
  \le
  \frac{n}{|\F|}.
\]
Programming \(r_{\mathrm{chk}}\) from \(G_{\mathrm{perm},r}\) changes the
distribution by at most \(n/|\F|\).  Hence the probability that the false
permutation reaches the six-sumcheck with all permutation residuals hidden is
at most
\[
  \frac{N+1}{|\F|}+\frac{n}{|\F|}.
\]
Conditioned on avoiding those two bad events, at least one of the six
Boolean-sum errors entering \(\RAASixSumcheck\) is nonzero.  As above, scalar
batching by \(1,\lambda,\ldots,\lambda^5\) hides a nonzero six-error vector
with probability at most \(5/|\F|\).  Let
\[
  A_{\mathrm{perm},\lambda}
  =
  \{\lambda\in\F:
    E_0+\lambda E_1+\cdots+\lambda^5E_5=0\},
  \qquad
  G_{\mathrm{perm},\lambda}
  =
  \F\setminus A_{\mathrm{perm},\lambda}.
\]
Programming \(\lambda\) from \(G_{\mathrm{perm},\lambda}\) changes the
distribution by at most \(5/|\F|\).  Finally, after
\(\lambda\in G_{\mathrm{perm},\lambda}\), let
\(A_{\mathrm{perm},\mathrm{sc}}\) be the set of \(n\)-round sumcheck tapes that
accept the false batched sum and let
\[
  G_{\mathrm{perm},\mathrm{sc}}
  =
  \Omega_{\mathrm{sc}}^n\setminus A_{\mathrm{perm},\mathrm{sc}}.
\]
The degree-\(3\), \(n\)-round sumcheck bound gives
\[
  \Pr[A_{\mathrm{perm},\mathrm{sc}}]\le \frac{3n}{|\F|}.
\]
Sampling the sumcheck tape from \(G_{\mathrm{perm},\mathrm{sc}}\) changes the
distribution by at most \(3n/|\F|\).
Therefore
\[
  \varepsilon_{\mathrm{perm}}
  :=
  \frac{N+1+n+5+3n}{|\F|}
  =
  \frac{N+4n+6}{|\F|}.
\]
After these programmed choices, a false permutation is rejected by
construction.  Hence every accepting transcript in Hybrid~4 satisfies both
displayed permutation identities.

\smallskip\noindent\textbf{Hybrid 5: packed-RAA consistency.}
The repetition stage is not a probabilistic check: by definition of the
virtual repetition handle,
\[
  u_1^\dagger=F_{\mathrm{rep}}m^\dagger.
\]
Combining this definition with Hybrids~3 and~4 gives, for every accepting
Hybrid~5 transcript,
\[
  u_5^\dagger
  =
  \Acc(M_{\pi_2}\Acc(M_{\pi_1}F_{\mathrm{rep}}m^\dagger)).
\]
The right-hand side is exactly \(\PRAA(m^\dagger)\).  Thus the monolithic
\(\mathsf{OpenInner}\) checks have forced the effective endpoint tensor to be
the packed-RAA encoding of the same effective message tensor whose MLE was
checked at \(z\).

After these hybrids, every accepting transcript in the final hybrid satisfies
\[
  u_5^\dagger
  =
  \Acc(M_{\pi_2}\Acc(M_{\pi_1}F_{\mathrm{rep}}m^\dagger))
  =
  \PRAA(m^\dagger),
\]
and the endpoint proximity gives
\[
  \Delta(y,\PRAA(m^\dagger))\le\delta.
\]
The accumulated distance from the real ideal-functionality execution is
\[
  \varepsilon_{\mathrm{inner}}
  \le
  \varepsilon_{\mathrm{merge}}
  +\varepsilon_{\mathrm{acc}}
  +\varepsilon_{\mathrm{perm}}
  =
  \frac{4s+3n}{|\F|}
  +\frac{4n+5}{|\F|}
  +\frac{N+4n+6}{|\F|}
  =
  \frac{N+11n+4s+11}{|\F|},
\]
with no additional error for the ideal HMLPCS proximity step.  This is a
union-bound sum over the bad-challenge events; using a maximum instead would
only improve constants and does not change the parameter conclusion.

We can now describe the final programmed simulator.  The simulator
\(\mathcal S_{\mathrm{inner}}^{\prover^\ast}\) runs \(\prover^\ast\) and
generates the verifier challenges itself.  At each challenge point it first
checks the predicates already made meaningful by the current transcript prefix.
If the relevant predicate is false, it samples the next challenge from the good
set named above: \(G_{\mathrm{merge},t}\),
\(G_{\mathrm{merge},\mathrm{sc}}\), \(G_{\mathrm{merge},e}\),
\(G_{\mathrm{acc},r}\), \(G_{\mathrm{acc},\lambda}\),
\(G_{\mathrm{acc},\mathrm{sc}}\), \(G_{\mathrm{perm},\alpha\beta}\),
\(G_{\mathrm{perm},r}\), \(G_{\mathrm{perm},\lambda}\), or
\(G_{\mathrm{perm},\mathrm{sc}}\), as appropriate.  The shared
\(r_{\mathrm{chk}}\) challenge uses the priority rule from Hybrid~3:
accumulators first, then permutations.  If the relevant predicate is true, the
simulator samples the next challenge from the ordinary verifier distribution.
Therefore, in the final programmed hybrid, every false ordinary-evaluation,
accumulator, or permutation predicate is rejected by construction.  The
distance from the real interaction is at most the sum of the
uniform-versus-good-set conditioning losses bounded above, hence at most
\(\varepsilon_{\mathrm{inner}}\).

The simulator records the effective tensors named in Hybrid~0.  In the final
programmed hybrid, an accepting transcript necessarily satisfies
\[
  \Delta\bigl(y,\PRAA(m^\dagger)\bigr)\le\delta,
  \qquad
  \MLE(m^\dagger)(z)=v.
\]
The simulator sends this extracted \(m^\dagger\) to
\[
  \mathcal F_{\EncMLE[\PRAA]}^\delta.\mathsf{Open}(O_y,z,v)
\]
and receives the ideal output bit.  It then samples the remaining transcript
conditioned on that ideal bit: accepting transcripts are sampled only from the
all-predicates-good branch above, while rejecting transcripts are sampled either
from the functionality's rejecting behavior for the extracted input or from one
of the programmed rejecting branches for a false predicate.  If the corrupt
prover aborts or otherwise forces a rejecting transcript before a valid
effective input has been extracted, the simulator submits a fixed invalid
message \(m_{\bot}\) with \(\MLE(m_{\bot})(z)\ne v\); for example, take
\(m_{\bot}\) to be a constant tensor with constant value different from
\(v\).  The unchanged \(\EncMLE[\PRAA]\) functionality then returns reject by
its wrong-evaluation rule.  Thus the ideal functionality determines the output,
and the simulator's challenge programming supplies a transcript distribution
matching the final hybrid.  Combining the programmed hybrid with the distance
bound above proves the claimed realization error.
\end{proof}
