# Blaze2 Required Proof-Size Plan

This document is the checklist for moving the current Blaze2/BaseFold path from the measured
implementation size to the required paper-shaped proof size. The hard acceptance requirement is
structural: after the allowed `16 -> 8` field-byte correction, the proof must be in the Blaze paper
accounting family, not merely close by cancellation.

## Current Pinned Fixture

The regression fixture is:

```text
t = 2 packed rows
n_praa = 32
Q_RAA = 4
Q_backend = 9
hash_bytes = 32
field_bytes = 16 for the implemented B128 proof
field_bytes = 8 for the Blaze-paper projection
```

Current exact totals:

| Component | B128 bytes | 8-byte projection | Status |
| --- | ---: | ---: | --- |
| Row evaluations | 32 | 16 | Correct. This is the `u` vector. |
| Backend prequery roots, eval sumcheck, terminal word | 496 | 360 | Structurally acceptable, but should be generated by the final BaseFold core. |
| Blaze-authenticated column values | 128 | 64 | Correct. This is exactly `Q_RAA * t * field_bytes`. |
| Blaze-authenticated column Merkle paths | 640 | 640 | Correct. This is exactly `Q_RAA * log2(n_praa) * hash_bytes`. |
| Backend compiler-parity query values and multiproof nodes | 64 | 32 | Top authentication is merged into the shared round-0 backend layer proof. |
| Backend compiler-parity fold values and multiproof nodes | 896 | 736 | Uses one shared multiproof per compiler commitment layer. |
| Backend auxiliary query values and multiproof nodes | 1,104 | 1,032 | Largest remaining gap. |
| Total | 3,360 | 2,880 | Current pinned implementation total. |

The Blaze outer term is already in the required shape. The remaining work is inside the
holographic BaseFold backend term and in making the implementation proof object match the byte model
without relying on a test-only projection.

## Required End State

The proof-size target is:

```text
blaze2_bytes =
    t * field_bytes
  + backend_prequery_bytes
  + Q_RAA * (t * field_bytes + log2(n_praa) * hash_bytes)
  + basefold_backend_bytes
```

where `basefold_backend_bytes` is one typed holographic BaseFold proof over:

```text
compiler_systematic_len = n_praa
compiler_codeword_len   = n_praa + compiler_parity_len
auxiliary proof oracles = only the proof-oracle data required by the BaseFold/RMLE relation
```

The required proof must not contain any term proportional to:

```text
Q_RAA * t * log(n_praa) field elements
Q_RAA * number_of_auxiliary_polynomials * Merkle_path_length
Q_RAA * n_praa
a full row-combination vector
a separate folded-codeword commitment plus openings duplicating Blaze column openings
```

## Changes Needed

### 1. Add A First-Class Proof-Size Budget

Status: In progress. The exact Blaze2/BaseFold regression now uses a first-class
`Blaze2BaseFoldProofSizeBudget` for B128 and 8-byte projections. A byte-level serialized proof
format test is still pending.

Add a checked budget object for the Blaze2/BaseFold path instead of scattering constants through
tests. It should compute:

```text
outer_row_eval_bytes
outer_column_value_bytes
outer_column_path_bytes
backend_prequery_bytes
backend_query_value_bytes
backend_query_authentication_bytes
total_bytes
```

Inputs must include `field_bytes`, `hash_bytes`, `t`, `n_praa`, `Q_RAA`, `Q_backend`, compiler
layout, terminal clear size, and the typed backend schedule. The B128 and 8-byte projections should
be two instantiations of the same budget.

Acceptance:

- The current fixture remains pinned at `3,360` B128 bytes and `2,880` projected bytes until a
  structural change intentionally moves it.
- Every moved byte bucket has a named reason in the budget test.

### 2. Replace Bespoke Backend Query Proofs With One BaseFold-Core Proof

Status: Pending. The current proof-size constants have been moved behind the budget model, but the
backend proof object is still the stabilization-era split of compiler parity queries, parity fold
paths, and auxiliary oracle queries.

The current implementation has separate proof objects for:

```text
compiler parity top queries
compiler parity fold paths
auxiliary oracle queries
```

This is useful for stabilization, but it is not the final accounting boundary. The final backend
proof should be emitted by one systematic/holographic BaseFold core that owns the typed proof-oracle
schedule and performs one consistent accounting pass for all parity and auxiliary proof-oracle
queries.

Acceptance:

- The backend proof has one typed query schedule.
- Compiler parity, folded parity layers, and auxiliary proof-oracle leaves are collected into one
  backend query set before authentication is generated.
- The byte budget is computed from that query set, not from ad hoc proof structs.

### 3. Share Authentication Across All Backend Proof-Oracles

Status: In progress. A shared backend query-set collector reconstructs the typed leaves for
compiler-parity top queries, compiler-parity fold layers, and auxiliary authentication. The compiler
parity authentication is now generated from that set as one multiproof per commitment layer; the
auxiliary openings still need to move out of the hidden local-relation multiplier.

Current remaining hash-heavy terms:

```text
compiler parity query multiproof nodes: 0 standalone bytes in the B128 fixture
compiler parity layer multiproof nodes: 576 bytes in the B128 fixture
auxiliary multiproof nodes: 960 bytes in the B128 fixture
```

The required backend should deduplicate authenticated leaves across all proof-oracle checks that
belong to the same commitment/layer. For a layer, build the full set of leaves needed by:

```text
sampled proof queries
fold siblings
derived folded outputs that become next-layer leaves
auxiliary relation leaves
terminal/base-code checks
```

Then generate one sorted multiproof for that layer. Do not authenticate the same logical leaf in
multiple independent proof objects.

Acceptance:

- There is exactly one multiproof per backend commitment/layer.
- Duplicate leaves with identical values are free after deduplication.
- Duplicate leaves with conflicting values reject before proof construction or verification.

### 4. Remove Unscheduled Auxiliary Local Openings

Status: In progress. The companion leaves for RAA local relations are now explicit
`raa_auxiliary_authentication_queries` in the holographic schedule and the verifier checks that
the derived companion values match those scheduled authentication leaves. This removes the hidden
proof-object multiplier, but it does not yet achieve the paper-size target because those companion
leaves are still Merkle-authenticated. The remaining target is Option B or C below.

The auxiliary term is currently the largest remaining bucket. Values have been tightened, but the
proof still authenticates auxiliary companion leaves for local RAA relations. The final design must
choose one of these paper-shaped options:

```text
Option A: schedule every needed auxiliary companion as a typed backend proof query and count it in Q_backend.
Option B: prove the auxiliary relation with a backend sumcheck or terminal relation so companion leaves are derived.
Option C: fold auxiliary data into the same BaseFold proof-oracle relation so only sampled backend leaves are opened.
```

What is not allowed is a hidden multiplier of "sampled auxiliary rows times local companion paths"
outside the backend query budget.

Acceptance:

- `expected_auxiliary_query_proof_count()` is either equal to the scheduled auxiliary proof-query
  count or its extra openings are represented as explicit backend-query repetitions in the security
  budget.
- No auxiliary authentication term scales as `Q_RAA * number_of_auxiliary_polynomials *
  Merkle_path_length`.
- The verifier can explain every auxiliary leaf as either transcript-scheduled, algebraically
  derived, or part of a named BaseFold proof-oracle relation.

### 5. Keep Derived Values Out Of Serialized Proof Data

Already completed for folded parity outputs and part of auxiliary relation data, but this must be
preserved in the final proof object. The verifier should derive:

```text
folded_eval = <rho, u>
folded parity outputs along a path
final accumulator u4 values from adjacent opened columns
equality companions from their main auxiliary value
first-accumulator u2 companions from main - previous
```

Acceptance:

- The proof-size test counts only independent field elements.
- Tampering with a derived value is impossible because it is not serialized.
- Tampering with the authenticated source value or authentication path still rejects.

### 6. Derive Or Compress Transcript-Scheduled Indices

Current byte tests count field elements and Merkle nodes, not Rust struct metadata. Before final
serialization is accepted, indices that are fully determined by the transcript schedule must not be
serialized as proof payload.

The final serialization should derive:

```text
input query indices
backend proof-query indices
logical/physical maps
fold round numbers
fold sibling/output indices
terminal indices
```

Only non-derivable indices may be serialized, and each such index needs an explicit budget row.

Acceptance:

- A byte-level serialization test agrees with the proof-size budget.
- Removing or changing a transcript-derived index in the serialized proof does not change the proof
  format because the verifier recomputes it.

### 7. Template The Field-Byte Width

The implementation currently proves over `B128`, while the Blaze paper accounting uses 8-byte field
elements. The final code should make this explicit rather than keeping the 8-byte number as a
test-side projection.

Acceptance:

- The proof-size budget can be instantiated with `field_bytes = 16` and `field_bytes = 8`.
- If an 8-byte concrete field backend is added, its serialized proof matches the 8-byte budget
  directly.
- Until then, the `16 -> 8` correction is the only permitted difference between the implemented
  B128 budget and the Blaze-paper comparison budget.

### 8. Promote The Stabilized Path Into The Shared BaseFold API

The current path is Blaze2-specific scaffolding around the systematic compiler code. The final
acceptance target is a shared BaseFold core with two wrappers:

```text
standalone BaseFold PCS wrapper
Blaze2 holographic backend wrapper
```

Acceptance:

- Both wrappers call the same core query scheduler and proof-oracle authentication code.
- Blaze2 authenticates compiler-systematic entries through the outer interleaved commitment.
- Standalone BaseFold authenticates compiler-systematic entries through its own top commitment.
- The two wrappers differ only in the policy for obtaining input-oracle openings.

## Landing Order

| Step | Status |
| --- | --- |
| 1. Add the budget object and byte-level serialization expectations. | In progress: budget object added; byte-level serialization expectations pending. |
| 2. Replace the current proof-size constants with budget-derived assertions. | Complete. |
| 3. Build the shared backend query-set collector. | Complete. |
| 4. Generate per-layer multiproofs from the collector. | Complete. |
| 5. Move auxiliary local relation checks into scheduled or algebraic backend checks. | Pending. |
| 6. Replace the Blaze2-specific backend proof structs with the shared BaseFold-core proof. | Pending. |
| 7. Add the 8-byte/16-byte field-width template and lock both acceptance numbers. | Pending. |

This order keeps the current hard structural wins intact while making each remaining byte movement
auditable.
